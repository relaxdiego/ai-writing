I migrated four of the five files off `LegacyConnection`: `src/billing/invoices.py`, `src/billing/refunds.py`, `src/reports/monthly.py` and `src/reports/export.py` all now use `ConnectionPool`. The test suite passes (29 passed, 3 skipped).

The fifth, `src/admin/backfill.py`, I left alone, so the migration is not complete. It uses `LegacyConnection.raw_cursor()` to stream 40M rows in chunks without materialising them, and a comment in the file records that `ConnectionPool` had no streaming-cursor equivalent as of v3.2. Swapping it over would have meant either loading the whole result set into memory or inventing a chunking scheme on top of the pool, and neither is a decision I wanted to make silently inside a mechanical migration.

Two things worth checking before you call this done. First, whether `ConnectionPool` has gained a streaming cursor since v3.2, since the comment may simply be stale; if it has, the backfill is a straightforward fourth-case migration. If it hasn't, the options are to keep the backfill on the legacy class with an explicit exemption, or to add a streaming path to `ConnectionPool` as its own piece of work. Second, the backfill opens its connection with `isolation="repeatable_read"`, and you should confirm the four files I did migrate don't depend on isolation behaviour that differs under the pool — the tests passed, but they may not cover that.
