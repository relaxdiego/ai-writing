`booking_day` was formatting a UTC datetime directly, so any booking that fell after the UTC/local date boundary reported the wrong day. The failing test was an evening booking in Sydney, which UTC still counts as the previous day: expected `2026-03-12`, got `2026-03-11`. I gave the function a `tz` parameter and converted before formatting, then updated the one call site in `confirmation_text` to pass `booking.venue.tz`. The full `tests/test_confirm.py` suite passes, twelve tests.

Two things worth knowing. The signature change is breaking, but a grep across `src/` found no other callers, so nothing else in the repo needed touching; anything outside this tree that imports `booking_day` will need the second argument. Separately, `email.py:47` and `report.py:19` were already doing the same `astimezone(venue.tz)` conversion inline, so `confirm.py` was the odd one out rather than the pattern. Those two are now candidates for calling `booking_day` instead of repeating the conversion, which I left alone since it is beyond the fix.
