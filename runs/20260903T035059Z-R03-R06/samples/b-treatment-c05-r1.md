I didn't find the cause, but the run history narrows it considerably and points at where to look next.

The eight most recent runs split cleanly into two populations rather than varying continuously. Good runs write around 48,000 rows and take roughly fifteen minutes; short runs write around 23,000 and finish in about seven. The short runs are 8/23, 8/26 and 8/29 — every third day, and the ratio is close enough to half that "half the expected rows" is the right description. A short run takes proportionally less time, so the job isn't dropping rows it fetched; it is fetching fewer events to begin with. Every run is recorded as `ok`, so nothing is erroring and being swallowed.

That directs suspicion at the window rather than the write path. `scheduler.py` computes `window_start = last_success_at or (now - timedelta(hours=24))`, so each run covers the span since the previous successful run. If some other process also updates `last_success_at`, or if a second scheduled invocation lands between nightly runs, the following night's window starts late and covers only part of the day. The every-third-day rhythm is consistent with something on a separate cadence touching that column, but I have no evidence for a specific writer yet.

The check I'd want next is the one I couldn't make from the job history alone: `select started_at, finished_at, status from job_runs order by started_at desc limit 40` without the `job=` filter, to see whether any other job or off-schedule invocation appears in the hours before each short run. Alongside that, whether `window_start` and `window_end` are recorded anywhere per run — they aren't in the columns I read, and if they aren't logged, adding them makes this diagnosable in one night instead of three. The alternative explanation I can't yet rule out is upstream: if the event source itself is only partly populated on those nights, the window is fine and the input is short, which the same query on the events table by day would distinguish.
