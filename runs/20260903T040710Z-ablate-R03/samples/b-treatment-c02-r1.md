Start with the evidence you already have, because the shape of the distribution discriminates between whole classes of cause. Pool exhaustion is an accumulation hypothesis: leaked connections only go one direction, so the hang should land at or after a fairly stable point in the run, and should creep earlier as the leak worsens. A position that is genuinely uniform across the suite points instead at a per-moment race, something that can bite whichever test happens to be running when two schedules collide. So pull the last reported test from your last few dozen hung runs and plot where in the ordering it fell. Clustered late favours accumulation of some resource, whether that is connections, file descriptors, memory or threads; uniform favours timing. One caveat before you trust that plot: with buffered output the last line printed is not necessarily where the process stopped, so make the runner line-buffered and timestamp every test start and finish, otherwise you may be attributing a teardown hang to the next test's setup.

The pool theory is also cheap to falsify directly. Nearly every pool has an acquisition timeout, and a hang rather than an error means yours is effectively infinite. Set it to ten seconds. If exhaustion is real, the failure converts into a loud, fast error that names the test and prints a stack; if runs keep hanging at twenty minutes, you have eliminated the hypothesis for the price of one config line. The same logic applies more broadly: set `statement_timeout` and `lock_timeout` on the test database, set read timeouts on every HTTP and socket client, and set a per-test timeout in the runner. None of these fix anything, but they turn a silent hang into a labelled failure, which is the actual bottleneck in your investigation.

As for what else it could be, the candidates worth taking seriously all live in the CI-versus-local delta rather than in the code. CI runners typically have two vCPUs against your laptop's eight or ten, and thread pool or event loop starvation is acutely sensitive to core count: one blocking call made from an async context is harmless with ten workers and fatal with two. CI usually runs tests in parallel workers against one shared database, so two workers can take row or advisory locks in opposite orders; a genuine cycle gets killed by the deadlock detector in about a second, but a wait on a lock held by a worker that is itself stuck waits forever. CI talks to services over a container network where a dropped packet on an idle connection produces no RST at all, so a client with no read timeout blocks indefinitely, whereas locally the same call hits a service on loopback. Then there are the mundane ones: a dependent service that is listening but not ready, with a client that retries without bound; stdout backpressure, where the process blocks in `write` because the log collector stopped draining the pipe and 64KB filled up; and, on older base images, blocking on `getrandom` for entropy.

The step that actually settles it is capturing state at the moment of the hang instead of letting CI kill the job with no evidence. Add a watchdog that fires below the CI-level kill and, before exiting, dumps the stacks of every thread of every process: `py-spy dump --pid` for Python, `jstack` for the JVM, `SIGQUIT` for Go, `SIGUSR1` for Node. Alongside it, dump `pg_stat_activity` including `wait_event` and `state`, `pg_locks`, `ss -tanp`, your pool's in-use and waiter gauges, and `/proc/PID/status`. One good dump usually names the cause outright, and the signatures are distinct. A stack parked in pool acquisition with exactly max_size connections sitting idle in transaction is exhaustion. A stack inside the driver on a query, with `wait_event` of type Lock and a blocking pid belonging to another worker, is lock contention. A stack in `recv` with an established socket and a peer that no longer exists is a missing socket timeout. All workers alive, a backed-up queue and near-zero CPU is starvation. Blocked in `write` to fd 1 is the log pipe.

While you wait for a hang to reproduce in CI, try to buy it locally by matching the environment rather than the code: run the suite in a container with `--cpus=2` and the same worker count, in a loop of fifty. In parallel, flip exactly one CI variable per experiment, starting with worker count set to one, since a serial run that stops hanging implicates cross-worker contention and nothing else.
