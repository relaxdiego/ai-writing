The detail carrying the most information is that the location moves. A test that stops in a different place each run is usually not the cause; it is whatever happened to be executing when a condition that had been accumulating across the whole run crossed a threshold, or when something outside the process stalled. Before leaning hard on that detail, check what "hangs at test X" actually means in your logs. On CI, stdout is a pipe rather than a terminal, so it is block-buffered rather than line-buffered, and the last test name printed can be several tests behind where the process is really parked. Until you have a stack from the stuck process, treat the reported position as approximate.

It also helps to split the bug in two. A hang is a failure plus a missing deadline: some wait, on a socket read, a lock, a pool checkout, a queue get, a child process, has no timeout on it, so a transient that would otherwise have surfaced as a fast error instead becomes an infinite one. That means there are two independent questions, what the transient is and where the unbounded wait lives, and you can answer the second without knowing the first. Putting deadlines on every blocking call converts a silent hang into a located exception with a stack trace, which is both a mitigation and your best diagnostic instrument.

Your colleague's hypothesis belongs to a real family, just a larger one than they named. Anything finite that leaks across a run produces exactly your symptom pattern, because a leak plus a threshold is inherently late and position-dependent rather than test-dependent: connection pool slots, file descriptors, ephemeral ports left in TIME_WAIT by many short-lived connections, thread pool workers, PIDs under a container limit. The signature that separates this family from the others is that the hang correlates with cumulative work rather than with any particular test, so it should arrive at roughly the same depth into the run even when you shuffle the order. A pool leak specifically shows as monotonic growth in checked-out connections over the run and, on the Postgres side, as sessions sitting in `idle in transaction` in `pg_stat_activity`.

The reason it never reproduces locally is itself evidence, because that difference has to be mechanical. Your laptop has eight or twelve cores; the runner probably has two, and both your test framework's worker count and your library's default pool sizes are frequently derived from core count. Shrinking every pool at once is how you reach deadlocks that are unreachable locally: a lock held across an `await`, a synchronous call made from inside an event loop, or the classic case where every worker in a bounded pool is blocked waiting on a subtask that needs a worker from the same pool. With ten workers the subtask always finds a free slot; with two it sometimes does not, and the whole thing parks permanently.

Two more mechanisms explain "never locally" without any concurrency involved. The first is subprocess pipe deadlock: if an integration test spawns a service or a helper and waits for it to exit while nothing drains its stdout or stderr, the child blocks once the 64KB pipe buffer fills and the parent waits forever for an exit that cannot come. Locally the child's output usually goes to your terminal, which is always drained, and CI often runs with verbose flags that push output past the buffer size for the first time. The second is the difference between a refused connection and a blackholed one. Locally, a connection to a dead port gets an immediate RST; behind a CI network policy or egress proxy, packets to a disallowed or unreachable address are silently dropped, and a socket with no timeout waits indefinitely. The same code path that fails in a millisecond on your machine hangs forever there.

Finally, consider what is shared. If CI runs touch a common database, broker, Docker network, or advisory lock, then contention only exists when two runs overlap, which is invisible locally by construction and naturally produces a rate like one in twenty. Correlating the timestamps of hung runs against other concurrently running jobs is cheap and either finds a pattern immediately or clears the hypothesis.

The move that discriminates among all of these at once is capturing state from the hung process instead of inferring it from logs. Set a per-suite timeout comfortably below the job timeout so that you get a dump rather than a kill, and have it emit stacks for every thread: `faulthandler.dump_traceback_later` or `py-spy dump --pid` in Python, `jstack` or `kill -3` on the JVM, `SIGQUIT` with `GOTRACEBACK=all` in Go, the diagnostic report on a signal in Node. Alongside the stacks, capture `ss -tanp`, `lsof -p <pid>`, `ps -ef --forest`, and whatever counters your pool exposes. Each hypothesis has a distinct fingerprint in that artifact. Every thread parked in a pool acquire means exhaustion, and whether the held connections are idle or mid-query tells you leak versus slow query. One thread in `read()` on an ESTABLISHED socket to a service that is not sending means a network or service stall. A thread in `waitpid` or a pipe read with a live child means the buffer deadlock. Two threads each holding what the other wants is a genuine deadlock, and it will be visible as such.

To get a feedback loop faster than one observation per twenty runs, make the failure more likely rather than waiting for it. Run the integration suite in a loop inside a single soak job with the dump instrumentation enabled, run the CI image locally under `--cpus=2` with stdout redirected to a file rather than a terminal, and if you can get `NET_ADMIN`, add tens of milliseconds of latency with `tc netem` to widen whatever race window exists. As for the pool theory itself, you can falsify it in one run without any of that: set a short acquire timeout and a small maximum size. If the theory is right, you will start getting fast, frequent, clearly labelled pool timeouts instead of hangs; if the hangs continue unchanged, the pool was never the thing holding the run.
