Keying on the SQL string alone will serve one user's rows to another, so that part has to change before anything else does. With parameterized queries the authorization predicate is in the string but the user id is not: `SELECT ... FROM documents WHERE owner_id = ?` is a single key across your entire user base, and whoever populates it first decides what everyone else sees for as long as the entry lives. Interpolating the values into the key closes the obvious hole but not the whole class of them, since two requests can produce identical SQL text under different session or tenant state. The safe key is a hash over the statement, the full parameter tuple, and the authenticated principal, with the principal included even when you believe it is already implied by the parameters.

A global dictionary is also per-process, and you are running eight of them. Each worker warms its own copy, so a given entry is populated roughly one request in eight rather than once, and each of the eight has an independent notion of how stale it is. Because the load balancer moves a user between workers, they can read a fresh value on one request and the older cached value on the next, which reads as data flapping rather than as a cache being slightly behind. If the results are worth caching at all they are worth putting in Redis or memcached where all eight workers share one view.

At 400 writes a minute nothing in the plan ever removes an entry, so every cached row diverges from the database within seconds and stays that way, and the dictionary grows without bound until the worker is killed for memory. Both problems go away with the same mechanism: keep a generation counter per table in Redis, bump it on write, and fold the current generation of every table the query touches into the cache key. Writes then never have to enumerate which cached queries they invalidated, because stale entries simply become unreachable and age out under a TTL you set as a backstop, say thirty to sixty seconds.

Bump the counter after the transaction commits rather than before, or a concurrent reader will cache a value that never existed. The narrow race in the other direction is harmless: if a write commits while a read is in flight, the read stores its result under the generation it read at, and every subsequent lookup uses the new generation and misses. Each cached query costs you an MGET for its table generations, which is worth batching into one round trip and is only worth paying at all when the database work clearly dominates it.

Before building any of this, put timing on the queries in production and look at what the top few actually are. Query caching earns its complexity against expensive reads over slowly changing data; if the hot queries turn out to be frequent and individually cheap, the round trips will eat most of the win, and a missing index or a read replica will give you more than the cache would. That measurement also tells you which handful of queries to make cacheable explicitly, which is a much smaller and more auditable surface than caching everything by default and hoping the authorization key is right in every case.
