Caching is the right instinct — the specific shape you've described will break in ways that are hard to detect and expensive to unwind, so it's worth spending a few minutes on before writing the code.

The most urgent problem is the cache key. If your queries are parameterized (`WHERE user_id = ?`), the SQL string is byte-identical for every user on the system, so the first user to run a query populates the entry and every subsequent user gets served that user's rows. Row-level authorization enforced in the WHERE clause means the parameters *are* the security boundary, and keying on SQL text alone throws them away. The failure is silent — no error, no exception, just user 4102 looking at user 887's records — and it will show up first in whatever your most-trafficked authenticated endpoint is. If instead you're interpolating values directly into the SQL string, the key is user-specific and the leak goes away, but then almost every entry is used by exactly one user and the hit rate collapses toward zero, which is a lot of memory and invalidation risk for very little speed.

The second problem is that eight worker processes means eight dictionaries. A process-local cache only helps when the same worker handles a repeat of the same query, so your load balancer is spreading requests across workers that each have to learn the same data independently. You pay eight times the memory for roughly an eighth of the hit rate you're imagining, and workers disagree with each other about what the current data is — a user can refresh a page and see the new value, refresh again, land on a different worker, and see the old one.

Third, 400 writes per minute is a write every 150 milliseconds, and a plain dictionary has no invalidation and no eviction. Stale data accumulates permanently, memory grows without bound until the worker is OOM-killed, and read-your-own-writes breaks: a user saves a change, the response is rendered from a cached read, and their edit appears to have vanished.

What I'd suggest instead, roughly in order of effort:

Start by measuring rather than guessing. Turn on the slow query log or your APM's database breakdown for a day and find out which queries actually dominate wall-clock time. In applications at this write volume the answer is very often a handful of missing indexes or an N+1 in a hot endpoint, and fixing those gives a larger speedup than caching would, with no correctness risk at all.

For the queries that genuinely need caching, split them by whether they're user-scoped. Reference data that isn't per-user — config tables, category lists, feature flags, pricing tiers — is exactly the case your original idea handles well, and it can go in a process-local dict with a short TTL and a size cap, because there's no authorization boundary to violate and the data rarely changes. User-scoped results belong in a shared store like Redis, with a key built from the entity and every parameter that affects the result (`user:4102:orders:page:1`), never from the SQL text. Add a modest TTL as a backstop and invalidate explicitly on write by deleting the keys for the affected entity, which is straightforward to hook into your ORM's save path.

If it turns out reads are simply saturating the database, a read replica for reporting and list endpoints is often a cleaner fix than an application-level cache, since it has no staleness semantics you have to reason about beyond replication lag.
