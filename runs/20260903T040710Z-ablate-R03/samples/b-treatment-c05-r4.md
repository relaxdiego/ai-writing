I did not find a definitive cause, so here is what the evidence supports and where it runs out.

The failures are not random. The last eight runs are bimodal: either about 48,000 rows in roughly fifteen minutes, or about 23,000 rows in roughly seven, with nothing in between. The short nights are 23, 26 and 29 August, which is exactly every third day. The most informative detail is that the runtime halves along with the row count, because that points away from the write path. A duplicate-key collision, a partial commit, or a silent rollback inside the `transaction()` block would still have paid the full cost of fetching, grouping and summarising, so the run would take its usual fifteen minutes and write half as much. Instead the job is doing half the work end to end, which suggests it is being handed half the input.

That leaves two families of cause, and I could not separate them from inside the repo. The first is that the window is too narrow. `scheduler.py` computes `window_start` as `last_success_at`, falling back to 24 hours, and since every recorded run has status `ok`, each window should on paper be a clean day. But `job_runs` does not store `window_start` or `window_end`, so I cannot reconstruct the windows for the nights I care about, and the table holds only 30 rows in total, so I cannot tell whether this cadence predates either of the two recent commits. Any invocation that advances `last_success_at` without leaving a row would quietly halve the next window, and 9d02e1e, "fix: retry transient fetch errors", is the sort of change that can introduce an unlogged success path or a retry that returns a partial result instead of raising. I did not read `fetch_events` itself, so that possibility is still open.

The second family is that the source genuinely has fewer events on those nights. A precise three-day period is more characteristic of infrastructure than of application logic: a rotation across three read replicas where one lags, or an upstream compaction or retention cycle. Nothing in this repository would reveal it.

The check that separates the two is cheap. Record `window_start`, `window_end` and the raw row count returned by `fetch_events` alongside `rows_written`, then compare that raw count against an independent count of source events over the same interval. Following the pattern, the next short run should be the night of 4 September. If the source count over the window matches what was written, the window is short and the bug is in the scheduler's success bookkeeping; if the source holds roughly 48,000 events for that window and the job wrote 23,000, the loss is inside the fetch path.
