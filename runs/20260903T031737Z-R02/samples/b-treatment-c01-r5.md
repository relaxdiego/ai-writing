I replaced the hardcoded TTL in the session cache with the shared config constant. `src/cache/session.py` had `session_ttl = 3600` sitting on the class while `src/config/defaults.py` already defined `SESSION_TTL_SECONDS = 900`, so the cache was expiring entries four times slower than the configured value intended — I pointed the class attribute at the constant, which changes the effective TTL from an hour to fifteen minutes.

That broke `test_expiry_boundary` in `tests/test_session_cache.py`, which asserted the literal `3600`. Since the test was pinning the old hardcoded number rather than any behaviour, I updated it to compare against `SESSION_TTL_SECONDS` too; the full file now passes at 8 tests.

Two things worth flagging before you take this further. The behavioural change is real and user-visible — sessions will now expire after 15 minutes rather than 60, so if 3600 was the value people had been living with in practice, this is a functional change dressed as a refactor and you may want `SESSION_TTL_SECONDS` bumped instead. I also noticed while reading `get()` that `now` is used at line 88 without being assigned anywhere in the method, which suggests either a missing `now = time.time()` or a module-level import I didn't see in the excerpt I read; the tests pass, so something must be supplying it, but it's worth a look since I only viewed lines 80–95 of that file.
