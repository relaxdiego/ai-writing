The instinct to cache is fine; the key is what worries me. If your queries are parameterized, the SQL string is byte-identical for every user who hits the same endpoint, and the user id lives in the bound parameters rather than in the text. Keyed that way, the first user to run a query populates the entry and every subsequent user reads their rows out of it, so the authorization you carefully enforce in the WHERE clause stops mattering the moment the cache hits. Even if you interpolate literals into the SQL and get distinct keys, you are one refactor toward parameterization away from turning a performance change into a data breach, and that failure is silent: nothing errors, users just see each other's data.

The eight workers cause a second, quieter problem. A module-level dictionary is per process, so you get eight independent caches with no way to invalidate across them. A write that lands on worker 3 clears worker 3's entries and leaves the other seven serving stale rows, and since the load balancer picks a worker per request, a user who saves something will see it appear and disappear as they click around. At roughly 400 writes a minute you are producing about seven invalidation events per second against caches that cannot hear them, and without per-table tracking you don't even know which cached queries a given INSERT invalidates, so the honest options are flushing everything on every write (which leaves the cache nearly always cold) or a short TTL that accepts bounded staleness. The dictionary also never evicts, so it grows until the worker is OOM-killed and restarted, which is its own kind of cache invalidation.

What I'd suggest instead depends on what is actually slow, and I'd want to measure before adding any layer. Turn on slow query logging or pull the top queries by total time from pg_stat_statements, because in most applications this shape of fix is aimed at either a missing index or an N+1 loop, and both give you a much larger speedup than caching with none of the correctness risk. A query that drops from 800ms to 4ms with an index is faster than a cache hit and is always correct.

If measurement says caching is genuinely the answer, the version that works is a shared store such as Redis or Memcached so all eight workers see one cache, with the tenant or user id as an explicit part of every key rather than something you hope is embedded in the query text, a short TTL as a backstop, and invalidation driven by the tables a write touches. Tagging cached entries with their source tables and bumping a per-table generation counter on write is the usual way to make that tractable. It also helps to cache slightly above the SQL layer, at the level of a loaded object or a rendered fragment, since the key can then be something meaningful like `user:1234:dashboard:v7` that you can reason about and invalidate deliberately.
