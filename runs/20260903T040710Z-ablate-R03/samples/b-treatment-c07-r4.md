Before the performance question, there's a correctness one: the SQL string isn't a sufficient cache key in your application. Your authorization lives in the WHERE clause, and if you're using parameterized queries, the query text is byte-identical for every user; only the bound parameters differ. A dictionary keyed on that text will happily hand user B the rows the database returned for user A, and it will do so silently, on a cache hit, with no error anywhere to tell you it happened. The alternative, interpolating literals into the string so each user gets a distinct key, collapses the hit rate toward zero and reintroduces injection risk to buy nothing. Any workable key has to carry the full authorization scope: the parameter tuple and the acting principal, not the query text alone.

The process topology breaks the other half of the idea. Eight workers behind a load balancer means eight separate dictionaries, each starting cold, each holding its own copy of the same rows, and none able to evict from the others. A write handled by worker three cannot invalidate the entry worker seven is still serving. At roughly seven writes a second you would be generating stale entries continuously, with no bound on how long any of them survives, because a plain dict has neither TTL nor eviction and simply grows until the process runs out of memory. In an application where access is granted and revoked by changing rows, stale reads aren't just wrong data, they're data the user is no longer permitted to see.

So the first thing worth doing isn't caching at all. Get p95 latency broken out per endpoint, then look at the slow-query log for the endpoints that dominate. In my experience most "the app is slow" cases at this scale turn out to be an N+1 pattern issuing hundreds of round trips per request, or a missing index on a column that's in a WHERE clause on your hottest read path. Both are cheap to fix and neither introduces a coherence problem. Connection pooling and prepared statements are in the same category of cheap wins.

If real numbers still say you need a cache after that, the version worth building looks quite different from the one you described. Put the cache in a shared store such as Redis so all eight workers see one copy and one invalidation. Cache below the authorization boundary rather than above it: store entities keyed by primary key, fetch them from the cache, and apply the per-user filter in application code afterwards, so identity never has to enter the key and a bug in key construction can't turn into a data leak. Give every entry a short TTL as a backstop, and on each write invalidate the specific entity keys that write touched. At 400 writes a minute, per-entity write-through invalidation is entirely affordable; that write rate is low enough to be an asset here rather than an obstacle.
