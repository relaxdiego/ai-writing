Don't try to settle this by reasoning about causes: get a stack dump out of the hung process. Every hypothesis below produces a different set of stacks, and one dump will tell you more than a week of theorising.

The reason your colleague's answer feels unsatisfying is that it doesn't fit the failure rate. A leaked connection is an accumulating condition, and accumulation is deterministic: if each run of the suite leaks the same connections, every run should hang, at roughly the same point. One in twenty means either something is randomising the order in which the accumulation happens (a shuffled test order, a per-run worker count, tests distributed across shards differently each time), or the leak only occurs on an error path that is itself intermittent, or the cause isn't accumulation at all. Pool exhaustion also usually announces itself: most pools have an acquire timeout and raise "timed out waiting for connection" rather than blocking forever. Check whether yours has that timeout set to zero or infinity. If it's set to thirty seconds, the hypothesis is close to falsified for free.

It's also worth confirming what "hangs at a different test" means. The test named in the log is the last one whose output was flushed, and with buffered output under a non-TTY (which is what CI gives you) that can be far behind the real position, or the process may in fact have finished all tests and be stuck at exit on a non-daemon thread or an undrained subprocess. If the reported test differs every run but is always near the end, you are probably looking at a teardown or shutdown hang, not a test hang.

The plausible causes fall into three families, and a stack dump separates them in one shot. Something is waiting on a resource that will never be released; something is waiting for an event that already happened or will never happen; or something is waiting on I/O that has no timeout. Concretely:

- **Cross-worker interference.** CI runs the integration tests in parallel; you almost certainly don't, locally. Two workers sharing a database schema, a Redis keyspace, a fixed port or a temp path will occasionally collide. The classic version is a lock wait that isn't a cycle, so the database's deadlock detector never fires: worker A holds a row lock and is itself blocked on an HTTP call, worker B waits on that row forever because `lock_timeout` is unset.
- **A lost wakeup.** A test waits on an event, a condition variable or a queue that is signalled by another thread. On your eight-core laptop the ordering is one way; on a throttled two-core CI runner with noisy neighbours it flips, the signal fires before the wait begins, and the waiter blocks forever. This produces exactly your symptom pattern, including hanging at a different test each time.
- **I/O with no timeout, into a blackhole.** Locally, a connection to a service that isn't running is refused instantly. In CI, egress firewalls commonly drop packets rather than reject them, so the socket sits in `SYN_SENT` through TCP retransmits, and with no socket timeout that is indistinguishable from a hang. Slow DNS behaves the same way.
- **A full pipe.** A test spawns a subprocess, the parent doesn't drain its stdout, the 64 KB pipe buffer fills, and both sides block. CI is usually more verbose than local runs, which is why it only shows up there.
- **A service container that died.** If the database or a dependency gets OOM-killed by the container memory limit mid-run, a client with infinite reconnect retries will hang rather than fail. This is invisible in the test log; you have to look at container exit codes or the runner's memory graph.
- **Executor saturation.** Not the connection pool but a fixed-size thread pool where tasks submitted to the pool block waiting on other tasks in the same pool. Same shape as your colleague's theory, different resource.

To discriminate, start by making the hang observable. Wrap the suite in a timeout shorter than the CI job timeout, and on expiry dump every thread's stack before anything gets killed: `SIGQUIT` for a JVM or Go process, `py-spy dump --pid` for Python, the inspector via `SIGUSR1` for Node. In the same handler, capture `ss -tanp` and, if a database is involved, `pg_stat_activity` including `wait_event_type` and `wait_event`, plus `pg_locks`. That single artifact distinguishes blocked-on-socket-read from waiting-on-a-semaphore from waiting-on-a-row-lock from joining-a-thread.

Two cheap experiments narrow it further while you wait for a hang to reproduce. Run the suite in CI with one worker, twenty times: if the hang vanishes, it's cross-worker interference and you can stop considering the network theories. And log the pool's active, idle and waiting counts after every test, which turns your colleague's hypothesis into a measurement: a leak shows a monotone ramp across the run, and its absence retires the idea permanently.

For the "never locally" half, the useful move is to stop treating your laptop as the control. Run the suite locally under `docker run --cpus=0.5` with the same worker count as CI, which reproduces most lost-wakeup races, and separately with egress to external hosts dropped rather than rejected (`iptables -j DROP`), which reproduces the blackhole class. If either makes it hang, you have a local repro and the rest is ordinary debugging.
