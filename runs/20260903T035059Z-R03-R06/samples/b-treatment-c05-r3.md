I didn't find the cause, but the run history narrows it considerably, and there's one thing I'd want you to check before anything else.

The eight most recent runs split cleanly into two populations rather than varying continuously. Good runs write roughly 48,000 rows and take about fifteen minutes; short runs write roughly 23,000 and finish in seven. That ratio is close enough to half that "half the expected rows" is literally what's happening, and the duration scales with it, so the job isn't failing partway through a fixed amount of work — it is being handed about half the input and processing all of it happily. Every run is marked `ok`, which fits: nothing is erroring, so nothing complains.

The most likely explanation given the code I read is the window boundary in `jobs/scheduler.py:61`, where `window_start` is `last_success_at or (now - timedelta(hours=24))`. If a run ever starts from a `last_success_at` that is only twelve hours old rather than twenty-four, it fetches half a day of events and writes half the rows. That could happen if some other process or a manual invocation updates `last_success_at` between nightly runs, if `last_success_at` is stored or compared in a different timezone or as a naive timestamp against a tz-aware `now`, or if a retry path writes a success marker. The retry commit `9d02e1e` is worth reading closely for that last possibility — retrying a transient fetch error is exactly the kind of change that can end up recording a partial success. I did not verify any of these; the scheduler file was only grepped, not read end to end.

I also could not rule out an upstream cause, where the events simply aren't all present at 02:00 on those nights because whatever populates the source table is late or partitioned. Distinguishing between the two is a single query: for one short night and one good night, count the source events in the full 24-hour window and compare against `rows_written`. If the source counts match on both nights, the job is choosing the wrong window and the bug is in the scheduler; if the source itself is short on the bad night, the problem is upstream and `nightly_rollup.py` is behaving correctly.

Two things I noticed but couldn't pursue. The short runs fall on 2025-08-23, 26 and 29, which is every third day, and a regular period like that points at something scheduled rather than something random. The full thirty rows of `job_runs` would confirm whether that spacing holds historically. Separately, `run()` wraps all the writes in one transaction but the row count comes from `job_runs`, so I don't know whether `rows_written` is recorded from the loop or computed independently, which matters for trusting the number at all.
