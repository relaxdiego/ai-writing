Before ranking causes, be suspicious of the observation that's doing the most work in your reasoning. "Always at a different test" is only meaningful if you know where it actually hung, and in CI you usually don't. Standard output is block-buffered when it goes to a pipe rather than a TTY, so the last line you see is wherever the buffer happened to flush, not where the process stopped. That alone can manufacture the appearance of a wandering hang point from a single deterministic culprit. Check whether the runner forces unbuffered output (`PYTHONUNBUFFERED`, `stdbuf -oL`, your framework's equivalent); if it doesn't, the "different test each time" evidence should be set aside entirely until it does.

The reason this class of bug lives in CI and not on your machine is that the two environments differ in specific, enumerable ways, and most of them are ways that can produce an infinite wait. In CI the tests usually run with parallelism or sharding you don't use locally; output goes to a pipe instead of a terminal; stdin is a closed pipe or `/dev/null` rather than a keyboard; dependent services are containers on a bridge network rather than processes on loopback; memory and CPU are capped by a cgroup so the OOM killer is a live actor; and the runner is often shared with other jobs, so load spikes are real. Writing down which of these apply to your setup narrows the field faster than any amount of speculation about the application.

Pool exhaustion is a real candidate, and it isn't crazy, but it has a specific signature you can check for rather than argue about. A leak means some fraction of tests each retain a connection, so the hang arrives once the cumulative leak count crosses the pool size, which under randomised ordering lands at a varying test but after a roughly constant number of leak-inducing ones. It also requires that your pool has no acquisition timeout, because a pool with a timeout produces a fast error with a stack trace, not a hang. Competing with it are several explanations that fit your symptoms at least as well. A socket with no read timeout against a peer that died without sending FIN, which is what happens when a container is killed or a bridge network drops state, blocks until TCP keepalive notices, and the default there is two hours. A database deadlock on advisory locks or explicit table locks can sit for the length of `lock_wait_timeout` rather than being detected and aborted. A subprocess writing to a pipe nobody drains fills the 64KB kernel buffer and blocks forever, which is purely a CI phenomenon and gets worse when you turn logging up in CI. A tool that decides to prompt for input, for an SSH host key or a git credential, waits on a stdin that will never deliver. A worker process killed by the OOM killer leaves the coordinator waiting on a result that isn't coming, and shows up as exit code 137 or an entry in `memory.events`. And ordering-dependent shared state, where test A leaves a lock or a global behind and whichever test follows it hangs, explains a moving failure point directly if your runner randomises the seed per run.

Rather than reason further from the outside, get a stack dump out of the hung process, because that single artifact discriminates among nearly all of the above in one shot. The obstacle is that CI timeouts send SIGKILL, which tells you nothing, so you need your own watchdog firing before the platform's: wrap the test command in `timeout -s QUIT 20m ...` or the equivalent, with the job timeout set comfortably higher. On the JVM, SIGQUIT gives you a thread dump with lock ownership, and HikariCP's `leakDetectionThreshold` will name the leaked connection's acquisition site. In Go, SIGQUIT dumps every goroutine stack, and the test binary's own `-timeout` should already be panicking with the same information, so if you never see that panic the hang is outside the test process. In Python, enable `faulthandler` and call `dump_traceback_later`, or attach `py-spy dump --pid` from a sidecar. In Node, the usual finding is an open handle rather than a blocked thread, which `why-is-node-running` will identify. Threads parked on an internal condition variable, threads blocked in a socket read, and threads waiting on pool acquisition are three visibly different pictures.

Alongside that, run a sampler in the background of the CI job that appends a snapshot every ten seconds: `ss -tanp` for socket states and counts, your pool's active and waiting gauges, `ps -eLf`, `pg_stat_activity` or `SHOW ENGINE INNODB STATUS` on the database side, and the cgroup memory counters. When a run hangs you then have a time series instead of a corpse, and the socket table is unusually informative. A wall of ESTABLISHED connections to the database with nothing in flight plus threads waiting to acquire points at exhaustion or a long query; ESTABLISHED connections whose peer container has already exited points at the missing read timeout; a rising count of CLOSE_WAIT means your code isn't closing sockets; and a quiet socket table with parked threads sends you back to an application-level deadlock.

One cheap experiment settles the pool question on its own. Set the acquisition timeout to ten seconds and rerun. If the theory is right, the failure converts from a hang into a fast, legible error naming the thread that couldn't get a connection; if the job still hangs, the pool is not your problem and you've spent an hour to eliminate it. That's worth more than raising the pool size, which can mask a lock problem and give you a false confirmation. In parallel, try to reproduce locally under CI conditions rather than your usual ones: the same image, the same cgroup limits, the same parallelism, stdout piped to `cat > /dev/null`, stdin from `/dev/null`, in a loop. If it hangs there, the loop is now your debugging harness; if two hundred runs pass, the cause lives in the runner environment rather than your code. Whatever you eventually change, hold off on declaring it fixed too early: at a one-in-twenty base rate, ten green runs happen 60% of the time by luck alone, and you need about sixty consecutive passes before the silence means anything.
