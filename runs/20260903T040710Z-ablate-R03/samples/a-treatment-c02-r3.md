Your instinct is worth taking seriously, and the specific detail that makes me share it is "always at a different test." A leaked-connection pool exhaustion bug is cumulative: connections escape back to the pool unreturned, and the run dies at whichever test crosses the threshold. Under a fixed test order that is the same test nearly every time, and under any order it is biased toward the back half of the run. So the first question to settle is whether your runner randomizes order (pytest-randomly, `--order-randomly`, Go's shuffle, RSpec's random seed). If order is fixed and the hang location really is scattered uniformly across the suite, that is genuine evidence against the pool theory. If order is randomized, "a different test" tells you almost nothing and you need to look at the test *index* rather than the test *name*.

The broader family the pool theory belongs to is the real suspect: some wait in your integration path has no deadline on it. A pool checkout with no timeout, an HTTP client with no timeout, a socket read, a lock acquisition, a queue receive, a "wait for the service to be healthy" loop with no bound. Locally these never bite because the resource is always there in single-digit milliseconds. On CI the database is a sidecar container on a contended host, DNS goes through a different resolver, and the runner has two cores instead of your ten, so a wait that is normally instant occasionally isn't, and an unbounded wait turns a slow response into an infinite one. One run in twenty is exactly the shape of a tail-latency event meeting a missing timeout.

Two other candidates fit the fingerprint as well as pool exhaustion does. The first is contention between parallel test workers over a shared external resource: two workers touching the same rows, the same advisory lock, or the same fixture table, blocking each other in a way the database's deadlock detector doesn't classify as a deadlock and therefore never breaks. Which pair collides depends on scheduling, so the hanging test differs every time, and it disappears locally because you likely run with different parallelism or a private database. The second is the classic subprocess pipe deadlock: a child process fills its stderr pipe buffer while the parent waits for the child to exit, and neither moves. That one is famously CI-specific because locally you often have a TTY or different buffering.

Also worth separating before you go further: does the run hang *during* a test or *after the last one*? A non-daemon thread, an unclosed event loop, a lingering container client, or an atexit handler waiting on a connection will let every test pass and then hang the process at exit. Your job log will look identical to a mid-test hang unless you check whether a test was in flight.

The way to tell these apart is to stop reasoning about it and get a stack dump out of the hung process, which is cheap to arrange. Set a suite timeout comfortably below the CI job timeout and make it dump every thread's stack rather than just killing the job. In Python that is `faulthandler.dump_traceback_later(N, exit=True)`, or `py-spy dump --pid` from a watchdog step; in Go, sending SIGQUIT prints all goroutine stacks; in Java, `jstack` or `kill -3`; in Node, `process.report.writeReport()` on a signal. At the same moment, capture the other side: `ss -tanp` for socket states, `ps -eLf` for surviving children, and on Postgres `select * from pg_stat_activity` including `state` and `wait_event` plus `pg_locks` for anything waiting. That single artifact discriminates nearly everything above. A thread parked in pool checkout with N idle-in-transaction connections is the pool theory confirmed. A thread in a socket read with an ESTABLISHED connection to a service that never answered is the missing-timeout theory. Two backends waiting on each other's locks is worker contention. A parent in `waitpid` with a live child is the pipe deadlock. No test in flight and a lone non-daemon thread is a shutdown hang.

Two experiments make the diagnosis faster. Set an explicit, short checkout timeout on the pool and short connect/read timeouts on every client used in integration tests: this doesn't fix anything, but it converts a hang into a loud, stack-bearing failure in seconds, which is strictly better than a 60-minute timeout with no information. And run the suite with parallelism forced to one, in a loop, several dozen times; if the hang vanishes there and survives at your normal worker count, it's cross-worker contention rather than a per-test leak. To get samples at a useful rate, run the suite forty times in a matrix of parallel CI jobs rather than waiting for it to happen organically, and constrain the container to one CPU (`docker run --cpus=1`) if you want a shot at reproducing it locally, since core count is usually the largest difference between the two environments.
