Start with what the symptom pattern already rules out. A hang that lands on a different test each run is evidence against any single test containing a deadlock, and evidence for a hazard spread across the whole run: either something accumulating until it crosses a threshold at whatever test happens to be executing when it does, or an ambient race that any test can lose. That it never reproduces locally narrows things further, because it means the trigger is environmental rather than logical. The candidates there are few and concrete: fewer usable CPUs, a memory ceiling, a container network instead of loopback, a database shared between parallel workers, a non-TTY reporter, or simply a different command than the one you run by hand.

Connection pool exhaustion is in the accumulating family, which is why the suggestion isn't silly. If a handful of tests leak a connection or leave a transaction open, the run dies at whichever test asks for the connection past the ceiling, and which test that is depends on ordering and timing. The hypothesis makes a prediction you can falsify in a minute, though. Nearly every pool has an acquisition timeout, and if yours is set to anything finite, exhaustion surfaces as a thrown `TimeoutException` or `Connection pool timeout` with a stack trace, not as an indefinite hang. So the pool story survives only if that timeout is disabled or set to something enormous, and it should also leave a signature on the server: a full `pg_stat_activity` with most sessions sitting in `idle in transaction`.

The other families look quite different once you know to look. CI runners typically expose far fewer cores than your laptop, often one or two after cgroup quotas, and code that blocks inside a bounded executor can deadlock at low parallelism while running fine at eight cores: a blocking call scheduled onto libuv's four-thread pool, or a `join()` on the same ForkJoinPool that's meant to run the joined task. Separately, any socket read without a timeout hangs forever if the peer vanishes, and peers vanish in CI in ways they don't locally, where a dead process sends an instant RST over loopback. A sidecar container that gets OOM-killed produces exactly this shape, as does a Docker network dropping a conntrack entry on an idle connection. Then there is the boring one that catches people repeatedly: a spawned subprocess writes to a pipe nobody drains, fills the 64KB buffer, blocks in `write()`, and the parent waits forever for an exit that can't come, with the amount written varying by test and by log verbosity. Finally, if CI runs the integration suite with parallel workers and your local runs are serial, you have contention that doesn't exist locally at all, whether that's row locks on shared fixture data, advisory locks, or port collisions.

The way to tell these apart is to stop inferring from the outside and capture state from the hung process. Configure the job so that instead of being killed silently at the CI timeout, a watchdog fires a few minutes earlier and collects three artifacts. First, thread or async stacks from every process involved: `SIGQUIT` for a JVM or Go, `py-spy dump --pid` for Python, `node --report-on-signal` plus `SIGUSR2` for Node. Second, the server side of every dependency, meaning `pg_stat_activity` with `wait_event_type`, `wait_event` and `state`, plus `pg_locks` joined to find the blocking PID. Third, `ss -tanp` on each container, along with `docker ps -a` exit codes and `dmesg | grep -i oom`.

Those three read differently for each hypothesis, which is what makes them worth the setup cost. Pool exhaustion shows threads parked on the pool's latch and a server full of idle-in-transaction sessions. A lock wait shows a client blocked in a query with the server reporting `wait_event_type = Lock` and a blocker you can name. A dead peer shows an ESTABLISHED socket with a non-empty send queue and no corresponding session on the server, or a dependency container with exit code 137. Executor starvation shows every worker thread parked and no outbound sockets at all. The pipe deadlock shows a child blocked in `write` to fd 1 and a parent in `waitpid`.

Alongside that, convert hangs into errors wherever you can, since an error names its own location. Set a pool acquisition timeout, a socket read timeout, `lock_timeout` and `statement_timeout` on the database session, and a per-test timeout in the framework set below the job timeout so the runner reports the test name and dumps state itself. To attack reproduction, run the suite in a loop under `docker run --cpus=1 --memory=2g` with the same worker count CI uses; if it reproduces under constrained CPU it's the starvation or race family, and if it needs the container network it's the I/O family. Running the integration suite serially for a few dozen runs is the cleanest single discriminator you have: if serial never hangs, the cause lives in the interaction between workers rather than inside any test.
