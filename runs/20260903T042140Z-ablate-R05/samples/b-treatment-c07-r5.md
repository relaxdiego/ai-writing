Caching is a reasonable instinct, but the specific design you've described will produce wrong answers rather than fast ones, and the failure mode is a security one. If your row-level authorization lives in the WHERE clause and the user ID arrives as a bound parameter, then every user issuing the same logical query produces the identical SQL string. Keyed by that string, the first user's rows become every subsequent user's rows. If instead you interpolate the user ID into the SQL text, the key becomes unique per user and the hit rate collapses toward zero, so the cache buys you nothing while still costing memory. There isn't a middle setting on that dial: either the key ignores the identity that the authorization depends on, or it includes it and stops being shared.

The eight workers compound this. A module-level dictionary is per-process, so you get eight independent caches with eight independent notions of the truth, each seeing roughly an eighth of your traffic. A write that lands on worker three cannot invalidate the stale entry sitting in worker six, and at 400 writes a minute you're mutating the underlying data constantly. Whatever hit rate you do achieve is mostly serving data that another worker has already changed. The dictionary also has no eviction, no TTL and no size bound, so it grows until the process is killed, which under a load balancer means intermittent restarts that people will spend a while misdiagnosing.

Before adding any cache, I'd want to know which queries are actually slow. Turn on `pg_stat_statements` (or the slow query log on MySQL) and look at total time rather than per-call time, because the usual culprit in a web application is a cheap query executed four hundred times per request from a loop over an ORM relationship. That pattern looks like a caching problem and is really an eager-loading or missing-index problem, and fixing it at the source gives you a speedup with no correctness risk at all.

If measurement does point at genuine caching wins, there are two shapes worth considering. The safe and surprisingly effective one is request-scoped memoization: a dictionary created at the start of each request and thrown away at the end, keyed by query plus parameters. It cannot leak across users because it never outlives a single user's request, it needs no invalidation because nothing in it can go stale within a few hundred milliseconds, and it kills the repeated-identical-query pattern outright. The heavier one is a shared cache in Redis or memcached, which solves the eight-process problem, but only if you key on semantic identity rather than SQL text, something like `user:{id}:dashboard:v2`, and write explicit invalidation into every code path that mutates the relevant rows. Short TTLs of thirty to sixty seconds act as a backstop for the invalidations you'll inevitably miss.

The best candidates for that shared cache are the queries with no user-specific predicate at all: reference tables, feature flags, catalogue data, anything where the authorization question doesn't arise. Those you can cache aggressively and hold for a long time.
