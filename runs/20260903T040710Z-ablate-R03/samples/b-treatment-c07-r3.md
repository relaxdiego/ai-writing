The mechanism you're describing would leak data between users, and that risk comes directly from the two constraints you mentioned in the same breath. If authorization lives in the WHERE clause and the query is parameterised, then the SQL string is byte-identical for every user who hits that code path; only the bound parameters differ. Keying on the SQL text alone means user A's rows get served to user B on the next request. If instead you interpolate the parameters into the string so the keys differ, the security problem goes away but so does the benefit: each user now has a private key space, hit rates collapse to roughly the rate at which a single user repeats their own query, and you have paid for a cache that mostly misses. There is no version of "key by the SQL string" that is both safe and fast here, because the thing that makes it fast is exactly the thing that makes it unsafe.

The eight workers compound this. A process-global dictionary is eight separate caches with no shared view, so a write that invalidates an entry in worker 3 leaves the other seven serving stale rows until something evicts them, which in your sketch is never. At roughly 6.7 writes per second you are not dealing with an occasional staleness window; a substantial fraction of the cached working set is wrong at any given moment, and the wrongness is invisible because it depends on which worker the load balancer happened to pick. Users will see a value change, refresh, and watch it change back. An unbounded dictionary is also a memory leak with extra steps: every distinct query string is retained for the life of the process, so you will meet the OOM killer eventually, and the resulting restart will look unrelated to the cache.

Before adding any cache, I'd want to know which queries are actually costing you. Turn on slow query logging or point an APM at the request path and get a ranked list by total time, meaning calls multiplied by duration rather than duration alone. In most applications shaped like yours the top of that list is a missing index or an N+1 pattern where an inner query runs once per row of an outer result. Both are cheaper to fix than to cache, and fixing them makes the system faster for writes and cold reads too, which caching does not.

Where caching does turn out to be warranted, two forms are worth having. A request-scoped cache, cleared at the end of each request, safely collapses the case where the same query runs several times while serving one page. It needs no invalidation, cannot go stale within its lifetime, and cannot cross a user boundary, so it captures a real win at almost no risk. Beyond that, put shared entries in Redis or memcached so all eight workers see one copy, and build the keys explicitly from the logical entity and the identity that authorises access, something like `user:{id}:dashboard:v3`, rather than from SQL text. Give every key a TTL short enough that a missed invalidation self-heals in seconds, and delete keys explicitly on the write paths that affect them. That is more work than a dictionary, but the work is the part that makes it correct.
