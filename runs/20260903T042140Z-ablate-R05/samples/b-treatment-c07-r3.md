The instinct is right that repeated queries are worth avoiding, but keying on the SQL string specifically is the one variant that will bite you, and it will bite in the form of a data leak rather than a performance regression. Your authorization lives in the WHERE clause, which means that if you use bound parameters (and you should), the SQL text for "fetch this user's invoices" is byte-identical for every user on the system. The user ID is in the parameter list, not the string. So the first user to run that query populates the entry, and every other user who runs it gets that first user's rows back, with the database never consulted and the authorization check never reached. If instead you interpolate literals into the SQL, the keys become distinct and the leak goes away, but now you have unbounded key cardinality and, more importantly, you've written the string-concatenation pattern that SQL injection lives in. Neither branch is somewhere you want to be.

The eight workers undercut the performance case even setting correctness aside. A module-level dictionary is per-process, so you get eight independent caches that each see roughly an eighth of the traffic, and a load balancer that doesn't pin users to workers will scatter a single user's requests across all of them. Your hit rate is a fraction of what a back-of-envelope estimate suggests. Worse, when a write happens and you try to invalidate, you can only clear the dictionary in the process that handled the write; the other seven keep serving the old rows with no way to be told. At 400 writes a minute you're mutating state around seven times a second, so those seven stale caches are wrong more or less continuously, and the bugs it produces are the intermittent kind that depend on which worker answered.

What I'd suggest instead starts before any caching. Turn on slow query logging or pull the timings from your APM for a representative hour and look at what actually dominates. In most applications that feel slow the cause is a handful of missing indexes plus N+1 query patterns from an ORM, and both are cheap to fix and carry no correctness risk. Caching layered over an unindexed query just hides a problem that will resurface the moment the cache misses.

If profiling does point at genuinely hot reads, there are two safe layers. Within a single request, a dictionary that lives for the duration of that request and dies with it is genuinely useful, since it collapses the repeated identical lookups an ORM makes while rendering a page, and it can't go stale or cross a user boundary because it never outlives either. Across requests, use a shared store such as Redis or Memcached so all eight workers see the same entries and one invalidation reaches everybody. Key it on the entity you're caching and the identity you're caching it for, something like `invoices:user:1234:page:1`, never on SQL text, so authorization scope is structurally part of the key. Give entries a short TTL as a backstop and delete them explicitly on the writes that touch them.
