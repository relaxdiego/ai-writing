Two details in what you've described carry most of the diagnostic weight: the hang site moves, and it never reproduces locally. A moving site is the reason to be sceptical of the plain version of the pool theory. If each test leaked one connection, the pool would drain after a fixed number of tests and you would stall at roughly the same index every time, drifting only with test ordering. Uniformly scattered hang sites look more like something that fires with a small per-test probability. That does not clear the pool entirely, because there are two variants that would look random: connections leaked only on an error or timeout path that itself fires occasionally, and nested acquisition, where a test holding a connection for an outer transaction calls code that acquires a second one, so the deadlock depends on how many workers happen to be inside that pattern at once. The suggestion isn't wrong so much as underdetermined by the evidence you have.

The CI-only part narrows things differently. A CI runner typically has fewer cores than your laptop, runs the suite with a different worker count, shuffles order with a fresh seed, talks to services over a container network that has real connect latency and occasional resets, and starts those services concurrently with the tests rather than hours earlier. Any wait that assumes an event arrives promptly, or that a notify happens after the corresponding wait begins, loses far more often on two starved cores than on eight idle ones.

The candidates worth holding in mind, beyond the pool, are these. An unbounded wait on something that occasionally never arrives: a webhook, a queue message, a container health check, a socket read with no deadline, where a single dropped event parks that test forever and the hang lands wherever the drop happened. Lock contention between parallel workers on shared state, such as the same fixture rows, an advisory lock, or a port; note that a true cycle would be killed by the database's deadlock detector, so a survivng hang usually means a waiter queued behind a session sitting idle in transaction, which is a leak of a different kind. Pipe buffer deadlock, where a subprocess or container writes logs the parent never drains, fills the 64KB pipe, blocks, and the parent waits on exit; that one is random because log volume varies with retries and verbosity. And a harness-level hang, where a worker died and the coordinator waits on it, or teardown blocks, in which case the last-reported test name is a red herring rather than the culprit.

You will not distinguish these by reasoning, and you should stop trying to. Get a stack dump at hang time. Add a watchdog inside the job with a timeout comfortably below the CI job timeout, so it fires and captures artifacts before the runner kills everything. On the JVM, SIGQUIT to stdout; in Go, SIGQUIT gives you every goroutine; in Python, `faulthandler.dump_traceback_later` or an external `py-spy dump` against the pid; in Node, `--report-on-signal` plus SIGUSR2. One such dump separates almost every hypothesis above: a thread parked in `pool.acquire` settles the pool question outright, a block in `read` on a pipe fd is the log deadlock, a socket `recv` with no deadline is the missing-event case, a futex wait with another thread holding the lock is contention, and all workers parked with nothing in flight points at the harness.

Alongside that, three cheap instruments. Log pool gauges (in use, idle, waiters) every few seconds during the run, since a leak shows as a monotone climb and a race does not. Set an acquire timeout, which converts exhaustion from a hang into an exception with a stack trace attached to the test that caused it. And snapshot the database at hang time, `pg_stat_activity` and `pg_locks` if it's Postgres, with `log_lock_waits` on; a session idle in transaction holding a lock is unmistakable.

Then a few experiments that split the space. Rerun CI with a single worker: if the hang vanishes, it's cross-test interference, and if it survives, it's a self-contained wait inside one test. Reproduce the resource profile locally under `docker run --cpus=1` with the suite in a loop overnight, which often finds races that a fast machine never loses. Record the ordering seed on every run and, when a hang occurs, look at the tests that preceded it rather than the one it stopped on, because in the interference case the hanging test is the victim and the culprit ran earlier.

One caution on confirming whatever fix you land on. At a one-in-twenty base rate, twenty green runs are unremarkable; you need roughly sixty consecutive passes before you can say at 95% confidence that the rate actually dropped. Cheaper than that is making the failure mode itself impossible to miss: put a bound on every wait in the integration path, so the next occurrence arrives as a timeout with a stack rather than a job that sits there for an hour.
