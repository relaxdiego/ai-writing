Before the performance question, there's a correctness one that decides whether this design is usable at all. If your queries use bound parameters, which they should, then the SQL string is identical for every user and the user's identity lives in the parameters, not the text. Keying the cache on the SQL string alone means the first user to run "SELECT ... WHERE owner_id = $1" populates an entry that every subsequent user reads, and your row-level authorization is bypassed by the cache sitting in front of it. If instead you interpolate the user id into the SQL text, each user gets distinct keys and the leak goes away, but the cache then fragments per user and the hit rate collapses on exactly the personalized queries you were hoping to speed up. Any workable version of this has to key on the identity and the bound parameters explicitly, not on the query text.

The eight workers break the other half of the idea. A module-level dictionary is per-process, so you get eight independent caches, eight copies of the memory, and a hit rate reduced by the load balancer spreading a user's requests across processes that each have to warm up separately. Worse, a write handled by worker 3 has no way to invalidate the entries worker 6 is still serving. At roughly seven writes a second with no invalidation path, stale reads are not an edge case but the normal condition, and the staleness has no bound: an entry written once is served forever, since nothing evicts it and nothing expires it. That last part is also a slow memory leak, because a dictionary keyed by query text with no eviction policy grows with the cardinality of your parameters until the worker is killed.

What I'd actually do starts with measurement rather than caching, because the shape of the fix depends on where the time goes. Turn on your slow query log or pg_stat_statements and look at total time per query, not per-call time; the usual finding is one missing index or an N+1 loop issuing hundreds of identical queries per request, and both of those are fixable with no staleness risk whatsoever.

For the N+1 case specifically, the safe version of your idea is a request-scoped cache: a dictionary created at the start of a request and discarded at the end, keyed on the query plus its parameters. A single request has a single authenticated identity, so cross-user leakage is impossible; nothing survives long enough to go stale; and the eight-process problem disappears because nothing is shared. This captures most of the duplicate-query win.

If you need caching across requests, it has to live in something all eight workers can see, so Redis or memcached rather than a process dictionary. Cache at the level of entities rather than SQL strings, storing "user 123's profile" or "org 45's dashboard totals" under keys you construct deliberately, because then a write to that user or org tells you exactly which keys to delete. Put a short TTL on everything as a backstop for invalidations you miss, and reserve the long TTLs for data that is genuinely shared and read-mostly: reference tables, configuration, feature flags, expensive aggregates that nobody minds being a minute old. Whether a user seeing their own write reflected 30 seconds late is acceptable is a product decision I can't make for you, and it determines the TTL on anything user-facing.
