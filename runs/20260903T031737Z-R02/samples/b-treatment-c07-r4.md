Caching is very likely the right direction, but keying on the SQL string is the one detail that turns a performance win into a data leak, and your authorization model is exactly the case where it goes wrong.

If your queries use bound parameters — `WHERE user_id = ? AND ...` — then the SQL string is identical for every user on the system. The first request populates the cache with one user's rows, and every subsequent request for that query shape gets served those rows regardless of who is asking, so the row-level authorization you've carefully put in the WHERE clauses stops being enforced at all on cache hits. If instead your queries interpolate values directly into the string, the keys are distinct per user and the leak disappears, but so does most of the benefit: each user gets their own cache entries, hit rates collapse toward zero for anything user-scoped, and the dictionary grows without bound in every process. Whichever way the parameters are handled, the SQL text alone is not enough to identify a result set — you need the full parameter tuple and the authenticated principal in the key, and once you're writing that key you've admitted the cache is really keyed on *data*, not on *query text*.

The eight workers compound the problem in a way a single-process test will never reveal. Each process holds its own dictionary, so you get eight independently drifting copies of your data with no way to invalidate them together. A user submits a write, gets routed to worker 3 on the next request and sees their change, then gets routed to worker 6 and sees the old value again — read-your-own-writes breaks intermittently and non-reproducibly, which is among the most expensive classes of bug to chase down. At roughly 400 writes per minute you're mutating state about seven times a second, so entries go stale continuously rather than occasionally, and a global dict has no mechanism for mapping "this INSERT touched the orders table" back to "these 340 cached SELECT strings are now wrong." Add that nothing evicts, and each worker's memory climbs until the box starts swapping or the OOM killer picks one off.

There's a version of your idea that is safe and that I'd suggest doing today: **request-scoped memoization**. Keep a dictionary keyed on the query plus its parameters, but let it live only for the duration of a single request and throw it away at the end. Nothing crosses a user boundary, nothing outlives a write by more than a few hundred milliseconds, and it eliminates the duplicate-identical-query pattern that ORMs generate prolifically. In applications with N+1 problems this alone often recovers a large fraction of the latency, and it carries essentially no correctness risk.

Beyond that, I'd want to know what's actually slow before building shared infrastructure. Turn on the slow query log and pull `EXPLAIN` for the worst offenders — a surprising share of "we need caching" turns out to be two or three missing indexes or a query that got a sequential scan after the table grew. Check whether you're opening connections per request rather than pooling them, and look for the N+1 loops directly. Caching a query that takes 400ms because it lacks an index means paying invalidation complexity forever to work around a fix that takes ten minutes.

Where measurement says caching genuinely helps, put it in a shared store — Redis or Memcached — so all eight workers see one copy and one invalidation. Cache at the entity level rather than the query level where you can: `user:1234:profile` can be deleted precisely when user 1234 is written, whereas an opaque SQL-string key gives you no way to know what a write affected. Include the principal in the key for anything authorization-scoped, set a TTL short enough that a missed invalidation self-heals within your tolerance, and pick that tolerance per query type — a dashboard aggregate can be thirty seconds stale, an account balance cannot be stale at all.
