The most informative thing you've said is that the hang moves. A test that hangs at a fixed point is a bug in that test; a hang that lands somewhere different each run is almost never about the test it lands on, because that test is merely the one unlucky enough to be holding the bag when a shared resource ran out or a race resolved badly. So the search space isn't your integration tests, it's whatever they share: a connection pool, a lock, an event loop, a socket to a container, the runner's CPU and memory, the stdout pipe. That reframing matters because it tells you not to waste time bisecting tests, which is the instinct most people follow first and which yields nothing here.

It also cuts against the pool-exhaustion theory in its simple form, though not fatally. A pure connection leak is a counter: some test fails to release on an error path, and the run dies when the (N+1)th checkout blocks. With a fixed test order and a fixed pool size, that would hang at roughly the same place every time. So if your ordering is deterministic and single-threaded, a leak alone doesn't explain the wandering. If your runner randomises order per run or shards across parallel workers, it explains it perfectly, and the theory is back in play. Check which of those you're in before arguing about it any further, and make sure the ordering seed is printed into the CI log so a hung run can be replayed.

What pool exhaustion really is, though, is one member of a family: every hang is a missing deadline. Something waited on something else with no upper bound on the wait. The interesting question is which wait, and the candidates each have a distinct fingerprint. A blocking checkout from an exhausted pool is one. A socket read with no timeout is another, and it is far more likely in CI than locally, because locally your services are on loopback and refuse connections instantly, while in CI they're containers behind a bridge network that can vanish without sending a FIN, leaving your client blocked in `recv` until TCP keepalive fires two hours later, if keepalive is even enabled. A lock wait is a third: Postgres, notably, defaults both `lock_timeout` and `statement_timeout` to zero, so two parallel workers touching the same rows will wait on each other indefinitely unless the wait forms a true cycle that the deadlock detector can see. A fourth, and the one people forget, is the stdout pipe. Locally you run against a TTY and output streams away; in CI the runner reads from a pipe with a 64 KB buffer, and if anything stops draining it, whichever process is writing blocks forever in `write`. That one produces exactly your symptom: never locally, different place each time, roughly proportional to how chatty the run is. Beyond these there is plain starvation, where an oversubscribed two-core runner turns a slow test into a timeout, and the OOM killer, which can remove a database or a worker mid-transaction and leave its client waiting on a connection that will never answer.

You will not distinguish these by reasoning, and you shouldn't try. Make the hang report itself. Add a watchdog to the CI job that, after the point where a healthy run has certainly finished, dumps every thread's stack in every relevant process rather than just killing the job: `jstack` or `SIGQUIT` on the JVM, `SIGQUIT` for a Go binary's full goroutine dump, `py-spy dump --pid` from outside or `faulthandler.dump_traceback_later` from inside for Python, `--report-on-signal` for Node. Alongside the stacks, capture the state the stacks can't see: `pg_stat_activity` with `wait_event_type` and `wait_event`, plus `pg_locks`, from the database server; `ss -tanp` for socket states and queue depths; the process tree; open file descriptor counts; `dmesg` for OOM kills; cgroup peak memory. That single change converts a one-in-twenty mystery into one solid data point per occurrence, and you probably need only one.

The stacks will name the culprit directly. Threads parked inside your pool's `acquire` frame, with the pool reporting active equal to max and the database reporting almost no sessions, is exhaustion, and you can confirm the leak by logging active-connection count after each test and looking for a staircase. Threads sitting in `recv` on a socket that `ss` shows connected to a peer that no longer exists is the vanished-container case. Two threads each waiting on a lock the other holds is a deadlock, and the JVM will even label it as one. A process blocked writing to fd 1 is the pipe.

Before any of that, there's a one-line experiment worth running immediately, because it settles the pool question in a single run: set an acquisition timeout on the pool, five seconds or so. If exhaustion is the mechanism, the next hang stops being a hang and becomes a loud, fast failure with a stack trace pointing at the test that was starved, and the test that leaked is usually a short distance behind it in the log. If the run still hangs silently, the pool is exonerated. Generalise the same move to everything else: connect and read timeouts on every HTTP and database client, `statement_timeout` and `lock_timeout` on Postgres, a per-test timeout in the runner, a deadline on every `wait` for a subprocess or a container healthcheck. None of this fixes the underlying bug, but it turns an unlabelled hang into a labelled error, which is the whole difficulty here.

For reproduction, bisect on the axes where CI differs from your laptop rather than on the test list: core count, parallelism, memory limit, TTY versus pipe, containers versus loopback, cold versus warm caches, service startup timing. Constrain a local container to the runner's actual CPU and memory limits, pipe the output rather than attaching a terminal, and loop the suite twenty or thirty times. Pinning to a single core with `taskset` compresses timing races and often takes a one-in-twenty failure into the single digits. And while that runs, go back over the last fifty CI runs and look for correlation: a particular runner, a particular shard, a time of day, a change that landed just before the failures started. When you find the hung test in a log, read the test immediately before it rather than the one that hung, because with poisoned shared state the predecessor is usually the guilty party.
