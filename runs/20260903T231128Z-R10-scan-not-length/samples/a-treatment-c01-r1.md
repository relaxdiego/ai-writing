`booking_day` was formatting the UTC datetime straight out of the database, so any booking whose local day differs from the UTC day rendered the wrong date. The failing test caught the clearest case: an evening booking in Sydney showed as 2026-03-11 when the venue's calendar says 2026-03-12. I gave the function a `tz` parameter and converted before formatting, which brings it in line with `email.py:47` and `report.py:19`, both of which already did `astimezone(venue.tz)` before rendering a day. `confirmation_text` was the only caller in `src/`, and it now passes `booking.venue.tz`; a grep for `booking_day` across the tree turns up nothing else, so the signature change is contained.

`tests/test_confirm.py` passes all twelve. I did not run the rest of the suite, so the other two call sites are unverified by me beyond reading them. One loose end I left alone: the comment above `booking_day` still says "`when` arrives from the database in UTC", which remains true of the argument but now reads as if it were the reason not to convert.
