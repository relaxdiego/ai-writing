Before choosing between explanations, arrange to capture a stack dump from the hung process. That one artifact separates nearly all of these hypotheses, and without it you're comparing priors.

The reason it's decisive is that each candidate has a distinct signature in the stacks. Pool exhaustion shows every worker parked in the pool's checkout frame and nothing in a query. A database deadlock shows threads inside a query, waiting on a lock. A lost wakeup shows one thread in a condition wait with no live thread that could ever signal it. A pipe deadlock shows the parent in `wait` and the child in `write`. The trouble is that the CI job's own timeout is usually a hard kill, which destroys exactly this evidence, so you need a watchdog that fires below it: `faulthandler.dump_traceback_later(600, exit=True)` in `conftest.py` for Python, `pytest-timeout` with `--timeout-method=thread`, `jstack`/`jcmd Thread.print` or SIGQUIT on the JVM, SIGQUIT with `GOTRACEBACK=all` for Go. Wrap the test step so that on timeout it also runs `ss -tanp` and dumps the database's lock view before anything gets killed.

On the pool theory: it's plausible, but the frequency argues against the simple version of it. A plain leak, where a connection is acquired and never returned, is monotonic. It would hang almost every run, at roughly the same depth into the suite, drifting only as test order changes. One run in twenty means either the leak is conditional (it only happens on an error path or when some race loses), or the pool is shared with other concurrent CI jobs, or exhaustion isn't the mechanism. You can falsify it cheaply by logging the checked-out count per test from the pool's own events, and by setting an acquire timeout. With a timeout configured, exhaustion stops being a hang and becomes a loud error that names the pool.

Here are the other candidates that fit "different test every time, never locally," each with the evidence that would confirm it:

- **Executor self-deadlock.** A thread pool sized from `os.cpu_count()` or `availableProcessors()`, which inside a container often reports either the host's core count or a cgroup-limited 2. A task that submits to the same pool and then waits on the result blocks permanently once the pool is small enough. Your laptop has ten cores and the runner has two. Test it by running locally under `taskset -c 0,1` or a CPU-limited container.
- **Lost wakeup.** A wait on a condition variable, future, or queue with no timeout, where the notification can arrive before the wait begins. A slower and differently scheduled machine shifts the interleaving enough to lose the race occasionally.
- **Lock-order inversion in the test database.** Parallel workers sharing a schema, truncating and seeding in different orders. Postgres would normally break a two-transaction deadlock on its own, so a hang here usually implicates an advisory lock, a lock held outside a transaction, or a client-side block that keeps `deadlock_timeout` from ever being reached. Snapshot `pg_locks` and `pg_stat_activity` with `wait_event` during the hang.
- **Unbounded network wait.** A service container that occasionally starts slowly, or a DNS lookup that misses, combined with a client that has no connect or read timeout. Sockets stuck in `SYN_SENT`, or an established connection with a non-empty send queue, confirm it.
- **Subprocess pipe deadlock.** The parent waits for the child to exit while the child blocks writing into a full 64 KB pipe buffer. This never reproduces locally because stdout is a TTY that gets drained, or because local output is smaller.
- **Fork while a lock is held.** Forking (via `multiprocessing`, or a test that spawns workers) while another thread holds the logging or allocator lock leaves the child deadlocked on its first use. The child's stack is typically one frame deep inside `acquire`.

The "always a different test" detail deserves less weight than it seems to carry. If your suite randomizes order, the identity of the hanging test is partly noise, and the real culprit may be a specific pair of tests that only sometimes land adjacent. Log the seed on every run, then replay a failing seed with the same worker count. A seed that reproduces at much higher than 5% points at a test-pair interaction rather than a global resource; a seed that reproduces at exactly the base rate points away from ordering entirely.

Since the whole thing turns on CI differing from your machine, it's worth writing down the differences explicitly and adopting them locally one at a time: core count and worker count, real service containers versus in-process fakes, stdout as a pipe rather than a terminal, cold caches, slower disk, and whether the database or broker is shared across concurrent runs. That last one is checkable from CI history alone. If hangs correlate with other jobs running at the same time, you have a shared-environment collision, and no amount of reading your own test code will find it.

Whatever the cause turns out to be, the structural fix is the same: put a timeout on every blocking boundary you own, including pool acquisition, socket connect and read, lock acquisition, and subprocess wait. A suite with timeouts everywhere doesn't hang. It fails, quickly, with a stack trace naming the resource that didn't arrive.
