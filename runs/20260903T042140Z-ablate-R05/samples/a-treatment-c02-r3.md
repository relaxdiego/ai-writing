The detail worth building on is that it lands on a different test each time. A test that hangs at itself is a test with a bug; a hang that wanders is nearly always something shared, so whichever test happens to be running when the shared thing goes bad is the one that gets blamed. Pool exhaustion fits that shape, which is presumably why it was suggested, but so do about four other families, and they're distinguishable if you set things up to capture evidence rather than argue from plausibility.

The first family is accumulation across the run. Something leaks a little per test until a threshold is crossed, and the crossing point drifts because tests vary in how much they leak and in what order the runner interleaves them. Connections are one candidate; file descriptors, unreaped threads, ephemeral ports stuck in TIME_WAIT, and transactions left open holding row locks are all equally good ones, and the last of these often looks exactly like pool exhaustion from the client side. The signature of this whole family is that the hang correlates with position in the run rather than with test identity: if you shuffle the order with different seeds and the hang keeps landing around the same ordinal, you're accumulating something.

The second family is the shape of the CI machine. Runners typically have two or four cores where your laptop has ten or more, and any pool sized from the CPU count shrinks accordingly. A test that occupies a worker while awaiting a task queued behind it on the same executor deadlocks reliably at two cores and never at ten. Latency differences do similar damage to condition-variable and callback code: a response that arrives locally after you've started waiting arrives on CI before, and the wakeup is lost. These reproduce locally the moment you stop running under laptop conditions, which is the single highest-value experiment here.

The third family is peculiar to running without a terminal, and it gets overlooked because nobody thinks of it as a concurrency bug at all. A subprocess whose output nobody drains blocks once it fills the pipe buffer, at about 64 KB, and sits there forever; the amount a test logs varies, so which test trips it varies. Similarly, anything that reads stdin under CI, whether a credential prompt, a confirmation, or a stray debugger, blocks on a descriptor that will never produce a byte or an EOF.

The fourth family isn't really a hang: it's a missing timeout turning an ordinary failure into an infinite wait. If your HTTP and database clients have no socket timeout, then a dependency container that OOMs, restarts, or loses a DNS lookup produces a thread parked in read forever. Worth checking alongside this is contention between concurrent CI jobs, since one shared database, schema, or advisory lock across two overlapping runs produces exactly the sort of one-in-twenty rate you're describing, and locally you never have a second run competing with you.

To tell these apart, make the hang produce a stack trace instead of a timeout message. Wrap the test step so that at, say, 80% of the job's time limit a watchdog dumps every thread's stack and then kills the process: SIGQUIT for a JVM, `faulthandler.dump_traceback_later` or `py-spy dump` for Python, SIGQUIT for Go's goroutine dump, `SIGUSR1` plus the inspector for Node. In the same hook, capture `ss -tanp`, the open file descriptors of the test process, `pg_stat_activity` or its equivalent from the database, the dependency containers' logs, and `/proc/pressure/*`. Add per-test timeouts and a timestamped line at each test's start and end so you know precisely which test was in flight. One capture settles the question that no amount of discussion will.

Reading the capture is then mostly mechanical. Many threads parked in `getConnection` or `acquire` with the pool reporting all connections in use, held by call sites belonging to already-finished tests, is genuine pool exhaustion. A single thread in a socket read with no matching connection in `ss` output is the missing-timeout case, and the container logs at that timestamp will tell you what died. Every worker waiting on a future whose task is still sitting in the same executor's queue is starvation from core count. A child process blocked in `write` on fd 1 is the pipe case, and anything sitting in `read` on fd 0 is the stdin case. Nothing blocked at all, with the process burning CPU, points instead at a retry loop or a livelock.

Alongside that, work on making it happen more often, because a one-in-twenty rate is unusable for iteration. Run the suite locally under CI conditions: `--cpus=2 --memory=2g` under Docker, output redirected to a file rather than a terminal, no tty, and the same container images the pipeline uses, then loop it thirty times overnight. Sweep the order seed while you're at it. Meanwhile the pool hypothesis is cheap to falsify directly, so it's worth doing even though I'd rank it below the core-count and missing-timeout explanations: emit the pool's active and idle gauges after every test. If active never climbs toward the maximum across the run, the theory is dead and you've spent twenty minutes; if it ratchets upward and never comes back down, you've found your leak and the stack dump will tell you which test opened it.
