Import no longer stops at a blank row, and one bad cell no longer kills the run

Support has had three reports this month of a contact import that reported success but created fewer contacts than the file contained. The cause was `read_rows`, which treated an empty first cell as end-of-sheet and broke out of the loop. Customers whose spreadsheets had a blank separator row partway down lost every contact below it, with nothing on the results page to say so. Separately, a single unparseable date raised out of `import_file` and reached the customer as a stack trace, abandoning the rows that had already been read.

Three changes follow from that. `read_rows` now skips a row only when every cell is blank after stripping, and continues rather than stopping, so a row with an empty first column but data elsewhere is imported instead of truncating the run. `import_file` catches `ValueError` from `parse` per row, records the sheet line number and message, and carries on; it returns an `ImportResult` carrying the created count and the list of errors instead of a bare integer. The upload view passes both to the template, so the results page lists which rows were skipped and why.

Two consequences worth a reviewer's attention. `read_rows` now yields `(line_no, row)` rather than `row`, which breaks any other caller; `import_file` is the only one in this tree, but a grep outside `src/importer` is worth doing before merge. And a partial import now commits: rows that parsed are created even when later rows fail, where previously the exception aborted the request. That is the behaviour support wants, since re-uploading a 2,000-row sheet to fix one date is the complaint underneath the tickets, but it does mean a customer who fixes the bad rows and re-uploads the whole file will duplicate the successful ones. There is no dedupe on `Contact` today, so this is a real gap rather than a hypothetical one, and it should be a follow-up rather than something bolted onto this change.

Tests cover both reported failures: a fixture with a blank row in the middle yields all 40 rows, and a fixture with one unreadable date produces 39 contacts plus a single error naming line 13 and the offending value.
