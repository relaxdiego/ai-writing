Before the performance question, there's a correctness one: keying by SQL string breaks your authorization model. If permissions are enforced through a bound parameter in the WHERE clause, the SQL text is byte-identical for every user who runs that query. `SELECT ... FROM documents WHERE owner_id = $1` is the same key whether the parameter is 17 or 4203, so the first user to run it populates the entry and everyone after them reads that user's rows. The only variant where the key naturally differs per user is one where you interpolate the id into the SQL text, which swaps the leak for an injection surface and gives you one entry per user per query shape with nothing bounding the total. A usable key has to cover the normalised SQL, every bound parameter, and the principal authorization is being evaluated against, which means you are caching per-user result sets and the hit rate is a fraction of what a shared cache suggests.

The eight workers undo most of the rest. In every common runtime a module-level dictionary is global to one process, so you get eight independent caches that each see roughly an eighth of the traffic, and a write handled by worker 3 leaves workers 1, 2 and 4 through 8 serving the pre-write value indefinitely. At 400 writes a minute something changes every 150 milliseconds, so the staleness isn't a rare edge case; it's the steady state, lasting until the process restarts. Nothing evicts either, so the caches grow until the box runs out of memory or the OOM killer picks a worker.

Start by finding out what is actually slow. Turn on `pg_stat_statements` (or your engine's equivalent) and sort by total time rather than mean, because the usual culprit is not one expensive query repeated but hundreds of cheap ones issued in a loop, or a single sequential scan that an index removes entirely. A missing index that takes a query from 400ms to 2ms beats any cache, and it beats it without introducing a second source of truth.

If repeated reads survive that analysis, the cheapest safe version of your idea is a dictionary scoped to a single request rather than to the process. It is created when the request starts, discarded when the response is sent, and it collapses the duplicate lookups that N+1 patterns generate without ever outliving the transaction that filled it. There is no cross-process staleness because nothing crosses a process, and no invalidation logic because entries never survive long enough to go stale.

For hits that need to span requests, use a shared store such as Redis or memcached so the eight workers see one cache, and move the caching a layer above SQL. Cache domain entities by identity, then apply the permission filter in application code on the way out, so the stored value is not user-specific and the authorization decision is never the thing being cached. Pair that with short TTLs sized to the staleness you can actually tolerate, plus explicit invalidation on write: either delete the affected keys, or embed a per-entity version counter in the key so a bump makes every old entry unreachable at once. Track the hit rate from day one, since a cache below roughly 80% on a fast query is adding a network round trip and a consistency hazard in exchange for very little.
