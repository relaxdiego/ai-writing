The plan has three problems that compound each other, and the first one is a security bug rather than a performance issue.

Since your authorization lives in the WHERE clause, the SQL string is not a sufficient cache key. If you use bound parameters, which you should be, then the query text for "fetch my invoices" is byte-identical for every user in the system and only the parameter values differ, so the first user to run it populates an entry that every subsequent user reads. That is a cross-tenant data leak, and it is the kind that passes tests, passes review, and surfaces in production as a customer seeing someone else's records. The obvious patch is to fold the parameters into the key, including the user id, but that changes the economics of the whole idea: the cache now holds one entry per query shape per user, so the cardinality is your query count multiplied by your active user count, the hit rate collapses toward the rate at which a single user repeats a single query, and memory grows without bound because a plain dictionary has no eviction. Whatever hit rate motivated the change in the first place was measured on the leaky version.

The second problem is that a global dictionary in a Python or Node process is per process, and you have eight of them. Nothing coordinates them, so a write served by worker three cannot invalidate the copy worker six is holding. You would get eight independently stale views of the same data, and a user hitting refresh would see values flip back and forth as the load balancer moves them between workers. Sticky sessions do not fix it, because the writes are still landing wherever they land.

The third problem is that 400 writes per minute is roughly seven per second, and without a dependency map from tables to cached keys you cannot know which entries a given write invalidates. The only correct-by-construction options are to flush everything on any write, which at seven writes per second gives cached entries a mean lifetime of about 150 milliseconds and buys you nothing, or to invalidate nothing and serve stale data indefinitely. Query caching is genuinely effective on read-mostly workloads; yours is write-active enough that invalidation, not lookup, is the hard part.

What I would actually do, roughly in order of payoff per unit of risk. Start by measuring: turn on slow query logging or your APM's database view and find out whether the latency is one expensive query, an N+1 loop issuing hundreds of small queries per request, or missing indexes causing sequential scans. In my experience these three account for most "the app feels slow" reports, and all three are fixed at the source rather than papered over. Confirm you have a connection pool sized sensibly for eight workers, since connection setup per request is a common and invisible cost.

If caching is still warranted after that, two safe shapes exist. A per-request memo, a dictionary created at the start of a request and discarded at the end, eliminates redundant identical queries within one request, cannot go stale, cannot leak across users, and needs no coordination. Beyond that, put a shared cache such as Redis in front of specific expensive queries, keyed by the query name plus the complete parameter tuple with the user or tenant id included, with an explicit TTL short enough that staleness is acceptable and explicit deletion of the affected keys on the writes you know touch them. Choosing which queries get this treatment by hand is a feature, because it forces you to reason about invalidation for each one, which is exactly the reasoning a blanket global dictionary skips.
