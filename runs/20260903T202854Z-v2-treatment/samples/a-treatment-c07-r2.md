Don't ship this as described: keyed on search text alone, the cache will serve one user's private page to everyone who searches the same words.

That follows from the three facts you gave about the page. The results include each viewer's own saved items, so the first person to search "wireless keyboard" fills the cache with their saved items and the next hundred searchers see them. The results are permission-filtered, so whoever populates the entry fixes the permission set for the hour, and a viewer with narrower access gets shown items they aren't allowed to see. Prices change through the day, so every hit inside the hour shows a price that may be an hour stale, which matters differently depending on whether anyone can transact from that page.

The fix is to cache at the layer that is genuinely shared rather than the rendered page. For a given query, the expensive work is almost certainly the search itself: matching, ranking, scoring across the corpus. That part does not depend on who is asking. So cache the ordered list of matching public item IDs, keyed on the normalised query text plus anything else that changes ranking, such as sort order, filters, and pagination. Then on every request, take that ID list and do the cheap per-viewer work fresh: drop the IDs this viewer can't see, look up current prices by ID, and merge in this viewer's saved items. Those are primary-key lookups against a small set of IDs rather than a corpus scan, and they will not be what's making the page slow.

This shape also fixes invalidation, which the whole-page cache handles badly. When an item is unpublished or its permissions change, the page cache stays wrong for up to an hour, whereas the ID-list cache is corrected at request time by the filter you're already running. You still want a bounded TTL so that newly created items appear, but a stale entry now costs you a missing new result rather than a disclosure.

One thing worth checking before you build any of it: confirm the search query is actually the cost. If the slowness is an N+1 fetch of item details or price lookups in the render loop, a search cache buys you very little and you'll have spent the week on the wrong layer. Query timings from a slow-request trace will tell you in an afternoon.

If it turns out the personalisation genuinely is the expensive part and you do want to cache rendered output, the key has to include the viewer identity and a version stamp for their permission set, so that a permission change busts the entry rather than waiting out the TTL. Be aware that this collapses the hit rate to "the same person repeated the same search", which is a much smaller win than the one you're expecting.

The ID-list cache is a week's work, including the metrics to confirm it helped.
