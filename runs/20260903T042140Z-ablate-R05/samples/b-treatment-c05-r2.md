I didn't find the cause, but the run history narrows it considerably and points at where to look next.

The short runs are not random. Of the last eight runs, three wrote roughly half the rows (23902, 22104, 23551) and each of those finished in about seven minutes rather than the fifteen the full runs take. So the job isn't dropping rows partway through a normal-length run; it's doing about half the work and exiting cleanly, reporting `ok`. That rules out a write-side failure or a partial transaction, and moves suspicion to the input: `fetch_events` is being handed a window that covers roughly half the events.

The window is computed in `jobs/scheduler.py` as `last_success_at or (now - timedelta(hours=24))`. That is the natural suspect. If `last_success_at` is set to something later than 24 hours before the run — for instance because a previous run recorded a finish time rather than the start of its window, or because a same-day manual or retried run updated it — the next window shrinks and the job legitimately sees fewer events. The `fix: retry transient fetch errors` commit is worth reading in this light, since a retry that succeeds and updates `last_success_at` in the middle of a run would produce exactly this pattern. I looked at the commit titles only and did not read the diff.

What I did not do, and what would settle it: pull `started_at`, `finished_at` and the actual window bounds for the short runs against the runs immediately preceding them, so you can see whether the short windows follow a particular kind of predecessor. If `job_runs` doesn't persist the window bounds, logging `window_start` and `window_end` at the top of `run()` would make the next occurrence self-diagnosing. I'd also check whether the short runs fall on any regular cadence; three in eight days with no obvious weekday pattern in this sample, but thirty rows exist in the table and I only read eight of them.

One caveat on the above. The half-rows-half-time correlation is strong but it rests on eight data points, and I haven't confirmed that `fetch_events` respects the window in the way I'm assuming rather than, say, applying its own cap or pagination limit. If reading the remaining run history doesn't show the window-shrinking pattern, that's the next thing I'd check.
