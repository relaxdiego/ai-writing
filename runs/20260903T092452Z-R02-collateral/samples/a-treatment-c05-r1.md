I did not find the cause. What I have is a narrowing and a specific gap in the evidence that has to be closed before anyone can name a culprit.

The short runs are not random. In the last eight runs, 23, 26 and 29 August all wrote about 22–24k rows and finished in about seven minutes, while the other five wrote about 48k and took about fifteen. Those three dates are exactly three days apart. Eight runs is far too few to call that a real period, and there are 30 runs in `job_runs` to check it against, but it is the first thing I would test, because a three-day rhythm points at something outside this job rather than at a race inside it.

The halving happens before any rows are written, which rules out part of the code. `run()` wraps the whole write loop in a single transaction, so a partial write plus a rollback would surface as a failed run with zero rows, not as an `ok` run with half. The short runs are also proportionally shorter in wall time, which is what you see when less data comes back from `fetch_events`, not what you see when a retry loop is churning. So the loss is upstream of `write_rollup`: either the window is wrong, the fetch is truncating, or the events genuinely are not there on those nights.

Those three are the live candidates, and the evidence in `job_runs` cannot separate them:

- **The window is short.** `window_start = last_success_at or (now - timedelta(hours=24))` in `jobs/scheduler.py:61`. If `last_success_at` is ever read stale or from a run other than the immediately preceding one, the window narrows and the row count falls with it. Against this: every short run is followed by a normal 48k run, not by a 72k catch-up, so whatever was missed is never picked up later. That is consistent with the window being fine and the data being absent, and it is also consistent with the watermark advancing past events that were never read.
- **The fetch truncates without raising.** Commit `9d02e1e` added retries for transient fetch errors. If that wrapper can exhaust its retries and return the pages it already has instead of propagating the failure, you get exactly this signature: fewer rows, shorter run, status `ok`.
- **The source is half-empty on those nights.** A three-day cadence in an upstream producer would explain the pattern without any bug in this job at all.

The gap is that `job_runs` records `rows_written` but not the window the run actually used. Nothing in the table says whether the 23 August run asked for 24 hours or for 12. Logging `window_start`, `window_end` and the row count returned by `fetch_events` alongside `rows_written`, then counting source events directly for the windows of a known short run and a known normal run, separates all three candidates in one night: matching source counts implicate the fetch, a narrow window implicates the watermark, and a genuinely sparse source clears the job.
