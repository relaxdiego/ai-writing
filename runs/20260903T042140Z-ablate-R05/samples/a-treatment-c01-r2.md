`session.py` was carrying its own literal for the session TTL while `src/config/defaults.py:31` already defined `SESSION_TTL_SECONDS`, so the class attribute now reads from the config constant instead of hardcoding 3600. One test failed on the first run because `tests/test_session_cache.py::test_expiry_boundary` asserted the literal 3600; I pointed that assertion at the same constant, and the suite is back to 8 passed.

Worth being explicit about the behavioural consequence, since this is not a pure refactor: the configured value is 900, so sessions now expire after 15 minutes rather than an hour. Every caller of `SessionCache.get` will see entries dropped four times sooner. If 3600 was the intended production behaviour and `defaults.py` was the stale copy, the fix belongs in the config value rather than in the cache, and I'd want your call on which of the two numbers is the real one before this goes anywhere near a deploy.
