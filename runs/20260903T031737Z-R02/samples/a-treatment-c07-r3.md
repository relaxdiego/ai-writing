The cache key is where I'd push back first, because with row-level authorization in the WHERE clause, keying on the SQL string leaks data across users. If you're using bound parameters — `WHERE owner_id = ?` — the SQL text is byte-identical for every user who runs that query, so whoever hits it first populates the entry and everyone after gets their rows back. If you're interpolating values into the string instead, the key separates users by accident rather than by design, and it stops working the moment a query filters on something that isn't a literal in the text: a role check, an org join, anything derived from session state. Authorization enforced in a query only survives memoization if the cache key carries the same identity the WHERE clause did, which means the key has to be the parameterized query plus the full parameter tuple plus the authenticated principal — never the SQL alone.

The eight workers break the plan on a second axis. A module-level dict is per-process, so you'd get eight independent caches, each warmed separately, which cuts the hit rate substantially on everything but your hottest queries. The bigger problem is that you'd also have eight independent copies of every stale row. A worker that handles a write can evict its own entry, but the other seven keep serving the old value, and since a plain dict never evicts anything, "until something displaces it" means forever. At 400 writes a minute you're mutating state roughly seven times a second, and a cache keyed by SQL string has no way to determine which entries a given `UPDATE` invalidates — there's no correct invalidation routine to write, even setting the cross-process problem aside. Unbounded growth compounds it: a dict that is only ever written to is a memory leak on a slow fuse, and with distinct SQL strings accumulating over a long-lived process, RSS climbs until the workers get OOM-killed.

Here's what I'd suggest instead, in the order I'd do it:

1. **Find out what's actually slow** — `pg_stat_statements`, the slow query log, or whatever APM you have. In my experience most "the database is slow" problems turn out to be a missing index or an N+1 in a request handler, and fixing either is strictly better than caching: correct by construction, helps all eight workers at once, and no staleness to reason about.
2. **Cache the unscoped data first.** Reference tables, config, feature flags, anything not filtered by user — this is the cheap version of what you asked for. There's no authorization risk because there's no per-user dimension, invalidation is tractable because the data changes rarely, and a bounded LRU with a TTL in each process is genuinely fine here.
3. **If per-user caching is still needed after that**, put it in Redis or memcached so all eight workers share one copy, key it on principal plus parameters as above, give it a short TTL (30–60s) as a correctness backstop, and delete entries explicitly on write keyed by entity rather than by query text.
