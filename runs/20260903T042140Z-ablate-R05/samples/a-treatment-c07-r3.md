I'd push back on the design before writing any of it, because the version you've described has a security hole rather than just a performance ceiling, and the fix changes what the code looks like.

The key is the first problem. Your row-level authorization lives in the WHERE clause, so keying on the SQL string is only safe if the user id arrives at the database as literal text inside the statement. Most drivers and ORMs bind parameters instead, which means every user's request for their own rows produces the same string, something like `SELECT ... FROM orders WHERE owner_id = ?`. The first request populates the cache, and everyone who follows gets handed that user's rows. On the other branch, if you genuinely are interpolating ids into SQL text, the keys are distinct per user and the cache is safe, but then it almost never hits on the per-user reads you were hoping to accelerate, and you have a SQL-injection surface to worry about separately.

Process topology is the second problem. A module-level dict lives in one worker's heap, so eight workers give you eight independent caches, each seeing roughly an eighth of the traffic and each going stale on its own schedule. A user who reloads and lands on a different worker sees a different snapshot, so a value they just wrote can appear, vanish, and reappear across refreshes. Third, nothing in a plain dict ever invalidates or evicts. At 400 writes a minute, cached rows start diverging from the database within seconds of being stored, and working out which cached statements a given INSERT invalidates means tracking which tables each cached query touched, which is most of the real work in building a query cache. Memory only goes up, so each worker grows until it gets OOM-killed.

There is a version of this that works, and I'm happy to build it. It caches in Redis or memcached so all eight workers share one view; it keys on the normalized SQL plus the bound parameter values plus the authenticated principal, so authorization can't leak across the key; it carries a short TTL as a backstop and invalidates by table tag, bumping a generation counter for each table on write so dependent entries fall out; and it covers a named allowlist of read-heavy queries rather than everything, since the write-heavy tables mostly won't benefit.

Before that, though, it's worth half a day of measurement, because "repeated identical queries" is a specific pathology and slow apps more often suffer from N+1 loops, a missing index, or one unbounded scan. If the profile shows those instead, the cache adds a lot of machinery and coherence risk for very little.
