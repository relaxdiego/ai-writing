The plan has one part I'd push back on hard and one part worth keeping, so let me separate them.

Keying by the SQL string is the dangerous part, given that your authorization lives in the WHERE clauses. If you use parameterized queries, which you should be, then the SQL text is byte-identical for every user hitting that endpoint and only the bound parameters differ. `SELECT * FROM documents WHERE owner_id = ?` is one cache key serving every owner in the system, so the first user to warm the entry decides what everyone else sees. That is not a slow page, it is a cross-tenant data leak that your test suite will almost certainly pass, because in dev you are usually logged in as one user. If instead you interpolate values into the SQL and the key does vary per user, the leak goes away but so does most of the benefit: cardinality explodes, hit rates collapse, and the dictionary grows without bound until a worker gets OOM-killed. Any cache key has to include the full parameter tuple and the identity of the principal the query was authorized for, not just the query text.

The global dictionary is the second problem. Eight workers means eight independent caches that never agree with each other, so a user's write lands in worker 3 and workers 1, 2, and 4 through 8 keep serving the old row. At roughly 400 writes a minute you are mutating something about seven times a second, which is frequent enough that stale reads will be a routine user-visible bug rather than a rare race. In-process caches also have no eviction and no invalidation story; there is no way for a write to reach into the other seven processes and delete the affected entries.

Before building the version that works, I'd want to know whether the database is actually your bottleneck. Repeated identical queries usually means an N+1 pattern in the ORM or a missing index, and both of those are cheaper to fix than a cache is to operate. Can you pull the p95 latency breakdown for your slowest endpoints and the slow query log for a busy hour? A single composite index frequently beats a cache layer outright, and it cannot serve one user another user's rows.

If the numbers do say caching, the shape I'd build is a shared store such as Redis rather than per-process dictionaries, keyed on a semantic identity rather than SQL, something like `user:1234:documents:v7`. Cache the computed result at the level your application reasons about, because that is the level at which you can express invalidation: when a document changes, you know which entity keys to bust, whereas from a SQL string you cannot tell what a given write affected. Give every entry a TTL as a backstop for invalidation you missed, and decide per query type how much staleness is acceptable, since a dashboard counter and a permissions check have very different answers.

There is one version of your original idea that is safe and worth doing today: memoize within a single request. A dictionary that lives on the request context, keyed by query plus parameters, dies when the response is sent and never crosses a user boundary. It kills duplicate lookups inside one page render, which is often where the repetition actually is, and it carries none of the invalidation or isolation risk.
