I haven't found the cause yet — here's what the evidence does and doesn't support, and where I'd look next.

The failure is real and it has a shape. Across the last eight runs, three came in at roughly half the usual output (23,551 / 22,104 / 23,902 rows against a normal ~48,000), and those same runs also finished in about seven minutes instead of about fifteen. The runtime halving matters more than the row count, because it means the job wasn't doing full work and losing half of it at write time; it had less to chew on from the start. That points upstream of `write_rollup` — at `fetch_events`, at the window it's given, or at the event data itself — and away from the write path. The `with transaction()` block reinforces this, since a partial write inside it should roll back the whole run and surface as a failure, not as a quietly short but `ok` run.

The other suggestive detail is the timing: the three short runs land on Aug 23, Aug 26, and Aug 29, an exact three-day spacing that is unlikely to be coincidence over that stretch. I did not confirm it holds further back — I only pulled eight rows out of the thirty available — so the first thing worth doing is extending that query and checking whether the cadence survives. A clean three-day period would suggest something scheduled rather than something random: a competing job, a rotation or partition cycle in the event source, or a retention/compaction step that runs on its own clock and briefly moves data out from under the rollup.

What I could not rule out is the window calculation. `window_start = last_success_at or (now - timedelta(hours=24))` means every run inherits its start from the previous run's recorded success, and every run in this table is marked `ok`, so the fallback never fires. If `last_success_at` is ever written as a finish time rather than a start time, or written from a different clock or timezone than `now`, the window would silently narrow — but nothing in what I read tells me which value actually gets stored, and a narrowing of that kind would more likely produce a small, drifting shortfall than a clean halving on a fixed cadence. I'd treat it as a secondary hypothesis rather than the leading one.

To settle this, the checks I'd run next are: pull all thirty `job_runs` rows to confirm or break the three-day pattern; count rows in the source events table grouped by day over the same period, which distinguishes "the job read less" from "there was less to read"; read `fetch_events` and whatever writes `job_runs.status` and `last_success_at`; and look for any other scheduled work — ingestion, compaction, replica maintenance — with a three-day period. The source-table count is the cheapest and most decisive of these, since it splits the problem in half before any code reading is needed.
