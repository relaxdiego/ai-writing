Same Postgres, with the seven-year tail moved out of it. Neither pure option is right, but the same-database side has the stronger case, for one reason that isn't the one your team is probably arguing about.

The write path decides it. An audit event not written in the same transaction as the change it records is an event you can lose. Shipping to a separate store means either a dual write, which drops events whenever the second write fails, or an outbox — and an outbox is a Postgres audit table with extra steps, plus a relay that can lag, stall, or replay. You end up with an audit table in Postgres either way, so start with one and be honest about it. A missing audit event is a compliance finding; a large table is an operations problem, and only one of those has a clean fix.

The separate-store camp is right about the thing that actually hurts, though, and it isn't throughput. Two million a day is roughly 25 inserts a second; Postgres won't notice. It's the storage tail. Call it 5.1 billion rows, 2.5 to 4 TB with indexes, and every byte rides along in base backups, the PITR window, replica rebuilds, and major-version upgrades. You'd pay that daily to serve queries that almost always touch the last few weeks.

On the joins, I'd push back on the requirement itself. An audit record should carry a snapshot of the actor and subject as they were at the time of the event, not a foreign key to a row that has since changed. If someone's role or email changed in April, joining to live user records gives you today's answer to a question about March, which is the wrong answer for an investigation. Denormalise actor name, email, role, and tenant onto the event. Most of the join requirement disappears, and what's left is the need to query recent audit data alongside live data, which the local hot window covers.

Concretely: partition the audit table by month in its own schema; grant the application role INSERT and SELECT only, with UPDATE and DELETE revoked and a trigger as a backstop; keep twelve months resident; detach older partitions on a schedule and export them to object storage as Parquet under object lock, queryable through DuckDB or an FDW for the rare investigation that reaches back years. That gives you transactional capture, fast support queries where support actually works, backups sized to the working set, and an archive whose immutability doesn't depend on nobody having superuser.

One thing would flip this, and it's worth settling before anyone builds. SOC 2 and ISO 27001 accept role-based immutability of the kind above. A WORM mandate — SEC 17a-4, or a sector equivalent — does not: there the locked object store has to be the system of record from the first write, and Postgres becomes a short-retention staging buffer rather than the primary home. The design above is right under the first regime and materially wrong under the second, so pin down which one you're under.
