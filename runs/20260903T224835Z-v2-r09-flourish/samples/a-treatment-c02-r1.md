The photos carry an EXIF orientation tag, and something between the upload and what you serve is discarding that tag without applying it to the pixels.

A phone camera sensor has a fixed physical orientation, so the JPEG it writes almost always stores the pixels in the sensor's native layout regardless of how the phone was held. Instead of rotating the pixel data, the camera records an Orientation field in the EXIF header with a value from 1 to 8 describing the rotation and mirroring a viewer must apply before display. The phone's gallery reads that field, and so does Preview or the Photos app on your laptop, which is why the file looks correct everywhere you have checked it. Your pipeline reads the pixels, ignores the field, and produces a derivative in which the rotation instruction has been thrown away. This is deterministic because the tag is a property of the file, so the same upload fails the same way forever, and it hits only some photos because a picture taken in the sensor's default orientation has Orientation 1 and needs no correction. Screenshots, edited exports and anything already normalised by another tool arrive with no tag at all and pass through fine.

The usual culprit is the resize or re-encode step. Most image libraries decode to a raw bitmap, drop all metadata on write, and never consult the orientation field on the way through, so the thumbnail comes out rotated even though the original was fine. Confirm this before changing anything: run `exiftool -Orientation -n` against the file as uploaded and against the derivative you actually serve. A value of 6 or 8 on the original and nothing on the derivative is the whole diagnosis. If you serve originals untouched, the variable is the rendering path instead. Browsers have honoured the tag in `<img>` since roughly 2020, but a `<canvas>` or `createImageBitmap` path can still bypass it depending on how you decode, and CSS `image-orientation: from-image` only affects the element, not pixels you have read out yourself.

The fix is to normalise at ingest, rotating the pixels once and resetting the tag, so that everything downstream can treat orientation as solved:

- sharp: `sharp(input).rotate().resize(...)`, where `rotate()` with no argument applies the EXIF transform.
- Pillow: `img = ImageOps.exif_transpose(img)` before any resize.
- ImageMagick: `-auto-orient` early in the argument list.

Three details decide whether this actually works. The auto-orient has to run before any resize or crop, because a crop box computed against unrotated pixels lands on the wrong part of the image. If you preserve metadata on write, set Orientation to 1 explicitly, or viewers will apply the rotation a second time to pixels you have already rotated. And use a library call rather than a hand-rolled rotate: values 2, 4, 5 and 7 involve mirroring, and a rotation-only implementation silently produces mirrored faces and backwards text. While you are stripping metadata, keep the ICC profile, or wide-gamut phone photos will shift colour.

For the photos already stored wrong, reprocess from the originals. That only works if you kept them, which is the argument for keeping the untouched upload as the source of truth: once a derivative has been baked into the wrong orientation and the tag discarded, nothing in the file records what the correct orientation was, and the only recovery is a human looking at it.
