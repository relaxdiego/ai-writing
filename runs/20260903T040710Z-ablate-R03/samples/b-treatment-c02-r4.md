Your scepticism is reasonable, but not for the reason you might think. "Always a different test" doesn't rule out pool exhaustion; it's exactly what pool exhaustion looks like, because the test that leaks the connection is not the test that blocks. The leak happens somewhere upstream, the pool drains, and the hang lands on whoever next asks for a connection. So the observation you're using to doubt the hypothesis doesn't actually discriminate, and neither does anything else you have yet. What you need are experiments that separate the families, and the good news is that the cheapest one also happens to be the most informative.

Start from the general fact that a hang, as opposed to a failure, means some wait in the stack has no deadline attached to it. Pool checkout with an infinite timeout, a socket read with no `SO_RCVTIMEO`, a database lock wait with no `lock_timeout`, a `join()` on a thread that will never finish. Whatever the root cause, it is only manifesting as a hang because a layer under it declined to give up. That reframing matters because it tells you the first move: make every wait fail fast, and the hang converts itself into a stack trace that names the culprit.

Beyond the pool, the candidates that fit "integration tests only, CI only, one in twenty" are worth naming individually because they predict different evidence. Cross-worker database contention is a strong one: if CI runs the suite with parallel workers against a shared schema and your laptop runs it serially or with fewer workers, two workers can collide on a row, a table lock, or an advisory lock while one of them sits in an uncommitted transaction. No deadlock detector fires, because it isn't a cycle, just a wait. Thread-pool or event-loop starvation is another, and it is characteristically CI-only because CI runners have fewer cores: a blocking call occupying the last worker thread, with the work that would release it queued behind itself. Then there's the subprocess pipe deadlock, which is badly underdiagnosed. If a test spawns a process, captures its stdout, and doesn't drain the pipe until after `wait()`, the child blocks on write once the 64KB kernel buffer fills, and the parent blocks forever on the child. Verbosity differences between local and CI runs are enough to flip that from fine to fatal. And finally, consider that the suite may not be hanging at all: if a worker process is OOM-killed, the runner can sit waiting for a report that will never arrive, and the "hanging test" is merely the last one it printed before the worker vanished.

To tell these apart, the essential capability is capturing state at the moment of the hang rather than letting CI kill the job at its ten-minute timeout and hand you nothing. Add a watchdog that fires after a period of no test progress and dumps thread stacks (`jstack`, `py-spy dump`, `SIGQUIT`, `SIGUSR1` depending on runtime), open file descriptors, socket states from `ss -tanp`, your pool's active/idle gauges, and the database's own view via `pg_locks` joined against `pg_stat_activity`. Upload it as an artifact. One captured dump will usually end the argument outright, because a thread parked in `pool.acquire` looks nothing like one parked in `recvfrom` or `waitpid`.

Alongside that, run three cheap discriminating experiments. Set the pool acquire timeout to something finite, say ten seconds; if the hypothesis is right, one run in twenty now fails fast with a stack trace at the acquisition site, and if runs still hang, the pool is exonerated for the price of a config line. Run the CI suite with a single worker; if the hang disappears, you're looking at cross-worker contention rather than a per-test leak, and if it persists, parallelism is off the hook. And try reproducing locally under CI's actual constraints rather than your laptop's, meaning `docker run --cpus=2 --memory=2g` and the suite looping a hundred times, which is what surfaces starvation and widened race windows that a fast eight-core machine papers over.

One thing to put in place regardless: log the random seed and the resulting test order on every run, and check `dmesg` for OOM kills in the failing jobs. Order-dependent state leakage between tests, such as a global fake-timer installed by one test and never restored, produces precisely your symptom pattern, and without a recorded order you cannot replay the failure even once you've caught it.
