Two facts in your description do most of the diagnostic work, and they point away from the pool theory as stated. The first is that it lands on a different test each time, which means the fault almost certainly isn't in any test's own logic but in something shared: a resource that accumulates across the run, a piece of global state one test leaves behind for whichever test runs next, or a race that any test can lose given the wrong interleaving. The second is that it never happens locally, which usually means the CI machine differs in a way your code is quietly sensitive to, most often core count, latency, or memory pressure rather than anything about the code path itself.

Connection pool exhaustion is a member of the first family and worth taking seriously, but it makes a prediction you can check almost for free. A leak drains the pool monotonically, so hangs should cluster toward the end of the run rather than scattering uniformly across it. If you plot where in the suite each of your failures landed and the distribution looks flat, exhaustion in the simple sense is unlikely. It's also worth noting that an exhausted pool is very often the symptom rather than the disease: one operation hangs while holding a connection, and twenty tests later the pool is empty and everything blocks on acquire. The hang you observe is then several minutes downstream of the actual bug.

The candidate I'd weight most heavily given "never locally" is thread pool or event loop starvation caused by a smaller CI machine. If any pool is sized from the CPU count, your laptop's twelve cores and the runner's two produce very different concurrency limits, and code that blocks a worker while waiting on work that must be executed by that same pool deadlocks only once the required concurrency exceeds the pool size. This reproduces reliably under `taskset -c 0,1` or `docker run --cpuset-cpus=2`, which makes it cheap to confirm or eliminate.

Close behind is cross-test state leakage, which the random ordering many suites use would explain the "different test every time" pattern neatly. A test that leaves a transaction open holds locks, and the next test's truncate or migration blocks behind it forever, since a plain lock wait is not a deadlock cycle and the database's deadlock detector will never fire. Frozen or mocked clocks do the same thing in a different register: a test freezes time globally, doesn't restore it, and something downstream waits on a timeout that can no longer elapse. In both cases the culprit is a pair of tests, not one, so the useful thing to record is which test ran immediately *before* the hang, along with the ordering seed.

Then there is the family of missing timeouts meeting a different network. A TCP connect to a host whose packets are being dropped by CI egress rules, a DNS lookup with no deadline, a dependent service container that came up slowly or was OOM-killed and is no longer accepting connections: locally each of these is loopback and instant, in CI each can block indefinitely if no timeout is set. A leaked child process holding the stdout pipe open belongs here too, though that tends to hang the run at the end rather than mid-suite.

The way to collapse all of this from speculation into one observation is to capture a stack dump at the moment of the hang instead of reasoning from the outside. Set the CI job timeout below the platform's kill timeout and use it to signal the process rather than terminate it: `timeout -s QUIT` gives you all goroutines in Go and a thread dump in the JVM, `py-spy dump --pid` works on a live Python process without cooperation, Node gives you a report on SIGUSR2 with `--report-on-signal`. Pair that with `ss -tanp` for socket states and a query against the database's own view of active and idle-in-transaction sessions. One good dump will tell you whether you're parked in a pool acquire, a lock wait, a socket read, or a condition variable, and those four answers correspond to four different bugs.

While you're waiting for that, make the hang fail loudly. Put an acquire timeout on the pool, a statement and lock timeout on the database, and read and connect timeouts on every client, so the next occurrence is a stack trace rather than silence. Setting pool size to one with a short acquire timeout will also settle the original hypothesis in a single run: if the theory is right, the failure becomes immediate and deterministic, and if the suite passes normally, you can stop arguing about it.
