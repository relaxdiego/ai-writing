Your photos are fine; something in your upload pipeline is dropping the EXIF Orientation tag that tells a viewer which way is up.

A phone's camera sensor is fixed relative to the body, so when someone turns the phone sideways the sensor still writes out pixel rows in its own unchanging order. Rather than rotating those pixels, the camera records a small metadata field, EXIF Orientation, with one of eight values covering the four rotations and their mirrored variants. The phone's gallery reads that tag and rotates on display, and so does Preview or Photos on your laptop, which is why the file looks right everywhere you've checked. Browsers honour it too these days: `image-orientation: from-image` has been the default for `<img>` since around 2019. What almost certainly happens on your site is that the file gets re-encoded somewhere between the upload form and storage. A resize, a thumbnail pass, a format conversion, or a deliberate metadata strip for privacy decodes the JPEG to a raw bitmap, writes a new file, and carries none of the original metadata across. The pixels are still in sensor order, but nothing is left to say so, and the browser has no choice but to draw them as they are.

That also explains the two things that look strange about the symptom. It is a property of the file, not of the request, so the same photo produces the same wrong result forever, and re-uploading changes nothing. And it only hits some photos because only some have a non-trivial orientation value: a portrait shot usually lands on 6 or 8, whereas screenshots, images that have been through an editor, and anything downloaded from the web have generally been normalised to 1 already and pass through your pipeline unharmed.

The fix is to bake the rotation into the pixels at ingest, before you resize, crop, or strip anything, and let the library clear the tag as part of the same operation:

- ImageMagick: `convert in.jpg -auto-orient -resize 1200x out.jpg` (the flag must come before `-resize`)
- libvips CLI: `vipsthumbnail --rotate`
- sharp (Node): `sharp(buf).rotate()` with no argument, called before `.resize()`
- Pillow (Python): `ImageOps.exif_transpose(img)`
- Go: `imaging.AutoOrient` or `imaging.Decode(r, imaging.AutoOrientation(true))`

Use one of those rather than hand-rolling a rotation from the tag value, because four of the eight values include a mirror, and code that only handles 90/180/270 will silently flip a handful of photos left-to-right instead.

Two details will bite you if you miss them. Ordering matters beyond just resize: any crop coordinates or face-detection boxes computed on the un-rotated bitmap will point at the wrong region once you rotate, so auto-orient first and compute everything downstream of it. And for orientation values 5 through 8 the rotation swaps width and height, so the dimensions you store in the database, the aspect-ratio placeholder you render to avoid layout shift, and any "max 4000px" validation all need to be read after the rotation, not from the file header. Separately, if you do a client-side downscale to a canvas before uploading, that is a strong candidate for where the tag is being lost, since canvas gives you a bare bitmap with no metadata attached; check that path before you go hunting on the server.

For the photos already stored wrong, reprocess from the originals if you kept them. The operation is safe to run broadly because auto-orient is a no-op on a file whose tag is absent or already 1, and every library above clears the tag as it rotates, so a file cannot be double-rotated by a second pass. The one case that does go wrong is a pipeline that rotated the pixels but left the tag at 6, which then gets rotated again by anything that trusts it; if you find files like that in your storage, they need the tag reset rather than another rotation. If you no longer have the originals and only have stripped derivatives, the information is genuinely gone and the only recovery is asking users to re-upload once the pipeline is fixed.

One last thing worth checking while you are in there: stripping metadata is the right instinct, since photos routinely carry GPS coordinates you do not want served publicly. Keep doing it, just do it after the auto-orient step. And if you accept HEIC from iPhones, confirm your decoder honours the rotation there as well, since the equivalent field lives in the container rather than in an EXIF block and some converters handle it separately.
