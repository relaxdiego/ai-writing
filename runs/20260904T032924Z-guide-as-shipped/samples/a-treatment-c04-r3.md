Move the files to a storage service and keep a reference in your database. At your size and team size, a shared disk buys you nothing that object storage doesn't, and it costs you a piece of infrastructure that one of your four people has to own.

The breakage you were warned about is worth being precise about, because it shapes the migration. Once three machines sit behind a load balancer, a file written to machine A's disk simply does not exist on B or C. The upload succeeds, then the download 404s or succeeds depending on which machine the request happens to land on, and the failure looks intermittent rather than structural. Sticky sessions would hide it in casual testing and still lose the file whenever a machine is replaced, redeployed, or scaled down.

A shared disk (NFS, or EFS if you are on AWS) does fix visibility, and that is the whole of what it fixes. In exchange you get a filesystem that every app server now depends on for liveness, latency that is much worse than local disk and occasionally much worse than that, POSIX locking semantics that behave differently under a network, a backup story you have to build yourself, and a capacity number somebody has to keep an eye on. You also still serve every byte through your application processes, so a few large downloads can tie up the workers that are supposed to be rendering pages. Object storage is a managed durable service with versioning and lifecycle rules already in it, and 200 GB is small enough that the bill is on the order of a few dollars a month with roughly a dollar a month added each year of growth. Request and egress charges will matter more than storage; if egress looks heavy for your traffic, Cloudflare R2 or Backblaze B2 price it far lower than S3 while keeping the same API.

The migration can be done without a flag day, in this order:

1. Add columns to the file table for the storage key and a nullable disk path, so a row can be in either place.
2. Change the write path to upload to the bucket and record the key. New files stop landing on disk from this moment.
3. Change the read path to use the key when present and fall back to the disk path when it is null.
4. Backfill the existing 200 GB with `rclone` or `aws s3 sync`, filling in keys as you go. This is the slow part and it runs while the site is up.
5. Once no row has a null key, delete the fallback branch and the local files, and take the disk out of the deploy.

A few things are easier to get right at the start than to correct later. Keep the bucket private and serve downloads through short-lived presigned URLs rather than making objects public, since these are account files and a public URL is permanently public to anyone who has ever seen it. Store the object key alone, not a full URL, so that changing bucket, provider, or CDN is a config change instead of a data migration. Keep the real metadata in the database row: owner, original filename, size, content type, checksum, and upload time, so that listing a user's files never requires talking to the storage service. Set content type and content disposition at upload time, because fixing them afterwards means rewriting objects. Turn on versioning and a lifecycle rule from day one; it is the cheapest protection you will ever buy against a bad delete.

The one case that would change this answer is a hard constraint you haven't mentioned: on-premise hosting with no object storage available, or code that genuinely needs a POSIX path, such as tools that seek into large files rather than reading them whole. Photos and documents are not that, and even under an on-premise constraint MinIO gives you an S3-compatible API on your own hardware, which keeps the application code identical to the hosted version.
