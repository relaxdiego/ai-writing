The most informative fact you have is the one that makes the pool theory awkward. A pool leak accumulates, so hangs from exhaustion cluster toward the end of a run and the position drifts later as the suite grows; if your hangs land uniformly across the run, something else is going on. Connection pools also usually have an acquisition timeout, and a hang means either that timeout is unset or the wait is happening somewhere with no deadline at all. Before arguing about causes, it is worth noticing that the real defect is the absence of a bound on some wait. Whatever is slow, a correctly bounded system fails in ninety seconds with a stack trace rather than sitting there until the job's hour cap.

"Always integration, always a different test, never local" is the signature of a timing-dependent interleaving rather than a bad test. CI runners typically have two cores against your eight, they are throttled and noisy, and they often run under a cgroup with a memory cap. Under that compression, orderings appear that your laptop essentially never produces: a callback that fires before the waiter registers, a lock acquired in a different order by a background thread that only wins the race when the main thread is descheduled, a future awaited by the same executor that must run the task completing it. Thread pool starvation is the version of this I would look at first, because it presents exactly as a hang at an arbitrary point and is strongly load-dependent. Blocking on an async result from inside a bounded worker pool is fine at eight cores and deadlocks at two.

Several other mechanisms are genuinely CI-only and worth ruling in or out cheaply. If your harness spawns a subprocess and captures output through a pipe that nothing drains until the process exits, the child blocks forever once the pipe buffer fills, which never happens locally because a terminal drains continuously. If concurrent CI jobs share one database, Redis instance or Kafka topic, then one run in twenty is roughly the rate at which two jobs overlap, and the hang is an ordinary lock wait against a sibling build. A test container that occasionally fails its health check, a DNS lookup on a network with no resolver timeout, or a TCP connection to a peer that black-holes packets with no keepalive will all produce an unbounded wait that is invisible on a developer machine.

Stop guessing at the first opportunity and get a dump out of the hung process, because that single artifact discriminates between everything above in one shot. Add a watchdog that fires below the job timeout and, before the runner is torn down, captures: full stacks for every thread or goroutine (`jstack`, `kill -QUIT` for Go, `py-spy dump --pid`), the socket table with `ss -tanp`, open file descriptors via `lsof`, and the database's own view of who is waiting, meaning `pg_stat_activity` including `wait_event` and `pg_locks`, or `SHOW ENGINE INNODB STATUS`. Upload all of it as a build artifact. Pool exhaustion shows as many threads parked in the pool's acquire method with the pool at max and no free connections; a lost wakeup shows one thread in a condition wait with nobody else running; a pipe deadlock shows a thread blocked in `write` and a parent blocked in `waitpid`; a cross-job lock shows a database session waiting on a lock held by a connection that isn't yours.

Alongside that, make the suspicion falsifiable. Set the pool acquisition timeout to a few seconds and every socket and query timeout to something short, so the next occurrence converts from a hang into a labelled failure that names the resource. Then reproduce under CI-like constraints locally: pin the suite to two CPUs with `taskset` or `docker run --cpus=1`, fix the test ordering seed, and loop the suite fifty times overnight. At a one-in-twenty base rate, you need on the order of sixty clean runs before a fix is more than a hopeful correlation, so the loop job is worth building regardless of which hypothesis wins.
