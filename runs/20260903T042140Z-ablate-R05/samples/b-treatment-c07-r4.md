I'd push back on this one, because the version you've described has a failure mode that isn't a performance regression but a data breach.

The core problem is the key. Your authorization lives in the WHERE clause, which means the SQL that fetches user 12's invoices and the SQL that fetches user 807's invoices is very likely the same string with different bound parameters, especially if you're using prepared statements or any ORM that parameterises properly. Key the cache on the SQL text alone and the first user to hit an endpoint populates a cache entry that every subsequent user reads, with the WHERE clause that was supposed to protect the rows now discarded along with the parameters. You would not see this in testing with one account, and you would see it immediately in production. Any cache key has to include every bound parameter plus the identity the authorization is scoped to, and honestly the identity should be in the key even when you believe it's already covered by the parameters, so that a future query which derives its filter from session state rather than an argument can't silently share an entry.

The eight workers undermine the mechanism in a quieter way. A global dictionary is global only within one Python or Node process, so you get eight independent caches, each with roughly an eighth of the traffic to warm it, each holding its own copy of the same rows. Memory use multiplies by eight, hit rates fall well below what a back-of-envelope calculation suggests, and invalidation becomes impossible: when a write happens in worker 3, workers 1, 2 and 4 through 8 have no idea and keep serving what they have. At 400 writes a minute that isn't a rare edge case. Something is changing every 150 milliseconds, and an in-process dictionary with no eviction and no TTL will drift from the database continuously while growing without bound, since nothing ever removes an entry.

There's a much cheaper version of your idea that's actually safe, and I'd start there: memoize queries for the lifetime of a single request. Same dictionary, but created when the request arrives and discarded when it finishes. Cross-user leakage can't happen because the cache never outlives one user's request, staleness is bounded by the request duration, and it eliminates the most common real cause of slow endpoints, which is the same lookup being issued five or fifty times while rendering one page.

Beyond that, I'd want to know what's actually slow before adding infrastructure. Turn on slow query logging or whatever your APM offers for a day and look at the aggregate: total time per query shape, not worst single execution. The usual answer is two or three queries missing an index, or an N+1 pattern in a loop, and fixing those gives you a larger speedup than caching would while leaving correctness alone. If a genuinely hot, genuinely expensive read survives that analysis, then a shared cache in Redis or memcached is the right home for it, with a key that includes the user scope and all parameters, a TTL short enough that a missed invalidation is survivable, and explicit invalidation on the writes that affect it. Doing that for a handful of identified queries is tractable. Doing it for every query in the application, which is what the blanket approach commits you to, means enumerating for each write which cached keys it invalidates, and that mapping is where these projects usually founder.
