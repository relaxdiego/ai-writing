Your instinct is right that repeated identical work should not be repeated, but each of the three things you described about the deployment breaks the specific design, and one of them breaks it in a way that leaks data between users.

Start with the authorization, because that is the serious one. If you use parameterized queries, which you should be, then the SQL string is a template: `SELECT ... WHERE owner_id = ? AND status = ?`. That text is byte-identical for every user who hits that code path, so a cache keyed on it will hand user B the rows that were fetched for user A. The failure is silent and looks exactly like a cache hit, and it will not show up in testing unless you happen to run two accounts through the same worker in the same window. The alternative, interpolating values into the SQL so the key differs per user, does avoid the leak, but then almost every key is unique, your hit rate collapses toward zero, and the dictionary's cardinality is bounded only by the number of distinct user-and-filter combinations you ever serve.

The eight workers undercut the idea from a different direction. A module-level dictionary is per-process, so you get eight independent caches: eight copies of the memory, and a hit rate roughly an eighth of what you are imagining, since the load balancer scatters a user's requests across workers. The caches also disagree with each other, which users perceive as a value that flips between old and new as they refresh. And because a write handled by worker 3 has no way to reach worker 6's dictionary, there is no place to put invalidation even if you wanted to write it.

Then 400 writes a minute means roughly seven opportunities per second for some cached entry to become wrong, against a cache that has no invalidation and no eviction. Entries never expire and never leave, so the dictionary is also a slow memory leak, and the process eventually gets restarted by whatever watches its RSS, which is its own kind of cache invalidation.

Before building any of this, I would want per-query timings and call counts from a real workload, because "the same expensive query runs repeatedly" is a narrower diagnosis than it sounds. Slow request handling in an app this shape is more often an N+1 pattern issuing hundreds of cheap queries per request, or a missing index turning a filter into a sequential scan. Caching either of those hides the cost rather than removing it, and the index is usually a one-line change that helps every user including the ones who miss the cache.

There is a version of your idea that is genuinely safe and worth doing: memoize within a single request rather than globally. Hang a dictionary off the request context, key it on the SQL template plus the full bound-parameter tuple, and throw it away when the response is sent. One request belongs to one user, so there is no cross-user leak; staleness cannot outlive a single request; memory is bounded by definition. This collapses N+1 fanout and repeated lookups of the same row in one handler, which is where a large share of the duplicate-query cost usually lives.

If measurement then shows you need caching across requests, do it in a shared store such as Redis rather than in process memory, so the eight workers see one cache and a write on any of them can invalidate it. Build the key from the query template, every bound parameter, and the authenticated user or tenant id explicitly, so a missing parameter cannot silently widen the scope. Give every entry a short TTL as a backstop, invalidate by entity on write rather than relying on the TTL alone, and skip the cache entirely for reads inside a write transaction so a user always sees their own writes.
