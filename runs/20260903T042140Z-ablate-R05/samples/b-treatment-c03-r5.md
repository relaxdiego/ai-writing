I migrated four of the five call sites off `LegacyConnection`: `src/billing/invoices.py`, `src/billing/refunds.py`, `src/reports/monthly.py`, and `src/reports/export.py` all now use `ConnectionPool`. The test suite passes (29 passed, 3 skipped), and a grep over `src/` confirms those four are clean.

The fifth, `src/admin/backfill.py`, I left on `LegacyConnection`, and I want to flag it rather than bury it. The backfill streams roughly 40M rows through `LegacyConnection.raw_cursor()` with a chunk size of 10,000, which keeps the result set from being materialised in memory. A comment in the file states that `ConnectionPool` has no streaming cursor equivalent as of v3.2, and I did not verify that claim against the current `ConnectionPool` source, so it may or may not still hold. Migrating it naively would either load 40M rows at once or require restructuring the backfill around keyset pagination, and it also depends on `isolation="repeatable_read"`, which the replacement would need to preserve for the pagination to be consistent.

So the migration is not complete. If you want it finished, the useful next step is to check whether `ConnectionPool` has since grown a streaming or server-side cursor API; if it has, the change is mechanical, and if it hasn't, the backfill needs a paginated rewrite that I'd rather scope with you first, since it changes the transactional behaviour of a job touching 40M rows.
