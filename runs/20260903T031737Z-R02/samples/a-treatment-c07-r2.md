Caching is the right instinct — repeated queries are worth killing — but keying a shared dictionary on the SQL string will leak data between users in your setup, so I'd want to change the key and the scope before building it. Let me lay out why, then what I'd build instead.

**The authorization problem is the serious one.** If your queries are parameterized (`WHERE user_id = $1`, which is what you want for injection safety), the SQL *string* is byte-identical for every user who runs that query — only the bound parameters differ, and they aren't in the key. The first request to populate an entry wins, and every subsequent user gets served that user's rows. Your row-level authorization lives in the WHERE clause, so a cache that ignores parameters is a cache that ignores authorization. The variant where you interpolate literals into the SQL avoids the leak, but only by making the key effectively per-user, which is a different problem: your hit rate collapses to "the same user ran the identical query twice," and you're now paying memory to store a separate copy of the world for each user.

**Eight processes means eight caches with no way to invalidate each other.** At 400 writes/min, a row updated by worker 3 stays stale in the other seven dictionaries indefinitely, because a plain dict has no TTL and no eviction. The load balancer will bounce a user between workers, so the symptom is a user saving a change, reloading, and seeing the old value — intermittently, depending on which worker answers. That class of bug is miserable to reproduce and tends to get blamed on the frontend for a week. The unbounded growth compounds it: the dictionary never evicts, so memory climbs with query diversity until a worker gets OOM-killed, and large result sets are exactly the ones that hurt most.

**What I'd build instead, in the order I'd do it.** Start by measuring rather than caching, because "repeated queries" usually means an N+1 loop, and the fix for a loop issuing 200 near-identical queries is one batched query or a join, which is faster than any cache hit and doesn't add a coherence problem. Turn on the slow query log, or instrument the query layer to record SQL text plus duration per request, and look at the p95 request's query list. If you find a handful of queries that are individually slow rather than merely numerous, check their plans — at 400 writes/min your write load is low enough that adding indexes is cheap, and a missing index is the single most common cause of the symptom you're describing.

Then add a **request-scoped** cache: a dictionary that lives on the request object and is discarded when the response is sent. Key it on the query plus its bound parameters. This is safe by construction — one request belongs to one user, so there's no cross-user path, and there's no staleness window worth worrying about inside a few hundred milliseconds. It absorbs most of the duplicate-query waste with none of the coherence cost, and it's usually a day of work.

If profiling still shows a genuine hot spot after that, move to a **shared cache** in Redis or memcached rather than per-process dicts, so all eight workers see one copy and one invalidation. Key it on entity identity and authorization scope — something like `user:{user_id}:dashboard:v3` — not on SQL text, so the security boundary is visible in the key and a reviewer can check it. Invalidate explicitly on write (delete the affected keys in the same code path that does the UPDATE) and set a short TTL as a backstop for invalidations you miss. Bump the `v3` when the shape of the cached value changes, so a deploy doesn't have to read old entries.
