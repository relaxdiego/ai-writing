The most informative fact you have is "always a different test." That almost certainly rules out the tests themselves as the location of the bug. If a specific test contained a deadlock, you would see it hang on that test, at whatever rate its race window opens. A hang that lands anywhere means some shared condition goes bad and whichever test is running at that moment takes the blame. So the real question is which shared thing degrades, and there are only a handful of families.

Pool exhaustion is one member of that family, so the suggestion isn't silly, but it has a signature you can check in an afternoon. A leaked-connection pool drains monotonically, which means hangs should cluster in the back half of the run: the suite survives until the Nth checkout fails, and N is roughly constant. If you log the index of the last test to start and the distribution is uniform across the suite rather than late-biased, that's strong evidence against a leak. The second check is even cheaper. Most pools have an acquisition timeout, and if yours is set, exhaustion produces an error naming the waiting test rather than a hang. If it's unset or infinite (several ORMs default that way), set it to ten seconds. Either the mystery converts into a clean error message that identifies the culprit, or it doesn't and you've eliminated the hypothesis for free.

The alternatives worth weighing against it, roughly in order of how often they turn out to be the answer:

Thread pool starvation from CPU count. Something blocks a worker thread waiting on a future whose completion needs a thread from the same bounded pool. Your laptop has eight or sixteen cores and the pool is wide enough that the cycle never closes; the CI container has two, or has a cgroup quota of two while the runtime's `availableProcessors` reports the host's sixty-four and sizes the pool wrongly. This explains "never locally" better than anything else on the list, and it explains "different test each time" because any test with enough concurrent work in flight can be the one that closes the cycle.

A genuine lost-wakeup or check-then-wait race. A condition signalled before the waiter registers, or a `wait` that isn't in a loop. The per-test probability is small and roughly uniform, which matches your distribution, and a loaded, slower, noisier CI machine widens the window by exactly the amount needed to take it from never to five percent.

Inter-test state leakage. If your runner randomizes order or shards across workers, the hang is a property of a pair of tests, not one: test A leaves a lock held, a mock server unclosed, a static flag set, or a frozen clock installed, and the next test to touch that resource blocks forever. Different victim every time, by construction. Check whether the seed is logged and whether you can replay it.

Environment and external dependencies. Testcontainers pulls, docker-compose services, DNS. A container that comes up without a working resolver or default route will hang a connect indefinitely rather than fail it, and again the victim is whoever first needs it.

Pipe deadlock on captured output. A subprocess fills the 64KB stdout buffer while the parent is waiting on exit instead of draining, and both stop. This is underrated and fits your case suspiciously well, because CI almost always runs with verbose logging and without a TTY, and locally you run with neither.

The way to tell these apart is to stop trying to reason from the outside and capture the process state while it's stuck. Do not let the CI job timeout kill it, because that gives you an artifact containing nothing. Wrap the test command in a watchdog inside the job, set to fire a few minutes before the job's own limit, and have it dump: all thread stacks (`jstack`, `py-spy dump --pid`, `SIGQUIT` for Node with the inspector, `gdb -p` with `thread apply all bt`), then `ps -efL`, `ss -tanp`, and `dmesg | tail`. One such dump discriminates nearly the whole list on sight. Threads parked in `getConnection` is the pool. Two threads each holding what the other wants is a lock cycle. Every worker in `await` with an empty queue is starvation. One thread blocked in `write` is the pipe. Everything idle with a single socket read outstanding is the external dependency.

While you wait for that to catch one, three cheap experiments narrow things independently. Run the suite with parallelism forced to one: if the hangs stop, it's an inter-test interaction and you can drop the single-test-race theories. Run it locally in the actual CI image under `docker run --cpus=2`, in a loop, a few hundred times: if it reproduces, thread starvation is very likely and you've also bought yourself a local repro. And turn CI's log level down to whatever you use locally for a dozen runs, which is a direct probe of the pipe theory.

One process note. At a five percent rate, don't bisect. A clean run is weak evidence, so you'd need dozens per candidate commit and you'd still be guessing. Add per-test start and finish timestamps to the CI artifact now, unconditionally, so every future hang tells you where in the run it landed without anyone having to remember to look. That single change turns your twenty-run wait into data instead of anecdote.

Underneath all of this is one structural observation worth acting on regardless of which hypothesis wins: a hang is an error that lost its timeout. Every place your suite can stop forever is a place with no deadline on it, and connect, read, lock acquisition, pool checkout, subprocess wait and the tests themselves should all have one.
