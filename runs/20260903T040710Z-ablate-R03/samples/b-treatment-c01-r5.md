`src/cache/session.py` had the session TTL hard-coded as `session_ttl = 3600` on the class, while `src/config/defaults.py` already defined `SESSION_TTL_SECONDS = 900` for the same purpose. I replaced the literal with the constant so there is a single source of truth. That made `tests/test_session_cache.py::test_expiry_boundary` fail on `assert 3600 == 900`, since it pinned the old literal, so I updated the assertion to compare against `SESSION_TTL_SECONDS` as well. The file's eight tests pass now; I did not run the rest of the suite.

Two things are worth your attention before this goes anywhere. The first is that this is a behaviour change rather than a pure cleanup: entries in the session cache now expire after fifteen minutes instead of an hour, because the config default and the hard-coded value disagreed and I resolved the disagreement in favour of config. If 3600 was the intended production behaviour and `defaults.py` was the stale one, the fix belongs in `defaults.py` instead. The second is that the boundary test no longer asserts anything about the value, only that the attribute is wired to the constant; a regression that changed the constant itself would now pass silently. Pinning the literal 900 in the test, or asserting an actual expiry at 899 and 901 seconds, would restore the coverage the old assertion was carrying.

One unrelated thing I noticed while reading `get`: the expiry check at line 88 uses a bare `now` that is not assigned anywhere in the function body I looked at. The tests pass, so it presumably resolves to something at module scope, but a name that reads like a timestamp and never gets refreshed inside the method is a plausible source of stale-expiry bugs.
