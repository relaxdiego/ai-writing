Caching is a reasonable instinct here, but keying on the SQL string collides badly with the row-level authorization you've described, and I'd want to change the shape of it before writing any code. If you're using parameterized queries, the SQL text is byte-identical for every user hitting the same endpoint; the user id lives in the bound parameters, not the string. So the first user to run a query populates the entry, and every other user gets served that user's rows. The authorization is still there in the WHERE clause, it just stops being consulted. If instead you're interpolating the user id directly into the SQL, the keys are distinct and the leak goes away, but then the key space fragments per user and the hit rate on a per-process dictionary collapses to nearly nothing, which defeats the point.

The eight workers cause a second problem independent of the first. A module-level dict is per-process, so you get eight caches that never see each other's writes. At roughly seven writes a second, an invalidation performed in worker 3 leaves the other seven serving stale rows until something evicts them, and a plain dict has no TTL and no eviction at all: entries live until the process restarts, and memory grows without bound. Users behind the load balancer would see data flicker between old and new depending on which worker took the request.

What I'd suggest instead depends on where the time is actually going, and I'd want to measure that first. In applications shaped like this one the win is usually not caching but a missing index or an N+1 pattern issuing hundreds of small queries per request, both of which are cheaper to fix and carry none of this risk. If we measure and caching really is the answer, the version that works is a shared store such as Redis, with the authorization principal built into the key rather than left in the query text, a short TTL as a backstop, and explicit invalidation on write keyed to the affected entity. Caching a computed result or a rendered fragment, where the ownership of the data is explicit at the call site, tends to be safer than caching at the query layer, where it's easy to forget which rows a given string was allowed to return.

If you can point me at the slow endpoints, or turn on query logging for a few minutes of real traffic, I can look at what's actually dominating the request time and tell you whether a cache is worth building.
