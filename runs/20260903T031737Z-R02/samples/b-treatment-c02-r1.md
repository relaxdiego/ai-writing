Your skepticism is well-founded, and the reason is in the statistics you already have. A connection leak is a monotone process: every run of the suite leaks the same connections on the same code paths, so once the leak exceeds the pool size you should hang on nearly every run, and the hang should drift steadily *later* in the suite as you add tests and *earlier* as you shrink the pool. A 1-in-20 rate with a uniformly scattered hang location doesn't fit that shape unless the leak itself is conditional — it only happens on an error path that is itself flaky, which just relocates the mystery. What "different test every time, only in CI, low rate" actually points at is a shared resource or a timing window that any test can lose, where the identity of the victim is an accident of scheduling.

## The mechanisms that produce this signature

The one most often misdiagnosed as pool exhaustion is a **leaked open transaction**. A test fails or times out partway through, its connection goes back to the pool still `idle in transaction` holding row or table locks, and the next test that runs a `TRUNCATE`, a migration, or an `ALTER` blocks on that lock forever, because unlike a deadlock — which Postgres detects and aborts — a plain lock wait has no timeout unless you set one. Both this and true pool exhaustion present identically from the outside as "the test suite stopped talking to the database," which is exactly why the pool theory is sticky.

A second family is **timeouts that don't exist at the socket layer**. If a connection is silently dropped by a NAT gateway, a service mesh sidecar restarting, or a container network hiccup, and your client has no read timeout and no TCP keepalive, the read blocks forever on a connection the kernel still believes is established. CI is where this appears because CI is where the network path has extra hops that your laptop's loopback doesn't. Over time this also drains the pool, so it eventually *looks* like exhaustion while having a completely different root cause and fix.

Third, **CPU quota interacting with thread pool sizing**. A container limited to half a core still reports the host's core count through `/proc/cpuinfo`, so libraries that size worker pools from CPU count build a 64-thread pool that gets a sliver of a core. Anything that requires two of those threads to make progress in a bounded time — a blocking call made from inside a pool that also serves the callback — deadlocks under contention and runs fine on an unloaded laptop. Related, and worth ruling out early: a **stdout pipe deadlock**, where a subprocess fills the 64KB pipe buffer because the parent isn't draining it, which never reproduces in a terminal and always reproduces under CI's output capture.

Finally, consider that the hang may be **external contention rather than a bug in your code**. If your integration tests touch a shared database, a shared Redis, or a shared broker, a 5% failure rate is roughly what you'd expect from "another PR's job happened to be running at the same time." The same goes for a single bad runner in the fleet, or a leftover container from a previous job squatting on a port.

## The instrument that ends the argument

Rather than reasoning further from the log, make the hung process describe itself. Add a suite-level watchdog set below the CI job's own timeout, and have it dump, as uploaded artifacts, the full stack of every thread or goroutine or pending async operation (`SIGQUIT` for JVM and Go, `faulthandler` or a `py-spy dump` for Python, `--inspect` plus a heap/async dump for Node), the socket table from `ss -tanp`, the pool's own metrics for in-use, idle and waiting counts, `ps` output showing whether the process is burning CPU or sitting at zero, and — most valuable of all — `pg_stat_activity` joined against `pg_locks` showing each backend's state, wait event, and current query.

One such dump discriminates between everything above in about a minute of reading. Threads parked in `pool.acquire()` while every connection is checked out means the pool theory is right, and the checkout stacks tell you which code path leaked them. An established socket with a thread blocked in `read()` and a database that shows no corresponding active backend means the connection is a zombie and you have a timeout/keepalive problem. A backend sitting `idle in transaction` while another waits on a relation lock means the leaked-transaction story. All threads runnable but nothing progressing means starvation. Zero CPU versus pegged CPU alone splits "blocked on something" from "spinning in a retry loop."

## Cheap experiments while you build that

Set timeouts on every waiting primitive first, independent of which theory you favor: a pool acquisition timeout, a client-side socket timeout, and on the database side `statement_timeout`, `lock_timeout`, and `idle_in_transaction_session_timeout`. None of these fix anything, but they convert a silent 1-in-20 hang into a 1-in-20 *failure with a stack trace at the point of blocking*, which is most of the diagnostic value of the watchdog for a fraction of the work.

Then bisect the axes that differ between CI and your machine, one at a time. Run the suite with parallelism forced to one — if the hang survives, workers aren't fighting each other and you can drop a whole family of hypotheses. Fix the test-order seed across repeated runs and see whether the hang follows the order or scatters independently of it, since a leak-based hang should correlate with cumulative test count while a race should not. Instrument the pool to emit in-use counts after each test and look for a monotonic climb, which proves or kills the leak theory without needing a hang at all. Check whether hanging runs cluster on particular runners or overlap in wall-clock time with other jobs against the same shared services. To attack the "never locally" part directly, adopt CI's traits one at a time: run in a container with `--cpus=0.5`, pipe output to a file rather than a TTY, and use the same worker count — the CPU limit plus output redirection combination reproduces a surprising share of CI-only hangs.

Given the scatter in your hang locations, I'd put the leaked-transaction/lock-wait story and shared-resource contention ahead of pool exhaustion in prior probability, with CPU-quota starvation close behind. All three are cheap to distinguish once the hung process is dumping its own stacks, so the watchdog is worth building before anyone changes pool sizing on a hunch.
