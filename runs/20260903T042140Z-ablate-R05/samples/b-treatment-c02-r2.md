Three facts in your description carry most of the diagnostic weight, and it's worth separating them before reaching for any specific cause. The suite hangs rather than fails, which means something is blocked waiting on an event that will never arrive, and somewhere in the stack a timeout is missing or infinite. The location moves between runs, which argues against a single defective test and toward either shared state that leaks across tests or a timing window that opens sporadically. And it only happens in CI, which points at the axes where CI actually differs from your laptop: parallelism and core count, cgroup CPU and memory limits, container networking, and service dependencies that live at the end of a bridge network instead of on localhost.

Connection pool exhaustion is a reasonable guess but it's the guess everyone makes, because it's the one everybody has been burned by once. It has a specific signature you can check against your data. A leak accumulates, so the hang should cluster in the later part of the run and correlate with the cumulative number of tests executed rather than with which test it lands on, and raising the pool size should push the hang later without removing it. It also requires that your pool has no acquire timeout configured, because a pool with a two-second acquire timeout produces a loud error and a stack trace rather than silence. That last point is a thirty-second falsification: read the pool config, and if there's a finite acquire timeout on it, the hypothesis is dead and you've saved yourself a week.

The alternatives worth holding in mind fall into a few families. Mutual blocking is the first: two parallel workers touching the same rows or tables, one of them leaving a transaction open on an error path so it sits idle-in-transaction holding a lock, while another blocks forever on a truncate or an alter because no lock timeout is set. Most engines detect true deadlock cycles and abort, but a plain lock wait with no timeout hangs indefinitely, and which test gets caught depends on interleaving, which explains the moving target precisely. A close cousin is thread pool starvation, where a bounded executor runs tasks that block waiting on other tasks needing the same executor, something that only bites once concurrency happens to reach the boundary. Lost wakeups are the second family: a condition signalled before the waiter began waiting, an unawaited promise, or, in integration tests specifically, one test consuming a message that another test was waiting for because they share a queue or topic without per-test namespacing. The third family is blackholed I/O, and it deserves particular attention given the CI-only pattern. On your laptop you talk to a service on localhost, so when the peer dies you get an immediate connection reset. In CI, across a bridge network or NAT to a service container that was OOM-killed or restarted, packets go into a hole and a client with an infinite read timeout waits until the job is cancelled. The fourth is the harness itself rather than your code: a child process whose stdout pipe fills its buffer and blocks on write while the parent waits for exit without draining it, or a leaked non-daemon thread that keeps the runner alive after the last test finished. Both are worth ruling in or out early by establishing whether the hang is inside a test or after the last one reported. Finally there's infrastructure, meaning CPU throttling under a cgroup quota, memory pressure turning into a GC death spiral that looks like a stall, a preempted spot instance, or log streaming stalling while the job underneath is fine.

The way to tell these apart is to stop trying to reproduce it and instead make the next occurrence self-diagnosing, because at one in twenty you'll get an instance within a day or two of merging instrumentation. Set a job timeout comfortably below the CI hard limit, and on expiry, before anything is killed, capture a full thread or goroutine dump of the test process, the state of every socket via `ss -tanp`, open file descriptors, and on the database side the contents of `pg_stat_activity` including state, wait_event and transaction start time, plus `pg_locks` joined to show blocked and blocking pairs. Add broker queue depth and consumer counts if a broker is involved, cgroup throttling counters, and `dmesg` for OOM kills. The mechanism differs by runtime: SIGQUIT for a JVM or Go process, `py-spy dump` against the pid for Python, `--report-on-signal` for Node. That single artifact discriminates almost everything above. Every thread parked in acquire means the pool. One thread in a socket read on a connection whose peer is gone means a missing timeout and probably a vanished container. An idle-in-transaction session with a waiter behind it means the lock story. Nothing running anywhere and a full pipe means the harness.

Alongside that, a few cheap experiments narrow the space without waiting. Run the integration suite with a single worker over enough runs to matter; if the hang disappears, it's cross-test interference rather than a per-test defect, and doubling the workers instead should make it more frequent, which also gives you a faster feedback loop. Add short timeouts everywhere you can, on socket reads, pool acquisition, statements and lock waits, since converting a hang into an error with a stack trace at the point of blockage costs you nothing and buys evidence on every future occurrence. Log a timestamped line at each test's start and end so you can see the run position of the hang and check whether it drifts later as the suite grows. And run the actual CI image locally, pinned to one or two cores with the same memory limit and the same service-container topology, because "never hangs locally" usually stops being true once the container network and the resource limits are part of the picture, and identifying which of those two restores the failure is itself the answer. Worth checking in parallel whether the failures correlate with a particular runner host, shard, or time of day, since a single sick machine or a noisy neighbour is a common and easily missed explanation for a stable one-in-twenty rate.
