I'd push back on this one, because the specific design has a correctness and security failure in it, not just a performance disappointment.

The authorization part matters most. If your queries use bind parameters, the SQL string is identical for every user: `SELECT ... FROM orders WHERE user_id = $1`. Keying the cache on that string alone means the first user's rows are served to the next user who runs the same query, and your row-level authorization is bypassed for everything the cache holds. If instead you interpolate literals into the SQL text, the key does vary per user and the cache is safe, but then very little repeats and you've spent memory for a near-zero hit rate. Depending on which of the two you're doing, the design is either unsound or ineffective, and with most ORMs and drivers it will be the first.

Second, eight worker processes means eight dictionaries with no way to invalidate one another. At 400 writes a minute, a write handled by worker 3 leaves the other seven serving pre-write data with no expiry, and because the load balancer moves a user between workers, they see the new value and the stale one alternately as they reload. Non-deterministic staleness is harder to debug, and harder to explain to a user, than a slow page.

Third, a global dict with no eviction and no TTL is an unbounded leak: every distinct query string pins its result set for the life of the process.

The thing to do first is measure rather than cache. `pg_stat_statements`, the slow query log, or whatever your APM gives you will usually show that the cost is a missing index or an N+1 query inside a loop. Both are cheaper to fix than a cache layer and neither costs you any correctness.

After that, the safe version of your idea is request-scoped memoization: a dict attached to the request object, keyed on the query plus its parameters, discarded when the response is sent. One request is one authorization context and, inside a transaction, one consistent snapshot, so there is no leak between users and no cross-process invalidation problem because nothing outlives the request. This captures the repeated-identical-query pattern, which is often most of the real duplication.

If you still want caching across requests, put it in Redis or memcached so the eight workers share one copy and one invalidation path. Key on the full parameter set plus the authorizing principal, not the SQL text; keep TTLs short enough that a missed invalidation self-heals; and delete keys explicitly in the write paths that touch them. Point it at data that is expensive, shared, and slow-changing, such as reference tables, configuration, and precomputed aggregates, rather than at per-user row reads, where the hit rate is lowest and the cost of a keying mistake is somebody else's data.
