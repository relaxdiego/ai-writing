Your skepticism is reasonable, though pool exhaustion is at least the right *shape* of hypothesis. The most informative fact you have is that the hang lands on a different test each time, which almost rules out a bug in the test that hangs. A test that deadlocks on its own logic hangs in the same place every time. A varying victim means something accumulates across the run, or some race resolves badly, and whichever test is holding the bag when the threshold is crossed takes the blame.

The accumulation story is the family pool exhaustion belongs to, and it generalises: a test errors out on a path that skips cleanup, a connection or transaction or file descriptor or worker thread is never returned, and the pool shrinks run by run until a checkout blocks forever because nobody set an acquire timeout. The same shape covers leaked database transactions specifically, which are nastier than plain exhaustion: a session left idle in transaction holds row or table locks, and the next test that touches those rows waits on `lock_timeout`, which in Postgres defaults to unlimited. Under CI's different timing and ordering, a different test gets caught each run.

The second family has nothing to do with your code's resource discipline and everything to do with CI's network. A blocking read on a socket whose peer has quietly vanished will wait forever unless something imposes a deadline. Containerised CI is unusually good at producing vanished peers: NAT conntrack entries expiring on idle connections so subsequent packets are blackholed rather than reset, a service container OOM-killed mid-suite, a DNS lookup stalling, or a connect to an external dependency with no connect timeout. This explains "never locally" far better than a leak does, since your laptop has a loopback interface and no NAT table in between.

Third, there are missed-wakeup races. Any test that registers a listener and then waits for an event has a window where the event can arrive first; if it does, the wait never completes. CI machines are usually slower and more contended than your laptop, so orderings that never occur locally occur at some low rate there. A 5% failure rate across a few hundred tests is a very small per-test window, which is exactly what this kind of race looks like.

Finally, be suspicious of the observation itself. If your runner buffers output, the last test name printed is not the test that hung; it is the last one that flushed. Relatedly, a subprocess whose stderr pipe fills while nobody drains it will block on write forever, and which test triggers that depends on which one happens to be verbose that run.

To tell these apart, stop reasoning about them and capture state at the moment of the hang. Set a per-test or per-suite timeout comfortably below the CI job timeout, and on expiry dump stacks for every thread or task, the pool's active/idle/waiting counts, `ss -tanp` for socket states, open fd count, and on the database side `pg_stat_activity` and `pg_locks` including `wait_event_type`. One such dump usually ends the argument: a stack sitting in `pool.acquire` is exhaustion; a stack in a socket read with no live peer is the network story; a session showing idle in transaction while another waits on a lock is a leaked transaction; all threads parked on your own mutexes is a genuine deadlock.

Two cheap experiments are worth running while you wire that up. Shrink the pool to one or two connections: if the hang rate jumps toward every run, your colleague is right and you've confirmed it in an afternoon; if the rate is unchanged, exhaustion is essentially falsified. Then run the suite with a single worker: if the hang disappears, the cause is cross-test interference or contention, and you can bisect by replaying the same random seed and trimming the prefix until the hang stops following a particular predecessor test.

Independently of diagnosis, put deadlines on everything that can block: pool acquire, socket connect and read, `statement_timeout` and `lock_timeout` on the database, and the test runner's own per-test limit. Timeouts convert an opaque hung job into a stack trace at the point of blocking, so the next occurrence tells you what the previous twenty could not. Reproducing locally becomes plausible too once you constrain the environment the way CI does, running the suite with `--cpus=1` and a bit of injected latency and loss.
