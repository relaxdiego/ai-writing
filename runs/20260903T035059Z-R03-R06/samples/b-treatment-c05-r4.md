I did not find a definitive cause. What the run history does give is a fairly sharp constraint on where to look, so here is what it rules in and out.

The failures are not a continuum of slightly-short runs. They are bimodal: roughly 48k rows in about fifteen minutes, or roughly 22–24k rows in about seven. Within the eight runs I pulled, the short ones fall on 23, 26 and 29 August, an exact three-day spacing. I only read eight of the thirty recorded runs, so that periodicity may be coincidence, and confirming it against the full thirty is the cheapest thing that would move the diagnosis. A strict three-day cadence would point at something else on a schedule (an upstream feed, a partitioned source that rotates, a competing job holding a lock) rather than at a transient fault; an irregular pattern would point back at the retry path added in 9d02e1e.

The duration scales with the row count rather than staying flat, which suggests the pipeline genuinely processed less work rather than fetching everything and discarding half of it late. That places the loss upstream of the write loop, in `fetch_events` or in what it is reading, and `run` itself has nothing in it that could halve the output. I did not read `fetch_events`, and the retry commit is the only recent behaviour change touching that path; the specific thing worth checking there is whether a retry restarts pagination from a fresh cursor or swallows an error mid-stream and returns the partial result it already has, since either would produce a truncated fetch that still exits cleanly and records `ok`.

One observation argues against the obvious window explanation. `window_start` is `last_success_at`, so a run that starts at 02:00 always covers about twenty-four hours regardless of what happened the night before, and if events had merely arrived late, the following run's window would still include them and would show roughly 72k rows. It shows 48k. The missing rows are never recovered, so they are being dropped rather than deferred, and window arithmetic can only explain the halving if `last_success_at` is being written from something other than the prior run's start, or if it and `now` are resolved in different timezones. Both are worth confirming in the code that updates `job_runs`, which I did not open.

Two things I cannot see from the repository at all. The first is what happens upstream on 23, 26 and 29 August, which only you can check against your ingestion schedule; if some source feed or export runs on a multi-day cadence, that alignment is the answer and the code is innocent. The second is where `rows_written` comes from: if it is incremented in the write loop rather than read back from the committed table, it measures intent rather than result, and a short value could in principle coexist with a full fetch.
