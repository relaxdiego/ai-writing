Caching is a reasonable instinct, but keying on the SQL string is the one detail that turns this from a speedup into a data leak. If your queries are parameterized, which they should be given the row-level authorization lives in the WHERE clause, then the SQL text is identical for every user and only the bound parameters differ. Two users issuing the same logical query produce the same cache key, so whoever gets there first populates the entry and everyone else reads their rows. The authorization check still runs; it just runs on a request whose answer was already decided by someone else's session. If instead you interpolate the user id into the SQL text, the keys separate correctly, but then you have string-built SQL, which is a worse problem than the one you started with.

The eight workers cause a second, independent failure. A module-level dictionary is per-process, so you get eight caches that never learn from each other: your hit rate is a fraction of what you are budgeting for, you pay for eight copies of the same rows, and each process can hold a different stale version of the same row. A user who writes and then reloads will see the new value or the old one depending on which worker the load balancer happens to pick, and refreshing will flip it back. Read-after-write consistency is the kind of bug that gets reported as "the site randomly loses my edits."

At 400 writes per minute, roughly seven a second, staleness is not an edge case either, and a plain dictionary with no eviction grows until the worker is killed.

The version of this that works keeps the idea and fixes the key and the location. Build the key from the query text plus the full parameter tuple plus the authenticated principal, hashed; put the cache in Redis or memcached so all eight workers share one view; give every entry a short TTL as a backstop, in the range of thirty to sixty seconds; and on write, invalidate explicitly rather than waiting for expiry, which is easiest to get right with a per-table version counter folded into the key so that any write to a table retires every cached read of it at once. Bound the whole thing with an eviction policy so memory is a configured number rather than an emergent one.

Before building any of that, it is worth knowing what is actually slow. Four hundred writes a minute is a light load, and applications at that volume are usually slow because of N+1 query patterns in a loop or a missing index on a column that appears in a hot WHERE clause. Caching in front of either of those buys a smaller improvement than fixing them and permanently adds an invalidation surface to every future change. A few minutes with the slow query log or an APM trace of your worst endpoint will tell you which problem you have, and if it turns out to be a genuinely expensive read that is repeated across users with the same authorization scope, the shared keyed cache above is exactly the right tool for it.
