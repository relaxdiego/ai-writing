## Start by reading the symptom pattern quantitatively

"Always a different test" is the most informative thing you've told me, and it's worth pushing on before picking a mechanism. If your integration suite has, say, 500 tests and 5% of runs hang, the per-test hazard is roughly one in ten thousand — the signature of a narrow race window that any test can happen to land in, rather than a defect belonging to a particular test. Two very different mechanisms produce that signature, though, and they make opposite predictions about *where* in the run the hang lands. A leak-and-threshold mechanism (the pool exhaustion story) predicts clustering: connections accumulate, and the run dies once the count crosses the pool size, so the hang should appear late and at a roughly reproducible test index even though the test name varies. A race predicts a uniform distribution across the run. Before anything else, go back through your archived CI logs and record, for each hang, how many tests had completed. If the answer is "always around test 380–420," believe the exhaustion theory; if it's scattered from test 12 to test 490, it's close to dead.

One caveat that can rescue the exhaustion hypothesis from an apparent scatter: if your runner randomizes test order per run, the accumulation rate varies run to run and the threshold crossing smears out. Check whether ordering is shuffled and whether the seed is logged.

The other thing worth extracting from existing logs is whether the hang is really inside the test body. In a lot of suites the last-reported test name is just whoever was holding the baton when a *shared fixture* stalled — setup, teardown, a transaction rollback, a truncation between tests. If you find the hangs are always during teardown or always between tests, the surface area collapses from five hundred tests to about twenty lines of fixture code.

## Mechanisms that fit "CI only, intermittent, position-independent"

Cross-worker database lock contention is my first guess. CI almost certainly runs the suite with parallel workers while you run it single-threaded locally. Worker A holds an open transaction touching a table; worker B issues a `TRUNCATE` or a DDL statement in its own setup, which needs `ACCESS EXCLUSIVE` and queues behind A; A is meanwhile waiting on something B holds, or simply on a slow query. Postgres's deadlock detector catches true cycles, but a plain lock wait with no `lock_timeout` set blocks forever, and the default `lock_timeout` is zero, meaning infinite. Advisory locks used for test isolation produce the same failure with none of the deadlock detection.

Missing timeouts are the second, and they're a precondition for almost every other cause rather than a competing explanation. A hang requires that *something* is willing to wait forever. Locally, over loopback, nothing ever waits long enough for you to notice the absence of a deadline; in CI, a connection to a container that stalled during startup or lost a packet will sit in `recv` indefinitely if no socket timeout, statement timeout, or client-level deadline is configured. Auditing every layer for a deadline is worth doing on its own merits, because it converts an undiagnosable hang into a failing test with a stack trace.

Undersized concurrency pools explain the "never locally" part better than almost anything else. Your laptop has eight or twelve cores; the CI container probably has two, possibly under a cgroup CPU quota. Any pool sized from `cpu_count()` shrinks accordingly, and code that blocks a pool thread while awaiting work queued on that same pool deadlocks only when the pool is small enough that all workers get blocked simultaneously. The same applies to async runtimes where a synchronous call blocks the event loop thread.

A worker being OOM-killed is worth ruling out early because it's cheap to check and produces a hang rather than an error. The coordinator process waits forever for a result from a worker that no longer exists. Memory pressure varies with scheduling and with what else shares the runner, which gives you exactly a low-single-digit percentage failure rate. Look for exit code 137, check `dmesg` for the OOM killer, and log peak RSS.

Pipe buffer deadlock is the classic CI-only hang: a subprocess you spawn (a container, a helper service, a migration tool) writes to stderr, nobody drains the pipe, the 64 KB kernel buffer fills, and the child blocks on write while the parent blocks waiting for the child to exit. Interactive terminals drain continuously, so this is invisible locally and reproducible only under captured output.

Finally, consider shared infrastructure. If two concurrent CI jobs point at the same database, Redis, or message broker, the hang rate is a function of job overlap, which would sit naturally around one in twenty. Correlate your hang timestamps against other jobs running on the same runner or against the same backing service.

## How to tell them apart

The single highest-value change is to make the hang produce evidence instead of a SIGKILL. Right now the CI job timeout kills the process and you learn nothing. Set a runner-level timeout comfortably below the CI job timeout, and on firing, dump every thread's stack — `faulthandler.dump_traceback_later` or `py-spy dump --pid` for Python, `jstack`, `SIGQUIT` for Go, `kill -SIGUSR1` for Node. In the same handler, capture `SELECT pid, state, wait_event_type, wait_event, query, xact_start FROM pg_stat_activity`, the blocking-pid join over `pg_locks`, `ss -tan | sort | uniq -c` for socket states, an fd count from `/proc/self/fd`, and `free -m` plus `dmesg | tail`. That one artifact discriminates nearly the entire list above in a single shot: threads parked in `pool.acquire` means genuine exhaustion, a thread in `recv` on an established socket means a missing timeout, `pg_stat_activity` showing `Lock`/`transactionid` waits means cross-worker contention, and a live parent with a vanished child means the OOM or IPC path.

Alongside that, a few experiments are cheap. Run CI with `-j1` — if the hang disappears across fifty runs, it's cross-worker contention rather than a per-test leak. Run the suite locally under `docker run --cpus=2 --memory=2g` with output piped rather than attached to a TTY, in a loop; "never locally" very often means "never on ten cores with a terminal attached," and reproducing it on your own machine is worth more than any amount of reasoning about it. Instrument the pool's checked-out count at every test boundary and assert it returns to baseline, which proves or kills the leak hypothesis in one clean run without waiting for a hang. Set `lock_timeout` and `statement_timeout` on the test database connection, since a hang that becomes a loud lock-timeout error tells you the offending statement and the blocker for free.

On the pool exhaustion suggestion specifically, it deserves partial credit even if it's wrong as stated. If someone observed an empty pool, that observation is probably accurate — but connections don't evaporate, they're held by callers that are themselves stuck, so exhaustion is usually the second domino rather than the first. Even confirming it would leave you asking what those connections were waiting on, which lands you back in the same list.
