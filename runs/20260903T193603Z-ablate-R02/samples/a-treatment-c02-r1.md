Your skepticism is well placed, though not for the reason you might think. The "always at a different test" detail feels like it rules out pool exhaustion, but it doesn't: when a bounded resource leaks, the hang surfaces at whichever test happens to draw the last one, which moves around with test order and timing. A hang localizes at the consumer, not the producer. So that observation is weak evidence and rules out almost nothing. What it does rule out is a plain bug in one specific test.

The more informative facts are the 5% rate and the fact that it never happens locally. Together those point at something that is a race or a rare interleaving, amplified by conditions CI has and your laptop doesn't: fewer cores, cgroup CPU throttling, real container networking instead of loopback, non-TTY stdout, and possibly other concurrent jobs sharing a database.

Here are the candidates I'd actually weigh. Resource exhaustion with no acquire timeout is one: not just DB connections but HTTP client pools, worker threads, semaphores, file descriptors. Anything with a bound and an unbounded wait. Second, and in my experience the most common cause of this exact signature, is a socket read with no timeout against a connection that has silently gone away. On loopback a dead peer produces an immediate RST; across a container bridge or a NAT gateway an idle connection can be dropped from a conntrack table with nothing sent to either side, and the next read blocks forever. Pooled connections make this worse, because an idle pooled socket is exactly the one that gets reaped, and it hangs on first reuse unless you have keepalives or a validation query. Third, a genuine database-side wait: a test that leaves a transaction open holding a lock, and a later test doing a truncate or a DDL that queues behind it. That looks like an application hang but the whole story is visible server-side. Fourth, pipe backpressure: a subprocess writing to a stdout pipe nobody drains fills the 64KB buffer and blocks. Locally you have a TTY or less verbose output, so you never reach the threshold. Fifth, event-loop or thread-pool deadlock, the sync-over-async kind, where a task waits on work queued behind it in a bounded executor. Sixth, cross-job interference if your CI shares one test database or Redis between concurrent builds.

The way to tell these apart is to stop reasoning about which is likeliest and make the hang produce evidence instead of a timeout kill. That is the single highest-value change. Set your job's own timeout below the CI platform's hard timeout, and on firing, dump: full thread stacks (jstack, py-spy dump, SIGQUIT, whatever fits your runtime), `ss -tanp` for socket states and queue depths, `ps -eLf`, and on the database side `pg_stat_activity` including `wait_event` and `wait_event_type` plus `pg_locks`. Take that dump three times, ten seconds apart. Three identical stacks is a hang; three different ones is slowness. That one artifact usually ends the investigation outright, because a thread parked in `pool.acquire` and a thread parked in `socket.recv` are not the same picture, and neither resembles a backend sitting in `Lock:transactionid`.

Alongside that, a handful of experiments discriminate cheaply:

- Shrink the connection pool to one or two. If the pool theory is right, the hang rate should jump sharply and move earlier in the run. If nothing changes, the theory is dead.
- Set every timeout that exists: socket connect and read, HTTP client, pool acquire, `statement_timeout`, `lock_timeout`. A hang that converts into a fast error names its own cause in the message. Keep these in CI permanently regardless of what you find.
- Run CI with parallelism forced to 1. If the hangs stop, you have a concurrency or shared-state problem; if they persist, it is environmental, which points at the network, pipes, or throttling.
- Log the ordered list of completed tests on every run. Then check what the stall position correlates with across failures: test count suggests a leaking bounded resource, elapsed wall time suggests an idle-connection reaper or throttling, cumulative output volume suggests the pipe. Also look at the predecessor of the stalled test rather than the stalled test itself, since a common predecessor across several failures is the real signal.

For local reproduction, the missing ingredients are usually resource limits and real networking. Run the suite in a container with `--cpus=1` and a memory cap matching the runner, with services on a bridge network rather than localhost, output redirected to a pipe rather than a terminal, and the same parallelism as CI. Then loop it. At one in twenty you need roughly twenty runs per hit, so an overnight loop should give you several, and a locally reproducible hang you can attach a debugger to is worth more than any amount of further theorizing.

If I had to bet before seeing a thread dump, I'd put the money on a missing socket read timeout over a connection killed by network middleware, with pool exhaustion as the second-order effect rather than the cause: the stuck reader holds its connection forever, and the pool drains behind it. That would explain why the person who suggested the pool saw real evidence for it, and why fixing the pool size wouldn't have helped.
