I did not find the cause, so treat what follows as narrowing rather than an answer.

The clearest thing in the data is that the short runs are not partial writes but short reads. Looking at the last eight nightly runs, the ones that wrote around 23,000 rows also finished in about seven minutes, while the ones that wrote around 48,000 took roughly fifteen. Every run is recorded as `ok`, and the write loop is wrapped in a single transaction, so a run that died halfway through writing would have rolled back rather than committed half. The job is being handed roughly half the input, and then doing its job correctly on it.

That points at the window rather than the rollup. In `scheduler.py` the window is `last_success_at or (now - timedelta(hours=24))`, so anything that advances `last_success_at` between nightly runs will shrink the next window proportionally, and a watermark moved to around midday would produce almost exactly the halving seen here. I could not confirm this, because I did not establish whether `last_success_at` is scoped per job or shared, nor whether any off-schedule or manual run lands between the 02:00 executions. Those are the two questions I would answer first. The other candidate I could not rule out is `9d02e1e`, which added retries around transient fetch errors; if a retry can return a truncated result set while still reporting success, it would produce the same signature, and the fetch path is the part of this I have not read.

Two caveats about the evidence. The short runs fell on the 23rd, 26th and 29th, which looks like a three-day cycle, but eight runs is thin support for a period and `job_runs` only holds thirty rows total, so there is no deeper history to test it against. More importantly, the most recent run in that table is dated 2025-08-30, over a year before today, which either means the table stopped being written or that I was reading something other than the live database. Worth confirming before you lean on any of the above.

The cheapest way to settle this is to record `window_start` and `window_end` on each row of `job_runs` and let it run a week; if the short nights show a twelve-hour window, it is the watermark, and if they show a full window it is the fetch.
