Caching will help, but keying on the SQL string is the one detail that breaks under your constraints, and it breaks in a different way depending on how you build the queries. If you use bound parameters, which I assume you do, the SQL text is byte-identical for every user; the user id lives in the parameters, not in the string. Your row-level authorization then stops doing anything: the first user to run a given query populates the entry, and every user after them reads that user's rows straight out of the dictionary. It is a cross-tenant data leak, and it is the kind that tests rarely catch, because a test usually runs one query as one user. If instead you interpolate the id into the SQL text, the keys become distinct and the leak goes away, but so does most of the speedup. Entries are now per-user, the hit rate falls to whatever a single user's repeat traffic looks like, and the dictionary grows as users times distinct queries with nothing ever evicting it, in all eight processes at once.

Writes are the second problem. At 400 a minute you are mutating something about seven times a second, and a key that is just SQL text gives you no way to work out which entries a given INSERT or UPDATE invalidated. That leaves flushing the whole dictionary on every write, in which case it is empty most of the time, or not invalidating at all and serving stale rows indefinitely.

The eight workers compound both. Each process has its own dictionary, populated at different moments and stale in different ways, and the load balancer sends consecutive requests from the same user to different workers. A user who posts something sees it, refreshes and sees the old state, refreshes again and sees the new one. Read-your-writes is what breaks first and what they will report.

What I would build instead keeps the idea and fixes the three things. Move the cache out of process into Redis or memcached so all eight workers share one view and a single invalidation is seen by everyone. Key on the query text plus the bound parameter values plus the authenticated user or tenant id, so identity is part of the key rather than something the WHERE clause is quietly expected to handle. Give every entry a short TTL, five to thirty seconds, so a stale entry cannot outlive a missed invalidation forever. Tag entries with the tables they read, so a write to `orders` drops the order entries rather than the whole keyspace. Bypass the cache inside transactions and on the read that immediately follows a write from the same user.

Before any of that, it is worth confirming that query execution is actually where the time goes. `pg_stat_statements` (or the equivalent for your database) and EXPLAIN on the two or three slowest endpoints will tell you in an afternoon whether you are looking at a missing index or an N+1 in an ORM loop, and caching a query that runs a hundred times per request only multiplies work you should not be doing. Where caching genuinely is the answer, the layer above SQL is usually the easier one to reason about: a computed result or a rendered fragment already knows whose data it holds, so identity is explicit in the key instead of buried in a WHERE clause. Whatever TTL you settle on is also the window during which a revoked permission still grants access, so for anything permission-sensitive keep it at the short end.
