Move the files to a storage service and keep a key in your database.

Both options unblock the three machines, so the deciding factor is what each one costs you afterwards. A shared disk is the smaller change today: mount the same volume on all three, change nothing in the code, done by Friday. What you have bought is a new piece of infrastructure that your team of four now operates. A network filesystem is a single point of failure that all three web servers depend on simultaneously, and its failure mode is unpleasant in a specific way: when an NFS mount hangs, processes touching it go into uninterruptible sleep, where they cannot be killed and the machine's load average climbs while nothing is happening. You get to learn this during an incident. Managed options like EFS soften it but do not remove it, and none of them are things a four-person team should want to hold opinions about.

Object storage also solves two problems you did not ask about. The first is durability. Ask yourself what happens today if that machine's disk fails, and whether the answer is a real backup or a volume snapshot somebody set up once. S3 and its equivalents give you eleven nines of durability, versioning, and lifecycle rules without you doing anything. The second is serving. Once files live in object storage you can hand the browser a short-lived presigned URL and let the bytes go direct, which takes file transfer off your application servers entirely. On a shared disk every download still occupies a web worker for its duration.

Cost runs the same direction. 200 GB on S3 standard is roughly $5 a month and your 10 GB of growth adds about 23 cents a month to that; the same 200 GB on EFS is about $60 a month. Egress and request charges will exceed the storage line for both, but the storage comparison is not close, and neither number is large enough to matter to the decision.

Shared disk is the right answer in a narrower set of cases than people expect. If your code hands file paths to external tools (ImageMagick, ffmpeg, a document converter), or seeks randomly inside large files, a filesystem is genuinely what you want. Even then the usual fix is to download to a temp file and delete it after. The stronger case is a hard constraint: on-premises deployment, or data residency rules that rule out a cloud provider. Self-hosted MinIO covers most of that while keeping the same API, so you would still be writing against the object storage interface.

One detail worth getting right at the start: store a key like `uploads/2026/09/<uuid>.jpg`, not a full URL. Buckets get renamed, regions change, a CDN gets put in front. A stored absolute URL bakes today's topology into 200 GB worth of rows. Store the key, the content type, the byte size, a checksum, and the user's original filename, and build the URL at read time.

The migration itself is bounded work:

1. Put a storage interface in front of every filesystem call you currently make, with a local-disk implementation behind it. Ship it with behaviour unchanged. This is the step that costs real effort, and you need it whichever backend you pick.
2. Add the object storage implementation. New uploads write there and record a key; existing rows keep their old path. Reads use the key when present and fall back to disk when it is null.
3. Backfill. Walk the rows without keys, upload, verify the checksum, set the key. Make it batched, idempotent and resumable. 200 GB is an afternoon, not a project.
4. When no rows lack a key, delete the fallback branch and the old directory, after a snapshot and a decent waiting period.

On the operational side, keep the bucket private and serve reads through presigned URLs with a short expiry. These are people's personal documents, and a public bucket with unguessable keys is not access control. For writes, the simplest start is to keep uploads flowing through your application as they do now and move only reads to presigned GETs; direct browser-to-bucket uploads are worth doing later for large files, but they mean the client writes to your bucket before your code has validated anything, so you need a post-upload check on size and sniffed content type.

Two things will leak if you ignore them. An upload that succeeds while its database transaction fails leaves an object nothing references, so write those to a `pending/` prefix with a lifecycle rule that expires them, or run a periodic reconciler. And on delete, remove the row first and sweep the object asynchronously, so a storage hiccup does not fail a user's request. For local development and tests, run MinIO in your compose file or point the same interface at its local implementation.

If the three-machine cutover lands before this work is finished, a shared mount as an explicitly temporary bridge is a reasonable thing to do, as long as somebody owns the date it gets removed. Sticky sessions are not a substitute: they break the moment a machine drops out or one user needs to read a file another user uploaded.
