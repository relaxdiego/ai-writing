Start with the part that is a security bug rather than a performance question. If your queries go through an ORM or any driver using bound parameters, the SQL string is a template: `SELECT ... FROM invoices WHERE org_id = ? AND status = ?`. Every user in the system produces the identical key, so the first request populates the entry and everyone afterwards reads that user's rows. Your row-level authorization lives in the WHERE clause, which means it lives in the parameters, which is exactly the part your key throws away. The same hole opens from the other direction if authorization is enforced by Postgres RLS or a `SET ROLE` on the connection, because then the identity never appears in the query text at all. Only in the case where you interpolate user IDs as literals does string keying separate users correctly, and there the cache fragments per user so the hit rate you were hoping for mostly disappears.

The eight workers break the other half of the idea. Each process gets its own dictionary, so a given query has to miss eight times before it is warm everywhere, and more importantly there is no path for an invalidation to travel. A write served by worker 3 clears worker 3's entry and leaves the other seven holding the old value, so the stale read appears or does not appear depending on which worker the load balancer picked. Users report it as "the page sometimes doesn't update, but it fixes itself if I refresh a few times," which is close to unreproducible. An unbounded dictionary also never evicts, so each of the eight processes grows toward whatever your distinct query volume is until the box starts swapping.

At 400 writes a minute you are mutating something roughly every 150 milliseconds, so for any table on the hot path a cache without real invalidation is wrong most of the time it is consulted. A TTL bounds the damage but does not fix read-your-own-writes, and that is the staleness users actually notice: they submit a form, land back on the list, and their change is not there.

Before caching anything, find out what is slow. Turn on `pg_stat_statements` or the slow query log and look at total time rather than per-call time, because the usual culprit is a fast query run 300 times per request through a lazy-loaded relation. N+1 patterns and a missing index on a foreign key account for most of what feels like "the database is slow," and fixing those costs you nothing in correctness.

There is a version of your instinct that is safe, which is memoizing within a single request. Hang the dictionary off the request context, key it on the query plus its bound parameters, and discard it when the response is sent. One request has one principal, so there is no cross-user leak, and nothing can go stale in the tens of milliseconds it lives. That alone collapses duplicate reads inside a request handler.

If you still need a cross-request cache after that, put it in Redis so all eight workers share one view and one invalidation, key it on the query template plus parameters plus the authorization principal, or better, cache the domain object above the SQL layer where the identity is explicit rather than inferred. Attach tags on write so that saving an invoice drops the entries derived from it, give it an LRU bound and a maximum size, and keep the paths where a user reads back their own write off the cache entirely.
