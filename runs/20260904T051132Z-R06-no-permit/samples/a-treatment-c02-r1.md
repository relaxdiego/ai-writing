Almost certainly EXIF orientation, and the fix is to bake the rotation into the pixels when you ingest the file.

Phone cameras don't rotate the sensor data when you hold the phone sideways. They write the pixels in whatever order the sensor read them and record how the phone was held in an EXIF tag called Orientation. A correct viewer reads that tag and rotates on the way to the screen. The phone's gallery does this, Preview and the Photos app on your laptop do this, and modern browsers do it too when they're handed the original JPEG. So the file is genuinely "sideways" on disk, and everything that looks right is doing a rotation you can't see.

That explains all three of the things you noticed. It isn't every photo, because a photo taken with the phone held in its default landscape position gets Orientation 1, meaning no rotation, and that file survives any pipeline unharmed; only the 90°, 180° and 270° cases (values 6, 8 and 3) depend on the tag. It's deterministic on re-upload, because it's a fixed property of the bytes rather than anything about the network or the session. And it looks correct everywhere except your site, because your site is the one place the image gets re-encoded.

The re-encode is where it breaks. When you resize, crop, generate thumbnails or convert to WebP, most image libraries decode to a raw pixel buffer, do the work, and write out a new file without the original metadata. The pixels are still in sensor order, but the tag that said "rotate this" is gone, so every viewer downstream now faithfully shows you a sideways photo. The same thing happens if you round-trip an image through an HTML canvas for a client-side preview or crop tool.

To confirm it before you change anything, take one of the bad uploads and run `exiftool -Orientation -n bad.jpg` against both the original the user sent and the derivative your server produced. You should see 3, 6 or 8 on the original and either 1 or nothing at all on yours.

The fix is to normalize at the front door: as soon as you accept an upload, apply the rotation to the actual pixels and reset the tag to 1, then let everything downstream treat the image as ordinary top-left data. Every mainstream library has this as a single call.

- **sharp** (Node): `sharp(input).rotate()` with no argument — it reads the tag and applies it.
- **Pillow** (Python): `PIL.ImageOps.exif_transpose(img)`.
- **ImageMagick**: `convert in.jpg -auto-orient out.jpg`.
- **libvips** CLI: `vips autorot in.jpg out.jpg`.
- **Go**: `github.com/disintegration/imaging`'s `AutoOrient`, or decode with `imaging.Open(path, imaging.AutoOrientation(true))`.

Two details will bite you if you get them in the wrong order. Auto-orient must run before any resize or crop, because a 90° rotation swaps width and height: crop coordinates computed against the stored dimensions land in the wrong place, and a "fit within 800×600" step boxes the image to the wrong aspect ratio. And once you've rotated the pixels you must not leave the original tag in the output, or a viewer that honours it will rotate a second time and you'll have traded one class of broken photo for another. The library calls above handle this correctly on their own; the danger is in hand-rolled code that copies metadata across wholesale after processing.

While you're at it, strip the rest of the EXIF block from what you serve publicly. User photos routinely carry GPS coordinates and device serial numbers, and once orientation is baked into the pixels you have no reason to keep any of it on the derivative.

Finally, this leaves you with a back catalogue. Every wrong-looking image already in storage was generated by the old path, so fixing ingest only helps new uploads. If you still hold the originals, re-run the derivative generation over them; if you kept only the processed versions, the orientation information is gone and you'll have to either accept the existing damage or offer affected users a way to rotate their own photos in the UI.
