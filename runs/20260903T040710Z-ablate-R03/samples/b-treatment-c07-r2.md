Caching is the right instinct, but keying on the SQL string is the one dimension that can't work here, and the reason is your row-level authorization. If you use bound parameters, the SQL text is identical for every user; the user id lives in the parameters, not the string. So the first request populates the entry and every subsequent user with the same query shape gets served another user's rows. That's not a performance regression, it's a data breach, and it will look like a cache hit in every metric you have. Interpolating the parameters into the key doesn't rescue it either, because you then depend on the string containing every input to the authorization decision, which fails silently the moment a query filters on something derived from the session rather than passed in, or the moment the database applies a row-level security policy of its own.

The other two facts you gave make the rest of it unworkable even if the key were safe. Eight worker processes means eight independent dictionaries with no way to invalidate each other: a write served by worker three cannot evict the stale entry sitting in worker five, and since the load balancer moves the same user between workers, they will watch a value flip between eight divergent snapshots of the database. At 400 writes a minute that divergence isn't a rare edge case, it's the steady state after a few seconds, and a plain dictionary has no eviction, so the memory grows without bound in all eight processes until something is killed.

Before building anything, find out where the time actually goes. Turn on `pg_stat_statements` or the slow query log and look at total time rather than mean, because the usual culprit is a fast query executed six hundred times in a loop, not a slow one executed once. A missing index or a fixed N+1 typically beats any cache outright and costs you nothing in correctness.

If measurement says you genuinely need a cache, there are two shapes worth having. The narrow, safe version of your idea is a per-request memoization dictionary, created when the request starts and discarded when it ends: one request belongs to one user, so the authorization problem vanishes, the lifetime is milliseconds so staleness is bounded by the request itself, and it collapses N+1 patterns nicely. The broader version needs to be a shared store such as Redis so all eight workers see one copy, with the user or tenant id as an explicit part of every key rather than something you hope the SQL text encodes, a TTL and a size bound, and invalidation driven by writes. Version-tagging is usually less error-prone than enumerating dependencies: keep a generation counter per entity type, include it in the key, and bump it on write so stale entries become unreachable and expire on their own.

Separately from all that, the data that genuinely is safe in a plain in-process dictionary is the read-mostly, non-user-scoped kind: configuration tables, country and currency lists, feature flag definitions. No authorization dimension, few writes, small and bounded. Caching those per process is cheap and correct, and it is often a surprising fraction of the query volume once you go looking.
