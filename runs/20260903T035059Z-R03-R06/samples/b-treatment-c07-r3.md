Caching every query keyed by SQL string has one failure mode that outranks the others: if your queries use bind parameters, the SQL text is identical for every user. The authorization lives in the WHERE clause, but the user id arrives as a parameter, not as part of the string, so `SELECT * FROM invoices WHERE org_id = $1 AND owner_id = $2` produces a single cache key for the whole userbase. The first user to run it populates the entry and everyone after them reads that user's rows. Interpolating values into the SQL text avoids that particular collision but not the general one, because session state that your authorization may depend on (the connected role, a `SET`-based tenant variable, `search_path`) never appears in the string either. Any key for an authorization-bearing query has to include the parameter values and the identity the check is being made against, not just the statement.

The eight workers undercut the plan in a quieter way. A module-level dictionary is per-process, so you get eight independent caches: a given user's repeat request only hits if the load balancer happens to route it back to the same worker, memory use is eight times what you sized for, and a write executed in worker 3 cannot evict anything in the other seven. At roughly 400 writes a minute you are mutating hot rows continuously, so those seven stale copies are the normal case rather than a rare race. A shared store such as Redis gives you one copy that every worker sees and one place to delete from when a write lands.

There is also no eviction in the design. Distinct parameter values are effectively unbounded, so the dictionary grows until the worker is killed, and the workers that have been up longest are the ones that die. Whatever you build needs a size bound and a TTL from the start.

Before any of this, find out what is actually slow. `pg_stat_statements` (or the equivalent slow query log) usually shows that a handful of statements account for most of the database time, and the fix is frequently a missing index or an N+1 loop in the request path, both of which speed things up without introducing a correctness surface. Where caching genuinely helps after that, scope it to an explicit allowlist of read queries whose staleness you have thought about, key each entry on the query name plus its parameters plus the user or tenant, keep it in Redis with a TTL measured in tens of seconds, and delete the relevant keys when a write touches the underlying table. The allowlist is the important part: a blanket cache opts in every query by default, including the ones where a stale read is a wrong invoice total and a crossed key is a data breach.
