Start with the fact that's doing the most work: the hang lands on a different test every time. A bug in one test's logic would cluster. When the victim is essentially arbitrary, the thing failing is machinery shared by all of them, and whichever test is holding the baton when the shared thing wedges takes the blame. Connection pool exhaustion fits that shape, which is presumably why it was suggested, but so do half a dozen other mechanisms, and the useful move is to narrow by shape rather than to argue about which story sounds best.

The other constraint worth taking seriously is that it hangs rather than fails. Something is waiting on something else with no bound on how long it will wait. That is a much smaller set of places than "anything that could go wrong," and it's worth enumerating where unbounded waits actually live in an integration suite. A connection pool with no checkout timeout is one, and note the corollary: if your pool does have a checkout timeout of thirty seconds, then a job that sits for twenty minutes is not pool exhaustion, and you can retire that hypothesis in five minutes by reading the pool config. Database lock waits are a second, and they're nastier than deadlocks because a real deadlock gets detected and one transaction gets aborted with a clear error, whereas a plain lock wait in Postgres blocks forever unless someone set `lock_timeout`, which almost nobody does. The classic version is a fixture doing a `TRUNCATE` or a DDL migration queued behind a session left `idle in transaction` by an earlier test that didn't clean up. Sockets are a third: a connection to a service container that established and then had its peer die without sending a RST will sit in `ESTABLISHED` until TCP keepalive notices, which by default is a couple of hours. Pipes are a fourth, and this one is very specifically a CI bug: a child process writes more than the pipe buffer to stdout while the parent is blocked waiting for the child to exit instead of draining it, and both sides sleep forever. Locally you have a terminal or different verbosity settings and never fill the buffer. In-process synchronisation is the fifth, where a lost wakeup, a promise never settled on an error path, or an `await` on a queue nobody will push to hangs a worker under an interleaving that only a slow, contended machine produces.

Three measurements separate most of that, and they're cheap. The first is whether the machine is busy or idle while it's hung. Idle means genuinely blocked on a wait, which points at the list above; busy means livelock, thrash, or retry storm, which points somewhere quite different. The second is where in the run the hang falls. Anything driven by a leak, including pool exhaustion, file descriptors, and orphaned transactions, accumulates, so the hang should be biased toward the end of the run. If you log each test's ordinal position and the hang positions come out roughly uniform over twenty samples, leak-style exhaustion is in real trouble as an explanation. The third is whether the hanging tests are random or all drawn from one family, such as everything that spawns a subprocess or everything that touches the message broker. People often report "a different test each time" when what's true is "a different test from the same class each time," and that class names the shared machinery directly.

The change that pays for itself before any of this is making the next hang produce evidence. Right now CI presumably hits a job timeout and gets killed with nothing to show. Wrap the integration run in a watchdog set below the CI timeout that, on firing, captures state and then kills things: thread or goroutine stacks from every process in the tree (`SIGQUIT` for a JVM, `py-spy dump --pid`, `SIGQUIT` for Go, `SIGUSR1` plus the inspector for Node), `ps auxf` so you can see the process tree and who is a child of what, `ss -tanp` for socket states and queue depths, `pg_stat_activity` including `wait_event_type`, `wait_event`, `state`, and `query` for every backend, your pool's gauges, and `/proc/pressure/*` if you're on a recent kernel. One captured hang read this way usually ends the investigation outright, because a stack trace showing a thread parked in `read()` on a socket to your Kafka container is not something anyone needs to theorise about.

While you wait for that, you can attack the frequency directly instead of accepting one in twenty. The reason it never hangs locally is a list of concrete differences, and each one is a knob you can turn to amplify. Locally you likely have more cores and no cgroup quota, so run the suite under `--cpus=0.5` or with a CPU stress load beside it; if the rate climbs sharply, you're looking at a timing or interleaving problem rather than a resource one. Locally you often run a subset rather than the whole suite in one process, so try running only the last third of the suite and see whether the hang survives; if it needs the full prefix, something is accumulating. Locally your test order may be fixed, so shuffle with a recorded seed, and when a hang occurs, re-run with the same seed. If it reproduces deterministically, the cause is cross-test state and ordering and you can bisect the prefix; if it doesn't, the nondeterminism is genuinely in the scheduler or the network and the prefix is incidental. Those three knobs, CPU pressure, prefix length, and ordering seed, span most of the hypothesis space between them, and any one of them showing a strong effect tells you more than a week of reading test code.
