# Migrating from formkit 2.x to 3.0

One change in this release cannot be automated and will not announce itself: validators no longer run on every keystroke. Nothing throws, nothing warns, and your forms keep working. They just give feedback later than they used to, so the only way to find the fields that cared is to look at them. Budget your time accordingly; the rest of the upgrade is a codemod and a one-line rename.

| Change | How it's handled | What you see if you skip it |
| --- | --- | --- |
| Node 16 dropped | Upgrade the runtime to 18+ | Install or build fails |
| `formkit.json` → `formkit.config.js` | `npx formkit migrate-config` | Startup error: no configuration found |
| `strictValidation` → `validation` | Rename one key by hand | Deprecation warning in 3.0; breaks in 4.0 |
| Validators receive `(value, context)` | Nothing; 2.x validators are unaffected | Not applicable |
| Validation runs on blur and submit | Manual audit; add `validateOn: "input"` | No error. Feedback arrives later than before |

The sections below are in the order to do them, which is not the order of importance. The timing audit comes last because you need the upgraded app running in a browser to do it.

## 1. Node 18 or later

Node 16 is no longer supported. Raise the version in your CI images, your Docker base image, and the `engines` field of your own `package.json` before you touch anything else, because the 3.0 install will fail on 16 and you would rather see that failure on its own than mixed in with the config migration.

## 2. Move the configuration file

Configuration moves from `formkit.json` to `formkit.config.js`. The reason for the move is that people needed to compute values, and JSON has no way to express a computation, so real configs were being generated by build scripts or patched at runtime. Run:

```
npx formkit migrate-config
```

This reads `formkit.json` and writes `formkit.config.js` beside it. It handles almost every case, but "almost" is doing real work in that sentence: if your old file was assembled by a script, or contains keys the command does not recognise, check the output before deleting the original. Once you are satisfied, remove `formkit.json`, since 3.0 ignores it and leaving it in the tree will mislead the next person to read the repository.

A converted file is the same data in a module:

```js
// formkit.config.js
export default {
  theme: "default",
  locales: ["en", "fr"],
}
```

Now that it is a module, the values can be computed, which is the payoff for the migration:

```js
export default {
  theme: process.env.FORMKIT_THEME ?? "default",
  validation: process.env.NODE_ENV === "production" ? "strict" : "loose",
  locales: ["en", "fr"],
}
```

## 3. Rename `strictValidation`

The boolean `strictValidation` becomes `validation`, which takes three values rather than two:

| 2.x | 3.0 |
| --- | --- |
| `strictValidation: true` | `validation: "strict"` |
| `strictValidation: false` | `validation: "loose"` |
| No equivalent | `validation: "off"` |

`"off"` is new. There was no way to express it in 2.x, so no existing configuration needs it; it is there for the cases where you want validation compiled out entirely, such as a test harness that supplies known-bad fixtures on purpose.

The old boolean still works in 3.0 and prints a deprecation warning at startup. It will be removed in 4.0. If `strictValidation` survives the config conversion, that warning is your signal to rename it by hand, and doing it now costs one line.

## 4. Validators receive a second argument

Field validators used to be called with `(value)` and are now called with `(value, context)`, where `context` carries the values of the other fields in the form. This is additive. A validator that declares one parameter is called exactly as before and needs no change:

```js
// Unchanged in 3.0
const isLongEnough = (value) => value.length >= 8
```

What the second argument buys you is cross-field checks that previously needed a closure over form state, or a subscription, or both:

```js
// 3.0
const matchesPassword = (value, context) => value === context.values.password
```

One flag on that example: the accessor shown here is the shape you should confirm against the API reference for your minor version, since the surface of `context` is the newest part of this release and the likeliest to have moved. The migration-relevant fact is stable regardless of how you reach into it, which is that your existing one-argument validators do not need to be touched.

## 5. Validators no longer run on every keystroke

In 2.x, a field's validators ran on every input event. In 3.0 they run when the field loses focus, and again on submit. The change was made because validators that call a server, checking whether a username is taken or a coupon code is live, fired one request per character typed. A ten-character username was ten requests, nine of them for prefixes nobody cared about, and the last one racing the others to decide what the user saw.

If a field genuinely needs per-keystroke validation, ask for it on that field:

```js
{
  name: "username",
  validators: [isAvailable],
  validateOn: "input",
}
```

Finding the fields that need it is the manual part of this upgrade, and it is manual because the failure is silent. Your tests will most likely still pass, since a test that fills a field and submits the form never notices when validation ran. The behaviour that changed is what the user sees between the first character and leaving the field.

Three kinds of field are worth checking by hand, in roughly this order:

- **Live meters and counters.** Password strength indicators, character countdowns, and anything else that updates as the user types. These are the clearest regressions: the widget now sits still until focus leaves. They almost always want `validateOn: "input"`.
- **Format-as-you-go fields.** Card numbers, phone numbers, postcodes, and any field where the validator was doing double duty as a formatter. Check whether the formatting still happens when you expect it to.
- **Server-checked fields.** Username availability, coupon codes, address lookup. Leave these on the new default. They are the reason for the change, and moving one back to `validateOn: "input"` restores the request-per-character behaviour you have just been given a fix for.

The check itself takes a browser rather than a test runner. Open each form, type an invalid value into a field, and watch whether the error appears before you tab away. Where the delay is wrong for that field, add `validateOn: "input"`; where it is fine, leave it, because the new default is cheaper for you and quieter for the person filling in the form.
