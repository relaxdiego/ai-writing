I replaced the hardcoded TTL in the session cache with the shared constant. `src/cache/session.py:14` had `session_ttl = 3600` sitting alongside `SESSION_TTL_SECONDS = 900` in `src/config/defaults.py`, and the class attribute was the one actually driving expiry at `src/cache/session.py:88`, so the config value was dead. The class now reads `session_ttl = SESSION_TTL_SECONDS`, and `tests/test_session_cache.py` asserts against the same constant rather than the literal 3600 — that assertion was the single failure after the first edit, and the suite is back to 8 passed.

Worth being explicit that this is a behavior change, not just a cleanup: cached sessions now expire after 15 minutes instead of an hour. Everything downstream of `get()` will see cache misses four times as often, so if the 3600 was load-bearing rather than a stale copy, the fix should go the other direction and `SESSION_TTL_SECONDS` should become 3600. I picked the config value as the source of truth because that's the one a deployment would expect to be authoritative, but I have no history telling me which of the two was written later.
