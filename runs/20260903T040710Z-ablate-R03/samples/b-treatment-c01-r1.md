The session cache had its TTL hard-coded: `SessionCache.session_ttl` was set to a literal `3600`, while `src/config/defaults.py` declared `SESSION_TTL_SECONDS = 900` as the intended value. Anything reading the config would have believed sessions expired after fifteen minutes, but the expiry check in `get()` was comparing against an hour. I replaced the literal with a reference to `SESSION_TTL_SECONDS` so the config value is the single source of truth.

That change broke `tests/test_session_cache.py::test_expiry_boundary`, which asserted the literal `3600`. Since the test was pinning the duplicated constant rather than any behaviour, I updated it to assert against `SESSION_TTL_SECONDS`; the full file now passes at eight tests. Be aware this does mean the test no longer pins a concrete duration, so a future edit to `defaults.py` will move both sides together and pass silently. If the fifteen-minute figure is a real contract rather than a tunable, a test asserting the literal `900` against `SESSION_TTL_SECONDS` in the config module would catch that.

Two things I did not verify and you should check before this lands. Neither edited file was confirmed to import `SESSION_TTL_SECONDS` — the tests passing suggests `src/cache/session.py` resolves it somehow, but the test file's import went unchecked and I never read the top of either file. And in the `get()` method, `now` is used in the comparison without being assigned anywhere in the surrounding lines I read, so it is either a module-level name or a latent `NameError` on the expiry path that the passing tests happen not to exercise.
