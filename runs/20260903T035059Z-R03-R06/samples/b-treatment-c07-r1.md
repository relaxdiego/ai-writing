Before the speed question, the plan has a correctness failure that would ship as a data leak. Keyed by the SQL string, the cache cannot tell your users apart. If your queries use parameter placeholders, every user asking for their own rows produces the identical key `SELECT ... WHERE owner_id = $1`, and whoever populates that entry first serves their rows to everyone who follows. If you interpolate the values into the SQL text instead, the key does separate users, but only for authorization that is literally visible in the statement; anything carried in connection or session state, a role set on the connection, a tenant setting read by an RLS policy, is invisible to the key and leaks exactly the same way. Any cache sitting underneath row-level authorization has to carry the full authorization context in its key, at which point the key is not the SQL string any more.

The eight workers then undercut the benefit you're paying for that risk. Each process holds its own dictionary, so a query must be executed once per worker before it is warm, and the load balancer scatters a user's requests across all eight so each copy ages independently. A write that lands on worker 3 leaves the other seven serving what they already had, and a plain in-process dict has no channel to hear about it. Invalidation is where this gets structurally hard rather than merely wasteful: to evict on a write you need to know which cached SQL strings that write affected, and you cannot derive that from the text of the INSERT. You would have to maintain a dependency map from tables or rows to cache keys by hand, and at roughly seven writes a second the map is being consulted constantly. Skip it and you choose between unbounded staleness and a TTL so short the cache rarely hits. The dictionary also never evicts, so memory grows without bound in all eight processes.

The safe version of your instinct is a per-request memo: a dict created at the start of a request, keyed by statement plus parameters, discarded when the response is sent. The authorization context is fixed for the life of one request, so the leak cannot occur, and staleness is bounded by request duration, so there is nothing to invalidate. That captures the genuinely repeated identical queries, which in most web apps come from the same lookup being made in three layers of the same handler.

For anything crossing requests, use a shared store such as Redis rather than process memory, and key it by entity identity and scope (`user:1234:dashboard:v3`) rather than by query text, so the code that writes an entity can delete the keys it owns, with a short TTL as a backstop for what you miss. Cache computed results, rendered fragments and expensive aggregates rather than the raw query layer, since those are the things that tolerate being a minute old.

Worth checking before any of it: your database already caches pages and query plans, so a repeated identical query is frequently cheap on the server side and expensive only in round trips. Applications that feel slow usually have N+1 query patterns, a missing index on a filtered column, or no connection pooling, and each of those is a bigger multiplier than caching. Turning on slow-query logging and counting queries per request for a day will tell you which of the three you have.
