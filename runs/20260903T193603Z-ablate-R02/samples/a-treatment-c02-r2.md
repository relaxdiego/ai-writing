A hang that lands on a different test every run is telling you something, and it is worth taking the signal seriously before picking a culprit. If a specific test had a bug, you would see it land on that test, at a rate proportional to how often the bad interleaving occurs. Landing anywhere means the cause is either shared across tests (a resource that accumulates, a background thread, a connection the whole suite reuses) or environmental (something about the CI network or the CI process tree that any test can trip over). One caveat before you lean on that inference: check whether your runner randomizes test order between runs. If it does, "different test each time" is also consistent with a boring pairwise interaction, where one test leaves state behind and whoever runs next blocks on it, and pinning the seed will collapse the problem into something reproducible.

On the pool theory, there is a one-minute check that will probably settle it. Look at whether your pool is configured with an acquisition timeout. Most pools default to raising after some seconds rather than blocking forever, and if yours does, exhaustion cannot produce a hang; it produces an error with a recognisable message. Even where the timeout is genuinely infinite, plain contention tends to bite early and often rather than one run in twenty, because the concurrency level is the same on every run. The version of the pool story that does fit your symptoms is a leak: a test that fails to return a connection, or leaves a transaction open, so the pool drains monotonically over the run and the suite dies whenever the drain happens to outrun the remaining tests. That variant makes a sharp prediction you can test, which is that the hang should be biased toward the back half of the suite. If you record the ordinal position of the last test to start and the positions are uniform across twenty runs, the leak story is dead.

Several other explanations fit "never locally" better than the pool does. The most common is that a socket in CI has no timeout and the peer is not there: a NAT or load balancer between the runner and the database silently drops an idle connection, the client later blocks in a read on a connection nobody will ever answer, and because it never writes, TCP never retransmits and never errors out, so it waits forever. Locally the same code talks to localhost, where a dead peer produces an instant reset. A close relative is the output pipe deadlock, where a test spawns a subprocess that writes more than the 64KB pipe buffer while the parent is not draining it. Then there is parallelism: if CI runs the suite sharded or with N workers and you run it serially, an entire class of interleavings exists only in CI. And CPU quota matters more than people expect, since a container pinned to two cores changes thread scheduling enough to expose lost-wakeup bugs that a laptop with twelve cores hides.

There is also a possibility worth eliminating first because it is cheap and it is not a test bug at all. Look at the tail of the log from a hung run. If the suite printed its summary line and the job still sat there, no test is hanging: a daemon or container that some test started has inherited the runner's stdout, and the runner is waiting on EOF from a pipe that an orphaned process is still holding open. That produces exactly your pattern, including the apparent randomness, because which test leaked the child depends on ordering and timing.

The thing I would actually do first is not test any of these hypotheses. A hang is the most tractable failure there is, because the process is still sitting in front of you in the broken state, and the reason this has stayed mysterious is that CI is killing the evidence. Add a watchdog to the CI job that fires a few minutes before the platform's own timeout and, before killing anything, dumps the stack of every thread in every relevant process, plus the open sockets and their TCP states, plus the server's view of its sessions. In Python that is `faulthandler.dump_traceback_later`; on the JVM it is `kill -3`; in Go, `SIGQUIT` prints every goroutine; in Node you want the diagnostic report wired to a signal. Alongside it, capture `ss -tanp` and, if Postgres is involved, a snapshot of `pg_stat_activity`.

That single artifact separates every branch above without any guessing. Threads parked in the pool's acquire call, with the server showing sessions idle in transaction, is the leak. A thread blocked in `recv` on an ESTABLISHED socket whose peer has vanished is the NAT reaping story. Blocked in `write` on a pipe is the subprocess deadlock. Two threads holding locks in opposite order is a deadlock you can then read directly. A stack sitting in a read on stdin means something is prompting in an environment with no terminal. And if no stack is in your code at all, you are looking at the orphaned-child case.

While that is landing, the two background experiments worth running are a loop of twenty CI runs with worker count forced to one, which tells you whether parallelism is required to reproduce, and a loop of the same image locally under the same CPU and memory limits, which usually converts "it never happens locally" into "it happens locally in about an hour".
