A hang is two independent facts stacked on top of each other, and the fastest way to make progress is to stop treating it as one. Something blocked, and nothing in the stack put a bound on how long it was willing to block. The intermittency lives entirely in the first fact; the fact that it hangs rather than fails lives in the second. Even if you never find the trigger, closing the unbounded waits converts a hung job into a stack trace, which is the only artifact that will actually settle the argument. It's also worth discounting "always the integration tests" as evidence, since those are the only tests that wait on anything external, so every wait-forever bug in the system lands there regardless of its cause.

Connection pool exhaustion is a real possibility but a weak default, and the version of it people usually mean is testable in an afternoon. A pool leak, where connections are checked out on a path that doesn't return them, accumulates monotonically through the run, so the hang should land at a roughly constant point in elapsed time or test count even though the test at that point differs from run to run. Contention-based exhaustion, where workers legitimately outnumber connections, would instead scatter. So the first question is whether CI differs from your machine in test parallelism or pool size: four parallel workers against a pool sized for one is a very different world from what you run locally. The cheap falsification is to give the pool an acquisition timeout of a few seconds and turn on leak detection (Hikari's `leakDetectionThreshold`, SQLAlchemy's `pool_timeout`, whatever your equivalent is). If the pool is guilty, the next hang becomes a fast, loud failure naming the thread that never gave the connection back. If the hang survives unchanged, the pool is exonerated and you've lost nothing.

Given "never locally," the hypothesis I'd rank above the pool is CPU quota. CI containers typically run with two cores or a fractional cgroup quota, while your laptop has eight or more. Any thread pool sized from the core count shrinks accordingly, and code that submits a task to a pool and then blocks a worker of that same pool waiting on it deadlocks outright once the pool is small enough. The same shrinkage widens every timing window you have: readiness waits, retry backoffs, races between a background thread finishing and a test tearing down its fixture. This class of bug is invisible on a fast machine and probabilistic on a slow one, which is exactly the one-in-twenty shape you're seeing.

Several other candidates fit the profile equally well. If any test shells out to a subprocess, a pipe deadlock is a classic: the child fills the 64KB stdout buffer and blocks on write while the parent blocks on `wait()`, and CI often runs with more verbose logging than you do locally, which is precisely what pushes output past the buffer. If your CI can run more than one pipeline at a time, a shared staging database, broker, or advisory lock will serialize two runs against each other, and the observed frequency would track how often two pipelines overlap rather than anything in your code. A background thread or consumer leaked by an earlier test can hold a lock that a later, unrelated test needs, which reproduces your "different test each time" symptom exactly. And an OOM kill of a child process can leave the parent waiting on a socket that will never close or produce EOF.

The move that separates all of these at once is capturing thread state at the moment of the hang. Set a per-test timeout below the job timeout and make the timeout handler dump every thread, goroutine, or pending task before it kills anything: `jstack` or SIGQUIT on the JVM, SIGQUIT for a full goroutine dump in Go, `faulthandler.dump_traceback_later` in Python, SIGUSR1 or a periodic async-hook dump in Node. Every threads parked in `pool.acquire` points at the pool; workers of one executor blocked awaiting results from that same executor is starvation deadlock; a thread blocked in `write` to a pipe is the subprocess case; a lone thread in a socket read with everything else idle is a missing read timeout on a service call. Alongside the dump, capture pool gauges, `pg_stat_activity` joined against `pg_locks` (or `SHOW PROCESSLIST`), `ss -tanp`, and the open file descriptor count, since the database's own view of who is waiting on whom often names the culprit directly.

Two correlations cost nothing and can be gathered from logs you already have. Emit a timestamped line per test and check whether hangs cluster at a similar elapsed time or test index, which discriminates leak-style accumulation from scattered contention, and check whether hangs concentrate on a particular runner or coincide with concurrent pipeline runs. In parallel, try to reproduce under CI's actual constraints rather than CI's actual environment: run the suite in a container with `--cpus=2`, the same memory limit, the same log level, and the same worker count, looped fifty times. At one in twenty you'd expect two or three hangs from that loop, and a reproduction that appears at two cores but not eight tells you the trigger is scheduling pressure before you have read a single stack.
