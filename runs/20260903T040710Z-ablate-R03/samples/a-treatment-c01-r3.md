`SessionCache.session_ttl` was hardcoded to 3600 while `src/config/defaults.py:31` defined `SESSION_TTL_SECONDS = 900`, so the config value was dead and every session actually lived an hour. I changed the class attribute at `src/cache/session.py:14` to read from the constant, which makes the config authoritative and shortens the real expiry window from sixty minutes to fifteen. That is a behaviour change for anything relying on the old lifetime, so it is worth a look before this ships.

One test failed on the change: `test_expiry_boundary` in `tests/test_session_cache.py` asserted the literal 3600. I updated it to compare against `SESSION_TTL_SECONDS` rather than a number, so the test now pins the wiring instead of restating a value the config owns. If that test was deliberately guarding 3600 as the intended production lifetime, then the fix belongs in `defaults.py` instead and my edit points the wrong way; nothing in the file said so, so I took the config as the intended source of truth.

The eight tests in `tests/test_session_cache.py` pass. I did not run the rest of the suite, and other callers may still assume the longer window. Reading the `get` method around `src/cache/session.py:88`, the `now` used in the expiry comparison has no assignment in the body I looked at; the expiry tests pass, so it resolves from somewhere, but I did not trace where.
