The instinct is sound — repeated identical reads are wasted work, and caching them is the standard fix. The specific mechanism you've described, though, will break in ways that are hard to detect once it's live, and the three details you mentioned about your setup are exactly the ones that break it.

Start with the authorization problem, because it's the one that hurts most. If your queries are parameterized (`WHERE user_id = ?`), then the SQL string is identical for every user, and a cache keyed on that string will serve user A's rows to user B on the next request. Your row-level authorization lives in the parameters, not in the text, so keying on the text throws away the only thing distinguishing one user's result set from another's. If instead you interpolate values into the SQL before it's sent, the key does include the user ID and you avoid the immediate leak — but you've traded it for near-unbounded key cardinality, since every distinct parameter combination becomes its own entry in a dictionary that has no eviction policy and grows for the lifetime of the process. You'd also still be caching authorization decisions: when someone's access is revoked, their cached rows keep answering until something evicts them.

The eight workers undercut the benefit even where it's safe. Each process gets its own dictionary, so a given query has to be executed eight times before it's warm everywhere, and your effective hit rate is roughly what a single-process cache would give at one-eighth the traffic. Memory cost multiplies by eight in the same breath. Worse, there's no channel for one worker to tell the other seven that a row changed, so any invalidation you write is local and the remaining seven keep serving stale data until they happen to evict on their own.

Then there's the write rate. At 400 writes per minute you have a mutation landing every 150 milliseconds, and for each one you'd need to know which cached SQL strings it invalidated. Deriving that from an `UPDATE` statement isn't tractable in general; the usual fallback is invalidating every cached query touching that table, which at your write rate means your hottest tables are being flushed continuously and the cache stops paying for itself. Skipping invalidation entirely leaves you with unbounded staleness on a system where users write frequently enough to notice.

Here's what I'd suggest instead, roughly in order of effort:

1. **Confirm the database is actually the bottleneck.** Break down p95 request latency into DB time, template rendering, external calls, and serialization. Turn on the slow query log for a day. It's common for the real cost to be an N+1 loop issuing 200 fast queries rather than any single slow one, and no cache layer fixes that as cleanly as fixing the loop.
2. **Fix indexes and N+1s first.** These are free in the sense that they add no new failure modes, no staleness, and no coordination problem — and they frequently deliver more than a cache would.
3. **If you still want caching, use a shared store.** Redis or Memcached in front of all eight workers gives you one warm cache instead of eight cold ones, plus a place to publish invalidations that every worker sees.
4. **Key on entities and scope, not SQL.** Something like `user:1234:invoices:v7` rather than the query text. You control the key, so you know what invalidates it, and the user ID in the key makes the authorization boundary explicit rather than accidental. Bump the version segment on write to invalidate a whole family at once.
5. **Give everything a TTL anyway,** as a backstop for the invalidation you inevitably miss. Short TTLs on frequently written data, longer on reference data that changes rarely — configuration, lookup tables, permission definitions — which is usually where the best cache-hit-to-risk ratio lives.
6. **Consider a read replica** if the load is genuinely read-heavy volume rather than a handful of expensive queries. It scales reads without introducing a staleness model you have to reason about per query.
