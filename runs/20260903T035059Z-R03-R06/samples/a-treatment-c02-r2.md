A hang is not the same kind of bug as a flake, and separating the two will save you time. Something in your system is waiting on a condition that will never become true, and it is waiting without a deadline. Whatever the underlying race or leak is, it only manifests as a hang because some wait is unbounded, so the first thing to do is enumerate the unbounded waits statically: connection acquisition with no acquire timeout, socket reads with no SO_TIMEOUT or read deadline, HTTP clients with a connect timeout but no total-request timeout, `join()` or `await` on a future nothing will complete, subprocess `wait()` without draining the pipe, and lock acquisitions with no timeout. That list is usually short and you can write it down in an afternoon from the code, and every hypothesis below has to route through one of those waits to produce the behaviour you're seeing.

The pool theory is half right in a way that's worth being precise about. "Connection pool exhaustion" names a symptom, not a mechanism: it tells you a resource wasn't returned but not why, and the why is the actual bug (a transaction left open when a test assertion throws before teardown, a fixture that acquires outside the try block, a background task holding a connection past the test that spawned it). More usefully, most pools have an acquisition timeout, and if yours does and it's set to anything finite, exhaustion produces a loud error at that deadline rather than a hang. So check the configured value first. If it's 30 seconds and your job dies at the 60-minute mark, the pool is largely exonerated; if it's zero or unset, it moves to the top of the list.

The other candidates that fit "only in CI, always integration, always a different test" are worth holding alongside it. Runtime thread starvation is structurally identical to pool exhaustion but harder to see: a blocking call executed on an async runtime's worker pool will deadlock when all workers are blocked waiting for work that needs a free worker, and CI containers typically get two cores where your laptop has ten, so the pool is small enough to saturate. Half-open TCP connections are the other big one: if a dependency container gets OOM-killed, or the Docker bridge's conntrack table evicts an idle flow, the client holds a socket that is ESTABLISHED locally and nonexistent on the peer, and a read on it blocks until the kernel's keepalive fires, which by default is two hours. Pipe deadlock shows up when CI captures output through a pipe while your local run writes to a TTY: a child fills the 64KB buffer and blocks in `write` while the parent blocks in `wait`. And in the database itself, a genuine deadlock gets detected and aborted in about a second, so a real hang points instead at a session sitting `idle in transaction` holding a row lock that every subsequent test queues behind.

None of this gets resolved by reasoning, though, and the decisive move is to stop letting the CI job time out and kill the evidence. Add a watchdog that fires a few minutes before the job deadline and, before anything is torn down, captures: a stack dump of every thread in the test process (SIGQUIT for the JVM, `py-spy dump --pid`, `jstack`, SIGABRT with a core for Go, `--inspect` for Node), `ss -tanp` for socket states and queue depths, `SELECT pid, state, wait_event_type, wait_event, query, xact_start FROM pg_stat_activity` plus `pg_locks` where not granted, `ps -ef --forest` for the process tree, `dmesg | tail` for OOM kills, and the logs of every dependency container. One good capture will collapse the hypothesis space almost entirely.

The signatures are distinct enough to read directly off that bundle. Pool exhaustion gives you exactly max-pool-size threads parked in `acquire`/`getConnection` and a matching set of server-side sessions that are idle or idle-in-transaction. Runtime starvation gives you all worker threads inside a blocking syscall with a nonempty task queue. A half-open socket shows as ESTABLISHED on the client with no counterpart server-side and no retransmit timer running. Pipe deadlock shows a child blocked in `write` under a parent blocked in `wait`. A lost wakeup shows one thread on a condvar or unresolved promise with nothing in flight anywhere else.

While you wait for a hang to recur, two cheap experiments discriminate without any capture at all. Shrink the pool to two connections: if it's a leak, the hang goes from one run in twenty to nearly every run and moves much earlier, and if the hang point doesn't budge, the pool isn't the constraint. Then run the suite locally under CI's actual constraints, `--cpus=2 --memory=2g`, output piped rather than to a TTY, same shard count and worker count, same container images. "Never hangs locally" very often means "never runs the same way locally," and closing that gap tends to reproduce the thing in minutes.

The statistics are also evidence you're currently throwing away. Log the random seed and the test ordering on every run, and record for each hang how far into the suite it occurred: test index, elapsed time, and which tests were running concurrently on other workers at that moment. A cumulative leak clusters tightly around a fixed count of completed tests even though the named test differs each time, because the test that hangs is just whichever one happens to cross the threshold. A timing race scatters uniformly. And if the hang correlates with a particular pair of tests being in flight simultaneously on different workers, you have cross-test interference through shared state, which no amount of staring at the named test would ever have shown you.
