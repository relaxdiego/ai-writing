Keying the cache on search text alone will serve one user's private items to the next person who searches the same words.

The page isn't a function of the search text. It's a function of the search text, the viewer's identity, the viewer's permissions, and the time of day, and the key you've proposed names only the first of those. The first person to search "invoice" populates an entry containing their saved items and whatever the permission filter let them see, and for the next hour everyone searching "invoice" gets that page. If there's a CDN or any shared HTTP cache between the app and the browser, the same entry can also reach logged-out traffic. Nothing errors when this happens; the pages just contain the wrong person's items, so it can run for days before anyone reports it, and by then the cache has been handing out other people's data the whole time. The stale prices are a smaller version of the same mistake: an hour-old page shows an hour-old price, and depending on how you sell, you may have to honour the number you displayed.

The obvious patch, adding the user ID to the key, closes the leak but gives you almost nothing. Query text varies enormously per person, so per-user entries would rarely be hit twice before they expire, and the prices are still an hour stale. The real problem is that one page mixes three ingredients with three different lifetimes, and a single TTL can't serve all of them. Split them instead:

- **The public candidate set for a query.** Genuinely shared between users, and almost certainly where the database load is. Cache the ordered list of item IDs keyed on the normalised query, with a TTL of a few minutes, and run the permission filter on every request against that list. Filtering IDs you already hold is cheap next to re-running the search.
- **The viewer's saved items.** Per-user, so key on user ID and invalidate when they save or remove something rather than waiting out a clock.
- **Prices.** Keep them out of any cached object, or give them their own TTL set by how often they actually move.

Whatever you key on, normalise it and put every parameter in the key: case, surrounding whitespace, filters, sort order, and page number. Miss the page number and someone asking for page 3 gets page 1; miss the filters and they get someone else's filtered view of the same words.

Before any of it, find out what's actually slow. "Search page is slow" could be the search query, the permission filter running per row, an N+1 fetching item details, or rendering. A cache on the wrong layer buys no speed and leaves you with an invalidation problem for as long as the code lives. If the search query is the cost, the candidate-ID cache is a couple of days of work, ships this week, and keeps every permission check on the live request path where it belongs.
