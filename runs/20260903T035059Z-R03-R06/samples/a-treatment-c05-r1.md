I didn't find the cause. What follows is what the evidence rules out, the two hypotheses it leaves, and the checks that separate them.

The last eight runs split cleanly into two populations: about 48k rows in roughly 15 minutes, and about 23k rows in roughly 7 minutes. The short runs land on 23, 26 and 29 August, every third day, with no drift in the 02:00 start. Both the row count and the wall-clock time are halved together, and that proportionality is informative. If the job were writing fewer rows out of a full input set, the fetch and the grouping would still cost their usual minutes; the run would be short on rows but not on time. A duration that falls with the row count points at the read side. The write loop also sits inside a single `transaction()` at `jobs/nightly_rollup.py:23`, so a failure partway through the writes would abort the whole rollup rather than commit half of it.

The window logic at `jobs/scheduler.py:61` is the natural suspect, and I think it's the wrong one. Since `window_start` is `last_success_at`, a truncated window on one night would leave the missed events inside the next night's window, and the following run would come in around 72k. Every run after a short one sits in the normal 48k band instead. The same reasoning rules out a skipped or double-fired execution, so the missing events are never written at all rather than being deferred a day.

That leaves two candidates I could not separate from what's in the repo. Commit `9d02e1e` added retries for transient fetch errors; if that path exhausts its attempts and returns the partial result it has instead of raising, the job would write a short rollup and still record `status = ok`, which is what `job_runs` shows for all three short nights. The alternative is that the events genuinely aren't in the source, because an upstream producer on its own cadence is late or short every third night. Both hypotheses produce byte-identical rows in `job_runs`, which records `rows_written` and nothing about rows read.

Counting source events directly for one short night and one normal night, over the same 02:00-to-02:00 window, tells you which it is: a full-sized input on a short night puts the loss inside `fetch_events`, and the retry error handling is then the specific thing to read, looking for a swallowed exception or a returned partial batch. A half-sized input puts the problem upstream of this repo. I did not read `fetch_events` itself, so the retry hypothesis is inference from the commit message rather than from the code.

One caveat on the pattern: I pulled only the last eight runs, and there are 30 in the table, so the three-day period rests on three data points and may be coincidence. The full 30 would show whether the cadence holds and, more usefully, when the first short run occurred. Dating that against `9d02e1e` would either implicate the retry change or clear it outright, since a short run predating the commit means the retry path was never the mechanism.
