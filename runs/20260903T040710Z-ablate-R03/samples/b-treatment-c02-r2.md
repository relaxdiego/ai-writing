Start with what the evidence shape tells you, because it constrains things more than any single hypothesis does. A hang that lands on a different test each run is evidence against a bug in any particular test and in favour of something shared: a resource with a fixed budget, a global piece of state, or an event ordering that CI's timing perturbs. The pool suggestion is one member of that family, but the family is larger, and the family resemblance is specific: a bounded resource acquired with an unbounded wait. Connections are one such resource. So are worker threads, event-loop slots, database locks, ports, subprocess pipe buffers, and semaphores in your own test fixtures. Any of them will produce exactly the symptom you describe, and the reason it only happens in CI is usually that CI has fewer cores, less memory, slower and jitterier I/O, and often more parallel test workers against one shared dependency.

Before reasoning further, though, the highest-value move is to stop inferring and capture the process state at the moment it is stuck. A hang is the easiest kind of bug to diagnose directly, because the evidence sits there indefinitely waiting to be read; the reason it feels hard is that CI kills the job and throws that evidence away. Add a watchdog that fires before the CI job timeout and dumps stacks rather than exiting. In Python, `faulthandler.dump_traceback_later(600, exit=False)` costs one line, and `py-spy dump --pid <pid>` works from outside without cooperation; for asyncio also dump `asyncio.all_tasks()`, since a blocked coroutine shows up nowhere useful otherwise. On the JVM, `jcmd <pid> Thread.print` gives you lock ownership as well as stacks. In Node, start with `--report-on-signal` and send `SIGUSR2`, which yields the pending libuv handles and requests, the thing you actually need. In Go, `SIGQUIT` dumps every goroutine. Around that, capture `ps -efH`, `ss -tanp` for socket states, and on the database side `pg_stat_activity` with `wait_event_type`, plus `pg_locks` joined to find blocking PIDs. One such artifact will usually end the argument in a minute: a thread parked in `pool.acquire` says pool, a thread in `recv` on an established socket while the server shows no matching session says half-open connection, a query in `Lock` state says contention, all worker threads busy with a full queue says starvation, and a parent in `waitpid` with a child blocked in `write` says pipe.

The candidates worth holding in mind while you read that dump are these. Pools and executors sized from `cpu_count()` shrink dramatically under a CI container's cgroup limits, so a test that needs three concurrent connections gets two and waits forever; this is the most common cause of "only in CI", and it is not really a leak. Genuine leaks look different, and the tell is positional: if a connection is leaked per test, the hang should cluster in the later part of the run, whereas a race distributes uniformly. Lock contention between parallel workers sharing a database will block indefinitely if `lock_timeout` is unset, and the deadlock detector will not save you because a plain lock wait is not a deadlock. A pooled connection whose peer died silently, or that a NAT or proxy dropped while idle, will block on read forever if no socket read timeout is configured. A lost wakeup, where a notification arrives before the waiter registers, flips into failure precisely when the machine is slow and scheduling is coarse. A subprocess whose stdout pipe fills while the parent waits on exit deadlocks in CI but not locally, because locally it inherits a terminal. And a dependency container getting OOM-killed leaves every client of it hanging on a socket that will never answer, which you confirm from `dmesg` or the container's restart count rather than from the test process at all.

Several cheap experiments discriminate among these without any instrumentation. Record the index of the test at which each hang occurs and build a histogram over runs: skewed late means accumulation, uniform means a race. Rerun the integration suite with parallelism set to one; if the hang vanishes, the problem is cross-worker contention over a shared dependency rather than anything inside a single test. Check whether the stuck process is at zero or one hundred percent CPU, which separates a genuine block from a livelock or GC death spiral in a few seconds. Try to reproduce locally under CI-like constraints instead of on your laptop's terms: `docker run --cpus=1 --memory=2g`, the same worker count, and if you can, a little injected latency with `tc netem`. At one run in twenty, roughly sixty looped runs give you good confidence either way, and reproducing under constraint is itself a strong result, because it identifies the constrained axis.

Two closing observations about the pool hypothesis specifically. It is often a symptom rather than a cause: connections held by queries blocked on a lock, or by threads blocked on something else entirely, present as exhaustion, so confirming that the pool is empty does not tell you why. And the test where the run stops need not be the test that caused it; whoever leaked the connection or left the lock held has usually finished and moved on. Regardless of which cause you land on, set explicit timeouts on every acquire, socket read, lock, subprocess wait and individual test. That will not fix the underlying race, but it converts an opaque twenty-minute hang into a stack trace at the point of contention, which is the difference between a bug you can work on and one you can only speculate about.
