The guard on line 34 raises immediately for any status below 500 except 429, so a 400 propagates out of the loop on the first attempt and never reaches the `time.sleep`. The retry set is exactly 5xx plus 429, which is what you'd want. My earlier recommendation to narrow the condition was advice to fix something that was already correct, and you should disregard it. One thing I did notice while re-reading, unrelated to the retry set: on the final iteration the loop sleeps `2 ** (attempts - 1)` seconds before falling through to `raise RetryExhausted()`, so a five-attempt call spends 16 seconds waiting after the last request it will ever make. Moving the sleep behind an `if i < attempts - 1` check removes that. `RetryExhausted` also discards the last `HTTPError`, which makes the failure harder to diagnose from a traceback; chaining it with `raise RetryExhausted() from e` keeps the underlying status visible.
