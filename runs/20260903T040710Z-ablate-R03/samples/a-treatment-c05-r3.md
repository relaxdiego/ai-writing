I didn't find the cause, but the shape of the failure narrows it considerably. The rows-written column is bimodal rather than variable: the eight most recent runs sit at either ~48k or ~23k with nothing in between, and the short runs took about seven minutes against fifteen for the full ones. Runtime tracking row count that closely suggests the job isn't dropping rows on the way out; it is being handed roughly half the input and processing it faithfully. That moves suspicion off `write_rollup` and the transaction block, where a partial commit would instead show up as a long run with few rows, and onto `fetch_events` and the window it's given. Every short run is also recorded as `ok`, so nothing along the path raises, which fits either a window that is legitimately smaller or an error being caught and turned into a partial result.

The window comes from `window_start = last_success_at or (now - timedelta(hours=24))` at `jobs/scheduler.py:61`. The fallback has never fired in the visible history, since every run succeeded, so `window_start` is always `last_success_at`. I could not tell from the scheduler alone which timestamp that column is written from. If it is `finished_at`, each window loses the previous run's duration, but that is fifteen minutes off twenty-four hours, nowhere near a halving. The window logic as I can see it explains a small shortfall, not this one, unless `last_success_at` is set from something I haven't found.

One pattern I can't account for: the three short runs fall on 23, 26 and 29 August, evenly three days apart. Over eight samples that may be coincidence. There are 30 rows in `job_runs` and I only pulled the most recent eight, so reading all 30 would say quickly whether the cadence is real, and a real cadence would point at something periodic outside this job rather than at a race inside it.

Two things I did not check could each account for the whole thing on their own. The first is whether the source events themselves were halved on those nights. If upstream ingestion delivered half the events, the rollup is correct and the bug isn't in this job at all; a count of raw events grouped by day over the same period settles that before more time goes into `nightly_rollup`. The second is `9d02e1e "fix: retry transient fetch errors"`, which I found in the log but didn't read. A retry that returns a partial result on the second attempt instead of failing would produce precisely this signature: half the rows, half the runtime, status `ok`. If the daily event counts come back flat across those three nights, that commit is where the answer most likely is.
