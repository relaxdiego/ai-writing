A one-in-twenty hang that lands on a different test each run is telling you the fault is not in any test's logic. If it were, the same test would hang, or at least a small family of tests would. What varies between runs is scheduling: which threads happen to be runnable, which connection happens to be handed out, which two jobs happen to overlap. So the useful hypotheses are all about shared state or shared execution resources, and the reason it never reproduces locally is almost certainly that your laptop has more cores, a TTY, warm containers, and no other job competing for the same database.

Take the connection pool theory first, because it is worth being precise about why your instinct is reasonable. Genuine exhaustion from a leak is monotonic: connections drift out of the pool as the run proceeds, so the failure should bias toward the end of the suite rather than scattering uniformly. Most pools also have an acquisition timeout, which turns exhaustion into a thrown exception with a stack trace rather than a silent hang. If you are seeing a true hang and not a timeout error, either the acquire timeout is infinite, or the block is somewhere other than acquisition. There is a nearby variant that fits your symptoms much better, though: a pooled connection that a NAT gateway or firewall silently reaped after an idle period, handed back out to a test, which then writes a query and waits forever for a response that no one will ever send because the peer never sent a RST. No socket read timeout means no error, just a thread parked in `recv`. That happens in CI and not locally because in CI there is network infrastructure between you and the database with an idle eviction rule, often around five minutes.

The other strong candidate is executor starvation, which is the classic "only on CI" hang. A fixed-size thread pool sized from available cores behaves differently on a two-core runner than on your ten-core machine. If any code path blocks a pool thread while waiting on work that is itself queued to that pool, you get a cycle whose likelihood depends entirely on how many threads are available to absorb it. With eight workers the dependency almost always resolves; with two it deadlocks a few percent of the time, at whatever test happens to be running when the pattern occurs. Related failures include a lost wakeup, where a completion fires before the waiter registers, and event-loop starvation from a synchronous call on an async path. Those are all sensitive to timing that CI stretches.

Two mundane causes deserve a place on the list because they are cheap to rule out. Output pipe backpressure hangs a process when it writes to a pipe nobody is draining, which happens in CI (output captured through a bounded buffer) and not locally (a terminal that drains continuously); it correlates with verbose logging and with subprocesses that inherit stdout. And cross-job contention, where two concurrent CI jobs share a database, a Redis instance, a fixed port, or an S3 prefix, would give you a hang rate that tracks your organisation's CI concurrency rather than anything about your code. A one-in-twenty rate is quite consistent with "sometimes another PR is building at the same time."

The single change that collapses all of this from speculation to reading is making the hang produce evidence before it dies. Set a per-test or per-suite timeout well below the CI job timeout, and on expiry dump the state of the process rather than killing it: `SIGQUIT` for a JVM or Go binary, `py-spy dump --pid` for Python, `SIGUSR1` plus `why-is-node-running` or the active-handles list for Node. At the same moment, capture `ss -tanp` for socket states and queue depths, `pg_stat_activity` including `wait_event_type` and `state` plus `pg_locks` where `granted = false`, and whatever counters your pool exposes for active, idle, and waiting. One captured hang read this way answers the question outright, and it costs you a single occurrence rather than a week of theorising.

While waiting for that, the discriminating experiments are all about reproducing the CI environment's constraints rather than its code. Run the integration suite in a loop under `docker run --cpus=2` with the memory limit your runner has, output redirected to a file rather than a terminal, and with `GOMAXPROCS` or `UV_THREADPOOL_SIZE` or your framework's pool size pinned to the CI value. If starvation is the cause, this usually reproduces within a few dozen iterations. Independently, set a finite acquire timeout on the pool and a socket-level read timeout on the database driver: if the hang becomes a fast failure with a stack, you have simultaneously identified the layer and made every future occurrence self-diagnosing. Set `max_pool_size` to 1 and run the suite; genuine exhaustion becomes immediate and deterministic rather than rare. Disable test parallelism for one run; lock contention and shared-fixture races vanish, executor starvation and stale-connection hangs generally do not. Finally, check whether the hang occurs at a consistent elapsed time rather than a consistent test, and cross-reference your CI history for jobs that were running concurrently with each hung run. A hang that always arrives around the same number of minutes in points at an expiry (an idle reaper, a credential TTL, a keepalive), and a hang that only ever happens when another job overlaps points at a resource you thought was private.
