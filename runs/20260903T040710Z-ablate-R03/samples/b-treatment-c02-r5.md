The detail worth taking seriously is that the victim is a different test every time. That fact does most of the work of ruling things out. A monotone leak, which is what connection pool exhaustion usually is, drains a fixed budget at a roughly fixed rate, so it tends to bite at a consistent depth into the run: the 340th test, give or take a few, and if the suite is order-randomised, at a consistent test *count* rather than a consistent test name. A uniformly random victim looks much more like a narrow race window being sampled once per test, where any test can lose, than like a resource being used up. So the pool hypothesis isn't crazy, but it makes a prediction you can check cheaply, and my prior is that it fails the check.

The candidates that fit "random victim, integration only, CI only" better fall into a few families. One is a leaked open transaction: a test errors or is interrupted on a path where rollback doesn't run, its session sits idle-in-transaction holding row or table locks, and then some later test that touches the same rows, or does a `TRUNCATE` or schema reset, blocks behind it. Postgres has no default `statement_timeout` or `lock_timeout`, so that block is genuinely forever, not slow. The victim is whichever test happens to collide first, which is effectively random. A second is a missing socket timeout on an HTTP or RPC client. In CI the dependency runs in another container over a bridge network, and connections can die without an RST, or the peer can be OOM-killed mid-request; a read with no timeout then blocks for the life of the job. Locally you talk to loopback or a process that never dies, so you never see it. A third, badly underrated, is a subprocess pipe deadlock: a test shells out, the child writes more than the pipe buffer to stderr, nobody drains it, the child blocks on `write`, the parent blocks on `wait`. This is CI-specific almost by construction, because locally the child's output often goes to a terminal rather than a captured pipe, and because CI environments are chattier with debug logging.

Underneath several of these sits the reason it's CI-only at all. CI runners typically have two cores where your laptop has eight or ten, and a lot of pool sizes are derived from CPU count: thread pools, async executors, and yes, connection pools. A deadlock that needs the pool to be smaller than the number of simultaneous holders may be unreachable at ten cores and reachable at two. Nested acquisition is the classic shape here, where a request holds a connection and then calls something that acquires a second one; with a pool of two and two concurrent tests, that hangs, and with a pool of ten it never does. This is also the version of the pool story that *would* produce random victims, so if you want to keep the pool hypothesis alive, this is its strongest form, and it's distinguishable from simple exhaustion by whether the saturation is instantaneous or gradual.

The way to tell these apart is not more reasoning, it's a stack dump from a hung run. Everything above is a distinct, immediately recognisable stack, and one captured dump ends the argument. Add a step to the CI job that, on timeout, dumps the state of the test process before killing it: `jstack` or `SIGQUIT` on the JVM, `py-spy dump --pid` for Python including `--native` if there's C extension involved, `SIGQUIT` for a Go binary to get all goroutines, `kill -USR1` or the inspector for Node. Alongside it, capture `ps -ef` for the process tree, `ss -tanp` for socket states, and, from the database, `pg_stat_activity` with `wait_event_type`, `state`, and `pg_blocking_pids(pid)`, or `SHOW ENGINE INNODB STATUS` on MySQL. Upload all of it as a job artifact. The usual trap is that CI's own global timeout kills the container without giving you any of this, so the internal timeout has to fire first and the dump has to be written somewhere the artifact collector still sees.

What you read off that is nearly mechanical. Every worker thread parked in `getConnection` or `pool.acquire` while the database shows almost no active sessions means pool exhaustion, and the pool's own checkout-wait metric will have ramped rather than spiked. One thread in a socket read against the database, with `pg_stat_activity` showing it blocked and `pg_blocking_pids` pointing at a session that is `idle in transaction`, means a leaked transaction, and the blocking session's `query` field names the test that leaked it. A stack in a socket read against something that isn't the database, with the peer container's logs ending abruptly or its exit code non-zero, means a missing timeout plus a dependency that died. A child process blocked in `write` with the parent in `waitpid` means the pipe. All threads blocked with the CPU idle is a deadlock; all threads busy with the CPU pegged is a livelock or GC death spiral, which is a different investigation entirely and worth splitting off early since it's a single `top` reading.

Two things make this go faster. Reproduce under CI's constraints rather than yours, by running the integration suite in a loop under `docker run --cpus=2 --memory=<runner size>`, which often takes the rate from one in twenty to one in three. And log the ordering seed on every run so a hanging run can be replayed exactly; when you have the seed and the victim, the culprit is usually a test that ran shortly before, not the one that hung. Independently of the diagnosis, set `statement_timeout` and `lock_timeout` on the test database and a read timeout on every HTTP client used in tests. That doesn't fix the bug, but it converts a hang into a stack trace, and a bug that fails loudly one run in twenty is a fundamentally easier object than one that fails silently.
