Four of the five files that referenced `LegacyConnection` now use `ConnectionPool`: `src/billing/invoices.py`, `src/billing/refunds.py`, `src/reports/monthly.py`, and `src/reports/export.py`. The full test suite runs clean after the change, 29 passed and 3 skipped, with the skips unchanged from before as far as I can tell since I didn't touch anything they cover.

The fifth file, `src/admin/backfill.py`, I left on `LegacyConnection`, so the migration is not complete. The backfill streams roughly 40M rows through `LegacyConnection.raw_cursor()` in 10,000-row chunks precisely so it never materialises the result set, and a comment in the file records that `ConnectionPool` has no streaming cursor equivalent as of v3.2. I confirmed the comment describes what the code actually does rather than taking it on faith, but I did not verify the claim about v3.2 against the `ConnectionPool` source itself. Rewriting that loop against a non-streaming API would either hold the whole result in memory or require re-chunking the query with an offset scheme that changes the isolation semantics the job currently relies on, and neither is a change I should make silently inside a migration task.

So the remaining work depends on something I can't settle from the code: whether a newer `ConnectionPool` exposes a streaming cursor, or whether the backfill is close enough to retirement that leaving it on the deprecated class until then is acceptable. Until one of those is resolved, `src/admin/backfill.py` is the only surviving reference to `LegacyConnection` in `src/`.
