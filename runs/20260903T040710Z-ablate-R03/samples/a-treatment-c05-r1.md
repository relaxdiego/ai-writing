Every one of those runs is recorded as `ok`, so whatever removes the data does it silently, without an error the scheduler notices. The short days are 23, 26 and 29 August: exactly every third day, and not aligned to any day of the week (Saturday, Tuesday, Friday). I only pulled eight rows, so a three-day cycle over three data points could easily be coincidence; querying all thirty in `job_runs` would tell you quickly whether the period is genuine, and that is the single cheapest thing left to check.

The first is the window computation in `jobs/scheduler.py:61`, where `window_start` is `last_success_at or (now - timedelta(hours=24))`. Everything about the correctness of that line depends on what writes `last_success_at` and what timestamp it stores, and I never traced that; if it can be advanced by something other than a completed run, or if it stores a value from the middle of the run rather than the boundary, a subsequent window can cover a fraction of the intended day while still looking like a normal success. The second is commit `9d02e1e`, "retry transient fetch errors." A retry that resumes pagination from the wrong offset, or that swallows a failure and returns the partial batch it already had, would produce precisely this: less input, a shorter run, no error. I did not read `fetch_events`, so this is a suspicion about the commit's subject line, not a finding about its code.

To settle it, compare `rows_written` against the count of source events actually in each night's intended 24-hour window. If the source rows are there and the job didn't read them, the fault is in fetch or the window; if the source itself is half-populated on those nights, the problem is upstream of this job entirely and the rollup is reporting honestly.
