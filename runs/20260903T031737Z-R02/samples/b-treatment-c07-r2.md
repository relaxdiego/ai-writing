I want to flag one thing before anything else, because it's a data leak rather than a performance question. If your queries use bind parameters — `WHERE user_id = ?` or `WHERE tenant_id = :tid` — then the SQL string is byte-identical for every user who runs that code path, while the result sets are completely different. Keying the cache on the SQL text alone means the first user to run a query populates the entry and every subsequent user gets served that user's rows, with the row-level authorization in the WHERE clause silently bypassed because the database is never consulted again. If instead you interpolate literals directly into the SQL, the keys become unique per user, which fixes the leak but also means your hit rate collapses toward zero for exactly the per-user queries you were hoping to speed up, while the dictionary grows one entry per user per query shape and never releases any of it.

The eight-worker topology causes a second problem. A plain global dict lives inside one process, so you get eight independent caches with no shared state and no way for a write handled by worker 3 to invalidate the stale copy sitting in worker 6. At roughly 400 writes per minute, something is being invalidated every 150ms or so, and a user who updates a record and then reloads the page has a 7-in-8 chance of landing on a worker that still believes the old value. Without a TTL or eviction policy, that stale data is permanent, and the dictionary is also an unbounded memory leak that will push each worker's RSS up until the OOM killer intervenes.

None of this means caching is wrong for your app — it means the cache needs a key that captures authorization scope, a store the workers share, and a story for invalidation. What I'd suggest instead:

- **Measure first.** Turn on the slow query log or use your APM to find where the time actually goes. Very often the win is a missing index or an N+1 loop issuing 200 queries per request, and neither of those is fixed by caching — a cache just makes the 200 queries fast instead of eliminating them.
- **Request-scoped memoization** is the safe, cheap version of your idea. A dict that lives for the duration of one request, keyed by SQL plus bound parameters, dedupes repeated identical queries within a single request. Since a request belongs to one authenticated user and the dict dies with it, there's no cross-user leakage and no invalidation problem at all.
- **A shared cache (Redis or memcached) for the genuinely hot reads**, keyed structurally rather than by SQL text — something like `user:{id}:dashboard:v3` — so the key encodes whose data it is. Give entries a short TTL as a backstop and delete the specific keys on write. Your write volume is low enough that explicit invalidation on the write path is entirely tractable.
- **Cache the read-mostly data most aggressively.** Reference tables, config, feature flags, aggregate counts that can tolerate a few seconds of staleness — these give you most of the benefit with almost none of the correctness risk, because they aren't user-scoped in the first place.
- **Check connection pooling and prepared statement reuse** before adding a caching layer. If you're opening a new connection per request or re-planning the same query thousands of times, fixing that is a smaller change with a more predictable payoff.
