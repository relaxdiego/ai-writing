I'd ship it to a separate store, but I'd make that store another Postgres instance rather than a specialised append-only product, and I'd tier the old partitions out to object storage rather than keeping seven years hot.

Start with the volume, because it decides less than people expect. Two million events a day is about 23 writes per second averaged, maybe a few hundred at peak, which is nothing for Postgres. The problem is accumulation: seven years is 5.1 billion rows, and at a realistic 500 bytes to 1 KB per row with indexes you land somewhere between 3 and 7 TB. If that sits in your application database, every operational property of the application database is now set by audit data. Your base backups get an order of magnitude slower, your PITR restore window stretches from minutes to hours, a major-version upgrade becomes a project, and the recovery time objective for the service your customers actually touch is dominated by rows nobody needs urgently during an outage. Splitting the instance is worth it for that reason alone, before any compliance argument.

The append-only requirement is really a statement about privilege rather than about storage technology, and it's worth being precise about it, because "append-only store" often gets treated as a product category when it's a permissions design. Postgres will behave as an append-only log if you grant the writing role INSERT and SELECT only, never grant UPDATE or DELETE on the audit tables to anything the application can reach, partition by month so that retention expiry is a DROP TABLE performed through a separate privileged path, and chain each row's hash to its predecessor so that after-the-fact edits are detectable even by someone with superuser. On a separate instance that credential boundary is real: the application's connection string simply has no route to mutate the log. In a shared database it depends on nobody ever granting the app role too much, which is exactly the kind of control an auditor will discount.

The join requirement is the weakest of the arguments for co-location, and inspecting it tends to flip its direction. An audit event that stores only a user_id and resolves the name, email and role by joining live user records will report today's values for an event from 2021. For a support investigation that's merely confusing; for a compliance record it's wrong, since the point of the log is what was true at the time. So denormalise the actor and target attributes into the event at write time: user id, email, role, tenant, source IP, whatever the investigation actually needs. Once you do that, the vast majority of support queries stop needing the join at all, and the residual ones (find every event by the user who currently owns this email) become a two-step lookup: query the app database for the id, then query the audit store. If you want it to feel like one system, postgres_fdw gives you cross-instance joins at some planning cost, which is fine at the frequency of "occasionally."

For the seven years, don't keep it all in Postgres. Events older than roughly twelve to eighteen months get read almost never, and when they are read it's usually a bounded export for a legal or audit request rather than an interactive query. Keep the recent window in the audit instance where support can query it fast, and roll each expired monthly partition out to Parquet in S3 with object-lock retention, which gives you genuine write-once storage and a cheap answer for the compliance question. Athena or DuckDB reads that fine when someone needs 2022. The storage cost difference over five years of cold data is large enough to notice, and object lock is a stronger tamper story than any grant configuration.

The case for staying in one database is real but narrow: it holds if you want transactional atomicity between the business write and its audit record, so an event can never exist without the change or vice versa. If that property matters to you, the usual compromise is to write the event into a small outbox table in the application database inside the same transaction, then relay it to the audit store asynchronously, which buys atomicity at the cost of a few seconds of lag and a relay to operate.
