I didn't find the cause, so what follows is the state of the evidence rather than a diagnosis.

The short runs are not scattered noise. In the last eight recorded runs, the row counts fall into two tight clusters: 47,760 to 48,440 on the full nights, and 22,104 to 23,902 on the short ones. The short nights are 23, 26 and 29 August, an even three-day spacing that doesn't line up with weekdays (Saturday, Tuesday, Friday). Three points is thin evidence for a period, but it's tight enough that I'd treat "something on a three-day cycle" as a live hypothesis rather than coincidence.

The more useful signal is duration. Full nights take about 15 minutes; short nights take about 7. A job that fetched all the events and then failed to write half of them would take roughly the full time, and a partial write would have aborted the whole transaction and shown a status other than `ok`. The short nights are cheap because there was less work, which puts the fault upstream of `write_rollup`, in `fetch_events` or in the window handed to it.

Two things there are worth pulling on. The first is commit 9d02e1e, which added retries for transient fetch errors. If `fetch_events` paginates and the retry restarts or skips a page rather than resuming it, a single transient error mid-fetch would produce a quietly truncated result set and a run that still reports success. I did not read the fetch implementation, so this is a shape that fits, not something I confirmed. The second is `window_start = last_success_at or (now - timedelta(hours=24))`. Which column feeds `last_success_at` matters: if it's `finished_at` rather than `started_at`, every window is short by the previous run's duration, and a run's own overrun shortens the next window. That mechanism is too small to halve a night on its own, but it's the kind of thing that compounds with a second trigger, and it means a short night's missing events are never re-read on a later night, so the shortfall is permanent data loss rather than a delay.

One caveat on the evidence itself. My count query was wrong for the question I meant to ask: `select count(*) ... limit 30` returns the total row count of `job_runs` for that job, which is 30, not the last thirty runs. So the history is only about a month deep and I've eyed eight days of it. Confirming the three-day period, or killing it, needs the full 30 rows plotted against date.

The discriminating check is on the input side: log the row count returned by `fetch_events` and the actual `window_start`/`window_end` values for each run, then compare a short night against the night before it. If the window is a full 24 hours and the fetch still returns half the events, the retry path is the culprit; if the window itself is short, the scheduler's success-timestamp logic is.
