Your instinct is worth trusting, because the shape of the evidence constrains the answer more than the pool guess does. "Different test each time" is the important part: it argues strongly against a bug in any particular test and toward something shared, and it splits into two quite different stories. Either something accumulates across the run and the victim is simply whichever test asks for the exhausted resource next, or every test is running the same risky pattern and occasionally loses a race. Connection pool exhaustion is one member of the first family, but so is any leaked handle: unclosed HTTP agents, file descriptors, undrained child-process pipes, orphaned transactions. A third possibility that people usually forget is that the test named in the output is not where the process is stuck at all. Most runners report a test as started and then never report a result, so a hang in global teardown, in a reporter flushing to a socket, or in an `afterEach` hook will be attributed to whatever happened to be in flight.

The reason it only happens in CI is almost never mysterious: CI machines have fewer cores, contended IO, and no TTY. A race whose losing window is microseconds on your laptop becomes milliseconds on a throttled two-core container, and something that never lost in a thousand local runs loses one time in twenty there. Non-TTY output changes buffering too, which matters more than it sounds: if any test spawns a subprocess and doesn't drain its stdout, the child blocks forever once the 64KB pipe buffer fills, and it fills only when logging is verbose, which is exactly the CI configuration. Database locks behave the same way. Postgres has no default lock timeout, so one test that leaves an idle transaction holding a row lock will hang the next writer indefinitely rather than erroring, and under parallel workers on a shared database that's a genuine deadlock rather than exhaustion.

Rather than reasoning further about which of these it is, the decisive move is to get a stack out of the hung process, because that single observation collapses the whole space at once. The problem today is that CI kills the job at its own timeout and you get nothing. Fix that first: set a per-test or per-suite timeout comfortably below the job timeout, and install a signal handler that dumps state before the process dies. On the JVM that's `jstack` or `kill -3`; in Go, SIGQUIT already dumps every goroutine; in Python, `faulthandler.register(SIGUSR1)` or an out-of-band `py-spy dump --pid`; in Node you want an async-resource dump along the lines of `why-is-node-running`, since a plain stack will just show an idle event loop. While you're at it, have the same handler shell out for `ss -tanp` and, if a database is involved, `SELECT state, wait_event_type, wait_event, query FROM pg_stat_activity`. A socket stuck in a read, a thread parked on a pool acquire, and a backend waiting on a lock look nothing alike, and you will know within one hang which you have.

There are two cheap experiments worth running in parallel with that. Log the ordinal position of each test as it starts, so that when a hang happens you know whether it was the 30th test or the 300th; accumulation bias toward the end of the run is the signature of a leak, and a uniform distribution across positions effectively rules the leak family out. Then run a nightly job with parallelism forced to one. If the hang survives that, it's a single test interacting badly with a slow environment, and cross-test interference is off the table.

As for the pool theory specifically, it is cheap to falsify rather than argue about. Configure an acquire timeout on the pool, a few seconds, and a `lock_timeout` and `idle_in_transaction_session_timeout` on the database side. If pool exhaustion or a lock is the mechanism, the next occurrence stops being a hang and becomes a loud error with a stack at the point of acquisition, which is most of the diagnosis handed to you. If the run still hangs silently with those timeouts in place, the block isn't happening anywhere your pool or your database can see it, and you should be looking at sockets without timeouts, subprocess pipes, and event-loop-level races instead.
