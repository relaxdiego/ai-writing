I'd go with a separate append-only store as the system of record, but have the events originate in Postgres and keep a rolling recent window there. That's a definite architecture rather than a compromise, and the ordering matters: the archive is authoritative for compliance, the Postgres table is a queryable cache of the last few months.

The strongest reason to write audit events into Postgres first has nothing to do with joins. It's atomicity. If the audit write goes directly to a separate store, you own the dual-write problem: the business transaction commits and the audit event is lost, or the event is written and the transaction rolls back. Both failures are exactly the kind an auditor will ask about, and neither is fixable after the fact. Writing the event in the same transaction as the change it describes gives you the invariant you actually want, which is that an audit event exists if and only if the thing happened. From there, shipping to the archive is an asynchronous, retryable, idempotent job driven off logical decoding or an outbox table, and a failure in that pipeline delays the archive rather than corrupting the record.

The join argument is weaker than it feels. Joining a five-year-old audit event to today's user row tells you the user's current email and role, not the ones in effect when the event was recorded, so for support investigations and especially for anything evidentiary the join is quietly giving you the wrong answer. Audit events should carry denormalized copies of the identifying fields at write time: actor id, email as it then was, role, tenant, IP, session. Once events are self-contained, the join you genuinely need is against recent events for live investigations, and a ninety-day to twelve-month hot window in Postgres covers essentially all of that.

Keeping all seven years in the application database is where it goes wrong. Two million a day is only about twenty-five writes a second, so throughput is a non-issue; the problem is accumulated size. You're looking at roughly five billion rows and several terabytes with indexes, and that mass lands on operations you care about for a completely different reason. Your backups get slower, your restore time balloons, your major-version upgrade window stretches, and your recovery objective for customer-facing data is now hostage to a table nobody queries. Cold audit data in object storage as partitioned Parquet costs a small fraction of provisioned database storage and doesn't participate in any of those operations.

There's also a separation-of-duties point that carries real weight with auditors. If the log lives in the database the application writes to, the application's credentials can in principle rewrite history, and so can anyone with production database access. You can narrow that with a dedicated role, revoked UPDATE and DELETE, and triggers, but the mitigation is only as strong as the people holding superuser. A write-once store with object-lock or equivalent, plus a hash chain over events so any gap or edit is detectable, gives you an answer to "how do you know this wasn't altered" that doesn't depend on trusting your own operators.

Concretely: partition the Postgres audit table by month, keep somewhere between three and twelve months, and drop old partitions rather than deleting rows. Stream to the archive continuously, verify by reconciling counts and hash-chain heads per partition before dropping anything, and give support a query path that hits Postgres for the hot window and the archive engine for older material. Most investigations will never touch the archive.

The case for staying single-database is that this pipeline is real work and a thing that can rot if nobody owns it. If your team can't staff it, a partitioned Postgres table will survive seven years at this volume, and you'd be choosing operational drag over a system you can't maintain, which is a defensible trade. I'd revisit that immediately if event volume grows by an order of magnitude, if payloads get large, or if a customer contract starts specifying tamper-evidence, because any of those turns the drag into a genuine constraint.
