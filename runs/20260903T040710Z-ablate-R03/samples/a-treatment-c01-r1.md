The hard-coded `session_ttl = 3600` in `src/cache/session.py:14` now reads `SESSION_TTL_SECONDS` from `src/config/defaults.py`, which was the only other place the TTL was defined. That was the sole use of the literal; the expiry check at `src/cache/session.py:88` already read the class attribute, so it picked up the change without edits.

Worth being explicit about the consequence: the two values disagreed, and the config constant is 900, so the effective session lifetime drops from an hour to fifteen minutes. If 3600 was the intended production behaviour and `SESSION_TTL_SECONDS` was stale, the fix belongs in `defaults.py` instead, and this commit changes behaviour rather than just removing a duplicate.

`tests/test_session_cache.py` failed on that change, asserting `session_ttl == 3600`, and I updated it to compare against `SESSION_TTL_SECONDS`. The suite is green at 8 passed, but the assertion is now tautological: it compares the attribute to the constant it is assigned from, so it will pass for any value and no longer pins the TTL to anything. If you want that test to keep its teeth, it should assert the concrete number you actually intend, in which case the number belongs in the test rather than the import.
