I didn't find the cause, but the run history narrows it a lot and points at where to look next.

The short runs are not random. Of the last eight runs, three wrote roughly half the rows (23902, 22104, 23551) and each of those finished in about seven minutes, while every full run took around fifteen. So the job isn't dropping rows at write time after doing all the work; it is doing about half the work and exiting cleanly with status `ok`. That rules out a good chunk of the usual suspects, including the transaction in `run()` and anything in `write_rollup`, since a partial write would leave the runtime roughly unchanged.

The candidate that fits the shape is the window. `scheduler.py` computes `window_start = last_success_at or (now - timedelta(hours=24))`, so the window is anchored on the previous run's success timestamp rather than on a fixed daily boundary. That means the window length is only correct if the previous run's `last_success_at` is what you think it is. If `last_success_at` is being written at completion rather than at start, a fifteen-minute run shifts the next window's start forward by fifteen minutes, and any bookkeeping that records it later than intended (or a retry from `9d02e1e` updating it mid-run) would shorten the following window. A window covering about half a day would produce about half the rows in about half the time, which is what the table shows.

To confirm it, I'd want two things I couldn't get from the code alone. First, the actual `window_start`/`window_end` values per run: if they aren't logged in `job_runs`, logging them is a one-line change and the next short run settles the question outright. Second, the definition and write point of `last_success_at`, which lives outside the two files I read. It would also be worth checking whether the short runs correlate with anything upstream, since a source table that is only half-populated at 02:00 on certain days would produce the same signature and the fix would be entirely different.

One thing I'd caution against: the pattern here doesn't look periodic in any clean way across only eight runs, so I wouldn't read the 23rd/26th/29th spacing as meaningful yet. Pull `started_at`, `rows_written`, and duration for all thirty runs in the table and see whether the short runs cluster by weekday or by what preceded them.
