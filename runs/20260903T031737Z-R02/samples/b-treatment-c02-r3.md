Before picking between causes, it's worth noticing that "always a different test" is doing most of the diagnostic work already, and it points away from a bug in any particular test and toward something that either accumulates across the run or fires with some fixed probability per unit of time. Those two shapes leave different fingerprints. If you collect the failures you already have and note *how far into the run* each one died — test number, or elapsed minutes — an accumulating resource leak should bias late, with the hangs clustering somewhere past a threshold, while a race or a timing-dependent block should scatter roughly uniformly across the run. You probably have enough historical CI logs to plot this today without reproducing anything.

That check also happens to be the cheapest test of the connection-pool theory, which makes a second prediction you can falsify in about a minute: a pool only hangs if `acquire` has no timeout. If your pool is configured with a 30-second checkout timeout and the job sits there for an hour, exhaustion is not what's happening, because exhaustion would have thrown. So read the pool config, and if a timeout is set, you can drop that hypothesis and stop arguing about it. If no timeout is set, the fix is to set one regardless — not because it addresses the root cause, but because it converts a silent hang into a stack trace pointing at the leak.

## Get state at the moment of the hang

Everything else is guesswork compared to a thread dump. The structural problem is that CI kills the job at the platform timeout and you get nothing, so set your own job timeout below the platform's — say 20 minutes against a 60-minute limit — and make the timeout path run a diagnostic step rather than exiting. A watchdog thread inside the test process is even better, since it can fire at N minutes of no test-progress and dump before anything is torn down. What you want captured, roughly in order of value: every thread's stack (`py-spy dump --pid`, `jstack`, `SIGQUIT` for Go, `kill -USR1` if you've wired a handler), the database's view of its own sessions (`pg_stat_activity` including `wait_event_type` and `state`, or `SHOW ENGINE INNODB STATUS`), open sockets and their states via `ss -tanp`, and open file descriptor counts. One hang with that data attached usually ends the investigation outright.

## What "never locally" narrows it to

The useful move is to enumerate the axes on which CI actually differs from your laptop, because the bug lives on one of them. Parallelism is the usual first suspect — CI probably runs several workers against one database or one Redis, where you run serially, so two workers take row locks in opposite orders and sit in a lock wait that nothing times out. You can test this directly by running locally with the same worker count and the same test-shuffle seed the failing run used; if you can't reproduce even then, the seed and worker count aren't the variable and you've cheaply eliminated a whole family.

CPU count is the next axis and it's underrated. CI containers are often 2 cores against your 10, and heavy CPU contention doesn't just slow things down, it changes which side of a race wins consistently enough to expose lost-wakeup bugs — a `wait()` with no timeout paired with a `notify()` that arrives before the waiter parks will hang forever, and it only loses the race when the scheduler is starved. Running your suite locally under `taskset -c 0,1` with the workers cranked up simulates this surprisingly well.

The network path is where I'd actually put my money given the "hang forever" symptom. On your laptop everything is loopback, where a connection to a peer that has stopped responding is rare and idle connections are never reaped. In CI you're crossing a container bridge or a cloud NAT, and NAT gateways silently drop idle flows after a few minutes without sending a RST. Any socket read without an explicit timeout then blocks until the OS TCP retransmit timer gives up, which can be well beyond your job limit. A pooled HTTP or database connection that was checked back in, went idle past the NAT window, and then got handed to the next test is exactly the mechanism that would strike at a random test each time. Grep your clients for missing read/connect timeouts and check whether pool idle-recycle is shorter than the gateway's idle timeout.

The last axis is output volume, which produces a genuinely classic hang: CI usually runs with verbose logging on, and if any part of your suite spawns a subprocess while reading only one of its two pipes, the child blocks once the 64KB kernel pipe buffer fills and the parent waits forever on a process that will never exit. Locally the child stays under the buffer and you never see it. If your integration tests shell out to a migration tool, a fixture loader, or a service binary, check that every spawn drains both streams or redirects them to a file.

If I were sequencing this: read the pool timeout config and plot hang position from existing logs today, wire the watchdog dump next, and try the local `taskset` plus high-worker-count reproduction while you wait for the next hang to hit.
