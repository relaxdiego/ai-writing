Before anything else: stop letting CI kill the hung job. Configure the run so that when it stalls you capture a stack dump of every thread in the test process, plus the state of whatever it's talking to. Everything below is inference, and one dump collapses it to a fact.

Your skepticism about pool exhaustion has a cheap test that costs nothing to run. Exhaustion normally shows up as an *exception*, not a hang, because pools have an acquire timeout: HikariCP defaults `connectionTimeout` to 30 seconds, SQLAlchemy's `pool_timeout` to 30, `database/sql` in Go blocks forever by default but only until context cancellation if you pass a context. So go read the config. If there's a finite acquire timeout and your job hangs for the full 45-minute CI limit, exhaustion is falsified outright, because you'd have a `SQLTransientConnectionException` in the log instead. If the timeout is unset or infinite, the hypothesis stays alive and you need the dump to settle it.

The genuinely informative detail is "always at a different test," and it splits the candidates in two. Ask whether the hang happens after roughly the same *number* of tests each run, or at a genuinely random position. Anything that accumulates across the suite (leaked connections, leaked file descriptors, unclosed transactions, growing thread count) crosses its threshold at a near-constant count, and the identity of the victim test varies only because the ordering does. A per-test race, by contrast, is a coin flip each test, so it lands anywhere. Your CI log already contains this data if it prints test names as they start; pull the last-started test and its ordinal from the last ten hung runs and see which pattern you have.

The candidates worth taking seriously, with what each looks like in a dump:

- **Thread pool deadlock from nested submission.** A task submitted to a bounded executor blocks waiting on another task submitted to the same executor. Locally your 10-core machine gives the pool enough slots that the dependency always clears; a 2-core CI runner sizing the pool by `availableProcessors()` does not. In the dump, every pool thread is parked and the work queue is non-empty. This explains "never locally" better than almost anything else.
- **An open transaction blocking a later one.** A test leaves a transaction uncommitted (a swallowed exception in teardown, a rollback that never fires), and the next test's `TRUNCATE`, migration, or update on the same row waits on the lock forever. Postgres shows this as one session `idle in transaction` and another with `wait_event_type = 'Lock'`; `pg_blocking_pids()` names the culprit directly.
- **A socket read with no timeout.** Integration tests talk over real sockets, and CI's container networking drops things localhost never does. One dropped packet against a client with no read timeout is a permanent hang. The dump shows a thread in `socketRead0` or `recvfrom`, and `ss -tanp` shows the connection ESTABLISHED with nothing arriving.
- **Cross-job contention on shared infrastructure.** If your CI jobs share one database, Redis, or a fixed host port rather than getting a per-job container, then two concurrently running branches collide. A 1-in-20 rate is a plausible overlap frequency for a moderately busy repo, and the failing test is random because the collision timing is random. The signature is that the hang correlates with other jobs running, and with nothing inside your own suite.
- **A lost wakeup or unresolved future.** An async callback fires before the waiter registers, or a `CountDownLatch` is never counted down on an error path. Purely timing-dependent, so it hits at a random test, and CI's different scheduling is enough to expose it.
- **Connection or fd leak.** Still on the list. Threads parked in `getConnection`/`acquire` with the pool reporting in-use equal to max is the positive identification, and it should coincide with the constant-count pattern above.

To collect the dump, set your job's own timeout below the platform's hard limit so you still get a cleanup step, and have that step signal the test process. On the JVM, `kill -3` prints a full thread dump to stdout, or `jstack <pid>` if you'd rather have it in a file. In Go, `GOTRACEBACK=all` plus `kill -ABRT` dumps every goroutine. In Python, `py-spy dump --pid <pid>` works without preparing the process, and `faulthandler.dump_traceback_later(seconds, exit=True)` works if you'd rather build it in. In Node, the open-handle question is the whole question, so run the suite under `why-is-node-running`. Capture the database side in the same step: `pg_stat_activity` joined against `pg_blocking_pids()`, or `SHOW ENGINE INNODB STATUS` for MySQL, along with a connection count.

While you wait for a hang to recur, two experiments discriminate cheaply. Run the full suite locally under a CPU quota matching the runner (`docker run --cpus=2`, or `taskset -c 0,1`) in a loop of fifty; if it reproduces, the cause is starvation or a scheduling-sensitive race rather than anything CI-specific. Separately, give the job its own database instance or a uniquely named schema per run; if the hangs stop, it was cross-job contention and nothing in your code is wrong.

Whatever the dump says, set the timeouts you're missing: socket read timeouts, a finite pool acquire timeout, and a per-test deadline in the framework. A hang carries no information and burns a runner slot; the same bug expressed as a timeout failure arrives with a stack trace attached.
