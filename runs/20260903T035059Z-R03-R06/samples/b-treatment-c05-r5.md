I did not find the cause. What I have is a strong pattern and an unverified mechanism, so treat the below as narrowing rather than an answer.

The run history is bimodal rather than drifting: full runs write about 48,000 rows in roughly fifteen minutes, short runs write 22,000–24,000 in about seven. Runtime scales with row count, which argues the job is processing less input rather than losing rows on the way out; a write-side drop would take the same time and produce fewer rows. Every short run is recorded as `ok`, so whatever happens does not raise.

In the eight runs I pulled, the short ones fall on 23, 26 and 29 August, an exact three-day spacing. Nothing weekly, so this is not a weekend or business-day effect. I only looked at eight of the thirty rows in `job_runs`, and three data points is thin enough that the period could be coincidence, so the cheapest next step is to pull all thirty and see whether the spacing survives.

For mechanism, the window comes from `window_start = last_success_at or (now - timedelta(hours=24))`. All eight runs started at 02:00 and all succeeded, so `last_success_at` should sit about 24 hours back every night and the window should be stable. Getting half the rows would need either a `last_success_at` roughly twelve hours stale, or `fetch_events` returning early. `run()` does nothing to bound the fetch, and the `transaction()` block covers only the writes, so a fetch that returned a partial result would commit that partial result and report success, which is the shape we see. The recent `fix: retry transient fetch errors` commit is the obvious suspect: a retry path that returns what it has instead of re-raising would produce short, successful, half-size runs exactly like these. I did not read that code, so this is a hypothesis and not a finding.

The reason I can't close it from the outside is that `job_runs` records no window bounds, so there is no way to distinguish a run that asked for twelve hours of data from one that asked for twenty-four and got half of it back. Logging `window_start`, `window_end` and the count returned by `fetch_events` would separate those two cases within one turn of the three-day cycle. The other possibility I never eliminated is that the input genuinely halves on those days, since I did not count events in the source table over the affected windows.
