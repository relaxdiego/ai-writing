Keyed on the SQL string alone, this will serve one user's rows to another user, and across eight processes it will serve stale rows to everyone. Both are worth walking through before writing any of it.

The authorization problem depends on how your queries are built. If you use bound parameters, the SQL text is byte-identical for every user and only the parameters differ, so a dictionary keyed on that text holds one entry for all users: whoever misses first fills it for everybody else. That is a row-level authorization bypass the WHERE clause cannot defend against, because on the second request the WHERE clause never runs. If instead you interpolate the user id into the string, the keys stay distinct and the bypass goes away, but so does most of the benefit; each user then gets a private cache, and the hit rate collapses to whatever one user's repeat rate happens to be.

Then the process count. A module-level dict is per process, so you get eight independent caches: eight copies of the same working set, each warming separately, and no way for a write handled by worker 3 to invalidate what worker 6 is holding. At 400 writes a minute something is mutating roughly every 150 milliseconds, and with SQL-string keys there is no way to know which cached SELECTs a given UPDATE invalidates, since that needs a map from tables to keys. Without one, entries stay stale until eviction, and an unbounded dict never evicts, which is also a slow memory leak.

Here is what I would do instead. Start by measuring: turn on `pg_stat_statements` or the slow query log and find where the time actually goes. In most applications this size it is a few N+1 loops and one or two missing indexes. Caching a query that is slow because of a missing index buys you speed, keeps the bug, and adds an invalidation problem on top.

Then split the queries by whether their results are user-scoped. The ones that are not, meaning your reference data such as plans, tags, feature flags, country lists, are safe to cache in exactly the way you described: a per-process dict with a size cap and a TTL of a minute or two. That is an afternoon's work, it needs no new infrastructure, and it is the part of your idea that is straightforwardly right.

For the user-scoped queries, if measurement says they matter, put them in Redis or memcached so all eight workers share one copy, and build the key from the authorization scope plus the query plus the bound parameters. That makes scope part of the identity of a cache entry rather than something a WHERE clause is trusted to have applied earlier. Invalidate on write by tagging each entry with the tables it read and dropping those tags on mutation. Where you can, cache the assembled object or response rather than raw rows: the hit is worth more and there are far fewer entries to keep honest.
