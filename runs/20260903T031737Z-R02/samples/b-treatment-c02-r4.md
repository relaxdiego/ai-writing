Your skepticism is well placed, though not because the pool theory is wrong — it's that "pool exhaustion" names the last link in a chain rather than a cause. A pool empties either because connections are leaked (never returned) or because every connection is checked out and blocked on something else, and those are completely different bugs with the same downstream appearance. Even confirming an empty pool at hang time only moves the question one step.

Start with what the symptom pattern already rules in and out. A different test every time means the bug is not in any test; it's in something shared — a fixture, a global, a connection, a background thread, a dependent service — where the test that hangs is the victim rather than the culprit. That the suite hangs rather than fails means some wait is unbounded: a lock acquire, a socket read, a queue receive, a future that never resolves, a `wait()` on a process that already died. Somewhere in the stack a timeout is missing or set to infinity, and that's true independent of which hypothesis turns out to be right. "Never locally" is the most informative fact of the three, because the list of things that genuinely differ is short and enumerable: worker/parallelism count, visible CPU count (especially with cgroup limits that runtimes misread), whether stdout is a TTY or a pipe, log verbosity, whether services are on a Docker network with NAT and conntrack idle timeouts, test ordering and shuffle seed, and cold caches making startup races winnable.

One caveat before you interpret any log: with buffered output the last line you see is not where the process is stopped. If the harness or the language runtime buffers when not attached to a TTY, "hung at test X" can mean "hung somewhere after X's last flush," which may be teardown, the next test's setup, or a reporter shutting down. Confirm where the process actually is before you spend a day on the wrong test.

## The mechanism families worth separating

**Leak-driven pool exhaustion** is the hypothesis on the table. It predicts accumulation, so hangs should cluster late in the run rather than land uniformly, and it predicts that shrinking the pool makes things dramatically worse in a specific way. If your CI shuffles test order, a leak also produces a different victim each run, which is why this theory survives the symptom report at all — but if order is fixed and the hang still moves, a simple leak is hard to sustain.

**Database lock contention** is the one most often misdiagnosed as pool exhaustion. Parallel workers sharing one database, one test leaving a transaction open (or an `ON CONFLICT`/upgrade lock ordering issue), and every other connection piles up behind it. Downstream this looks identical — no connections available, everything stalled — but the connections are checked out and *busy*, not leaked. Postgres will tell you the difference immediately from `pg_stat_activity` and `pg_locks`, and most databases have no default lock timeout, which supplies the missing bound.

**Thread or async-worker starvation** explains "never locally" better than anything else on this list. Runtimes size their worker pools from the CPU count, CI containers often expose fewer effective cores, and a blocking call inside an async context that's harmless with twelve workers deadlocks with two. Sharded pipelines make this worse because runners are contended.

**A lost-wakeup race** — the test registers a listener after the event it's waiting for already fired, or a webhook/callback arrives before the receiver is ready — is timing-dependent, hence rare, hence sensitive to machine speed and load. The victim is whichever test happens to lose, which fits "always different" cleanly.

**Order-dependent state pollution** covers a mocked clock never restored, a patched socket layer, a paused scheduler, a global registry left dirty. Here the culprit is fixed and the victim is arbitrary, and shuffle seeds turn it into a 1-in-20 event.

**Environmental kills and plumbing** round it out and are cheap to exclude: a sidecar OOM-killed while the test waits forever on a socket to a dead service, a subprocess blocked writing to a pipe nobody drains (64KB fills only when a test logs enough, and CI usually logs more), or a connection idled out by conntrack with no keepalive so a read blocks until the heat death of the runner.

## Make the next hang self-diagnosing

Guessing between six mechanisms from logs is slow; capturing state once settles it. The critical detail is that CI job timeouts destroy the evidence, so you need a watchdog that fires *below* the job timeout, dumps, and uploads as an artifact. Have it capture thread stacks for every thread (`SIGQUIT`, `jstack`, `py-spy dump --pid`, whatever your runtime offers), the async task tree if you have one, pool metrics broken into in-use / idle / waiters, `ss -tanp` for socket states and counts, open fd count, `pg_stat_activity` with `wait_event_type` and `pg_locks`, the shuffle seed and the full executed test order, and container/kernel state for OOM events. That single artifact distinguishes every hypothesis above on sight: waiters queued against a full pool with idle connections says leak; connections active with `wait_event_type = Lock` says lock contention; all workers parked in blocking calls with a non-empty run queue says starvation; a parked future with a completed producer says lost wakeup; a socket in `ESTABLISHED` with no peer says conntrack.

While you're there, add bounded timeouts to pool checkout, HTTP clients, socket reads, and lock acquires. It won't fix anything, but it converts silent hangs into failures with stack traces and moves you from one data point every twenty runs to one every time it happens.

## Cheap experiments that discriminate fast

Shrinking the connection pool to one or two is the decisive test for your colleague's theory — a real leak turns 1-in-20 into 20-in-20 and moves the hang much earlier in the run, while no change at all effectively kills the hypothesis for the cost of one config line. In parallel, pull hang positions out of your existing CI history and check whether they're biased toward the end of the run or uniform, since accumulation and races have different distributions and you already own that data. Then close the local/CI gap deliberately rather than in aggregate: run with CI's worker count against a shared database, with CPU limits applied, with CI's log level, and with output piped rather than attached to a terminal. If a recorded seed reproduces, delta-debug the test list down to a minimal culprit/victim pair, which is by far the fastest route when order-dependent pollution is the real story. It's also worth checking whether failure rate correlates with runner load or time of day, because a correlation there points at starvation and preemption rather than anything in your code.
