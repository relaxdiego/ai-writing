The shape of the idea is fine, but the key is where it breaks. If your queries are parameterised, which they should be, then the SQL string is identical for every user and the user id travels separately in the bind parameters. A cache keyed on the SQL text alone would therefore serve the first user's rows to the second user who runs the same query, and since your authorisation lives in the WHERE clause, that is an authorisation bypass rather than a stale-data bug. The only version where the key is safe is the one where the user id is interpolated into the SQL text itself, which trades the leak for an injection risk and gives you a near-zero hit rate anyway, because every user gets their own key. I can check which style your query layer uses if you point me at it.

The second problem is that 400 writes per minute against a cache with no invalidation means results start lying almost immediately. A short TTL bounds how stale they get but does not fix read-your-own-writes: a user saves a form, the next page load hits a cached read, and their own change has vanished. That class of bug gets reported as data loss and is miserable to reproduce.

The third is the eight workers. A module-level dict is per process, so you would have eight independent caches with eight copies of the data, and consecutive requests from one user would hit different workers and get different answers. A plain dict also never evicts, so it grows until the worker is killed.

What I would do instead, in order. First, find out which queries are actually slow, using pg_stat_statements or the slow query log rather than guessing; in most applications this size the answer is a couple of missing indexes and an N+1 loop in a serialiser, and fixing those is faster than any cache and carries no correctness risk. Second, add per-request memoisation, which is close to what you were asking for and is safe: a dict on the request object, keyed by query plus parameters, thrown away when the response is sent. It collapses the repeated identical queries that a single page tends to issue, and it cannot go stale because a request is a single point in time. Third, if there is still a hot read after that, cache it deliberately in Redis so all eight workers share one copy, keyed by the user id along with the query and parameters, invalidated explicitly when the underlying rows are written and given a short TTL as a backstop.
