I'd keep it in Postgres, but not on the same lifecycle as your application tables: one partitioned audit table in the same database, written in the same transaction as the change it records, with old partitions detached and archived to object storage after a hot window. The binary framing is what has the team split, because the two things people want from the separate store, an audit write that can't diverge from the data and an archive that can't be tampered with or dragged around by the application, come apart cleanly.

The strongest case for staying in Postgres is that it makes the write correct by construction. Any external store forces you to pick a moment to ship: before commit, and you record events for transactions that later roll back; after commit, and you lose events whenever a process dies in the gap. The usual repair is a transactional outbox with a relay process, which does work, but you have now built and must operate a delivery pipeline with retries, ordering, and deduplication, all to reproduce what a single INSERT inside the existing transaction gives you for nothing.

Volume is not the argument on either side. Two million events a day is about 23 writes a second on average, which Postgres will not notice. The accumulated size is a different matter: roughly five billion rows over seven years, a few terabytes of heap depending on payload, and quite possibly more than that again in indexes on actor, target, and timestamp. Left in one table, that mass rides along in every base backup, every replica rebuild, and every major version upgrade, and it makes your recovery time for the application database a function of data nobody needs online. Monthly partitioning turns it into 84 partitions of about 60 million rows each, and once partitions are detachable you can keep something like the last twelve to eighteen months hot and push the rest to Parquet in object storage.

Append-only is worth being precise about, because it is a permissions property rather than a storage property, and a separate store does not confer it automatically. In Postgres you get most of the way by revoking UPDATE and DELETE on the audit table from every application role and letting only a retention role drop whole expired partitions. What you cannot get from Postgres alone is tamper-evidence against someone with administrative access, which is usually the thing an auditor is actually asking about. Archiving detached partitions to S3 with Object Lock in compliance mode, or the equivalent, gives you genuine WORM for the six-plus years that make up the bulk of the retention obligation, and it does so without putting the write path behind an external system.

The join requirement deserves a harder look, because it is weaker than it sounds and it is pushing the decision more than it should. Support investigations overwhelmingly concern recent activity, so a hot window in Postgres covers them with ordinary SQL. More importantly, an audit record should capture what was true at the time of the event, not depend on a foreign key into mutable state: if you store only user_id and the user is later renamed, re-roled, or deleted, the join returns the wrong answer or none at all. Denormalizing actor email, display name, and role onto the event at write time is the correct audit semantics independently of where the data lives, and it has the side effect of making archived partitions self-contained.

I'd go the other way in a few specific cases. If your compliance regime names an independent or third-party-held log, that settles it regardless of engineering preference. If audit events originate in several services rather than one application, a central store fed by per-service outboxes is the more honest architecture, since the transactional argument only holds for events produced by the service that owns the database. And if the application database is already near its operational ceiling on connections, IO, or maintenance windows, adding several terabytes to it is not a change you want to make on architectural grounds alone. One thing to settle before you commit to seven years of immutable records with denormalized personal data in them: erasure requests. Audit logs generally survive them on legal-obligation grounds, but Object Lock means you are choosing that answer permanently at write time, so it should be a decision your privacy counsel has actually made rather than one the storage configuration makes for you.
