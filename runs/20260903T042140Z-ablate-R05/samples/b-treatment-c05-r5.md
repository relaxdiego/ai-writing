I didn't find the cause, but the run history narrows it considerably and points at where to look next.

The short runs are not random. Of the last eight runs, three wrote roughly half the rows (23902, 22104, 23551) and each of those finished in about seven minutes rather than the usual fifteen. The job status is `ok` in every case, so nothing is erroring out and being swallowed; the short runs genuinely have less work to do. That rules out a partial write or a crash mid-loop, and moves suspicion onto the input window rather than the write path.

The window is computed in `jobs/scheduler.py` as `last_success_at or (now - timedelta(hours=24))`. That is the piece I'd examine first. If a prior run's `last_success_at` is recorded at a time later than the actual start of its window, the next run starts from that later point and covers less than 24 hours, which would produce fewer rows in less time and still report success. The bad dates I have (26th, 29th, and the 23rd from the tail of the list) are two to three days apart, which is consistent with something stateful rather than a daily coincidence, but eight rows is not enough to establish a pattern and I did not verify what `last_success_at` actually holds.

Two things would settle it. First, query the recorded window bounds per run rather than just start and finish times: `select started_at, window_start, window_end, rows_written from job_runs where job='nightly_rollup' order by started_at desc limit 30` (if those columns aren't persisted, adding them is worth doing on its own). If the short runs show a window materially narrower than 24 hours, the cause is in the scheduler's bookkeeping and the code above is where it lives. Second, check where `last_success_at` is written, which I did not trace; `9d02e1e` added retries to fetch errors and it's worth confirming that a retried run doesn't update that timestamp in a way that shortens the following window.

I should be clear about what I did not check: I never read `fetch_events`, so an upstream source that is itself sometimes incomplete at 02:00 remains an alternative explanation that the timing evidence fits equally well. The seven-minute runs tell us the job saw less data; they don't tell us whether the window was too narrow or the data wasn't there yet.
