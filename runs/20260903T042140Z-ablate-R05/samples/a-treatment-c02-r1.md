Your skepticism is half right. The pool theory has the correct shape but may have the wrong noun in it. A hang that lands on a different test every time, only under CI, almost always means some resource shared across tests is being leaked or contended, and the test that hangs is the victim rather than the cause: it is simply the next one to ask for the thing that ran out. Before going further, check whether your runner randomizes test order per run. If it does, "always a different test" is exactly what a single deterministic culprit would look like, and the observation carries much less information than it seems to.

Connections are one candidate resource among several that fit equally well. A pool with no checkout timeout will block forever once every connection is held by a leaked transaction, which is the classic version. But a thread or executor pool sized from CPU count deadlocks the same way when a task submitted to the pool blocks waiting on another task in the same pool; your laptop has enough cores to hide it and a CI container capped at one or two does not. A socket with no read timeout will hang indefinitely when the CI network path silently drops an idle connection, and NAT conntrack tables commonly evict at five or fifteen minutes, so watch for hangs that begin after a suspiciously round idle interval. If any integration test spawns a subprocess, a full pipe buffer will deadlock parent and child against each other, and CI often turns log verbosity up far enough to cross the 64KB threshold that local runs never reach. Parallel workers sharing one database schema can also block on row or advisory locks in a way a serial local run never produces.

The way to tell these apart is to stop reasoning from priors and get a stack dump out of the hung process. Set a job timeout below whatever your CI platform enforces, and have that timeout trigger a dump of every thread in every relevant process rather than a bare kill: `py-spy dump --pid` for Python, `jstack` for the JVM, SIGQUIT for Go, `--report-on-signal` or `why-is-node-running` for Node. Capture `ss -tanp` and the database's own view at the same moment, meaning `pg_stat_activity` with `state` and `wait_event` for Postgres or `SHOW ENGINE INNODB STATUS` for MySQL. The hypotheses separate cleanly in that output. Pool exhaustion shows every worker parked in an acquire call, with the database side reporting connections idle in transaction. Executor starvation shows workers blocked on a future that only a queued task could complete. A lock fight shows `wait_event_type` of Lock and a visible blocker. A pipe deadlock shows the child in write and the parent in waitpid. A dead socket shows a thread in recv against a connection the peer has long since forgotten.

Two cheap changes are worth making regardless of which one it turns out to be. Put a finite timeout on every blocking operation, especially pool checkout and socket reads, so the failure surfaces as an error with a stack instead of silence. And log the test that finished immediately before the hang along with the random seed, because with a leaked resource the informative name is the leaker's, not the victim's. If one particular predecessor keeps showing up across incidents, you have your answer without needing the dump at all.

To reproduce it locally, match the CI constraints rather than the CI script: same image, same worker count, `--cpus=1 --memory=2g`, same log level, then loop the suite a hundred times. If forcing the suite to run serially makes the hang go away entirely, the cause is cross-test interference and you can stop considering everything else.
