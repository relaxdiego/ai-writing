Four of the five call sites are migrated to `ConnectionPool`: `src/billing/invoices.py`, `src/billing/refunds.py`, `src/reports/monthly.py`, and `src/reports/export.py`. The full suite runs clean afterwards, 29 passed and 3 skipped, and the skips were not ones I looked into, so I can't tell you whether any of them cover the paths I touched.

The fifth, `src/admin/backfill.py`, I left on `LegacyConnection`, so a grep for the class still returns one hit. The backfill streams roughly 40M rows through `LegacyConnection.raw_cursor()` in 10,000-row chunks, and a comment in the file records that `ConnectionPool` has no streaming cursor as of v3.2. I confirmed the comment rather than the library itself. Swapping in the pool without a streaming equivalent would materialise the whole result set, which is the failure mode the current code exists to avoid, so this one needs either a streaming API on `ConnectionPool` or a rewrite of the backfill into bounded keyset-paginated queries that each open and close a pooled connection. Both are larger than the mechanical substitution the other four needed, and the second changes the isolation guarantees, since the migration currently runs the whole scan inside one `repeatable_read` transaction and paginated batches would not.

If the goal is to delete `LegacyConnection` outright, that last file is the blocker and the decision about which of those two routes to take is worth making before anyone writes the code.
