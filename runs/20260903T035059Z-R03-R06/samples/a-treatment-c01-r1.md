`src/cache/session.py` carried its own `session_ttl = 3600` as a class attribute, so the expiry check in `get()` (src/cache/session.py:88) never saw `SESSION_TTL_SECONDS = 900` from src/config/defaults.py. I pointed the class attribute at the config constant instead. That broke `tests/test_session_cache.py::test_expiry_boundary`, which had pinned the literal `3600`, so I changed the assertion to compare against `SESSION_TTL_SECONDS`; the file now passes all 8 tests. A grep for `session_ttl` across `src/` turned up only those three sites, so nothing else was reading the old value.

Two consequences you should weigh. Sessions now expire after 15 minutes instead of an hour, which is a real behaviour change for anyone holding a session across a coffee break, and if 3600 was the value production has actually been running on, the fix is to raise `SESSION_TTL_SECONDS`, not to keep the shadowing attribute. The repaired test is also weaker than the one it replaced: it asserts the attribute equals the constant it is now assigned from, which holds for any value and would no longer catch a reintroduced override that reads from config and then overwrites it. If the intent of `test_expiry_boundary` was to pin the boundary itself, it should build a cache, age one entry past `SESSION_TTL_SECONDS` and one just under, and assert that only the first is evicted.
