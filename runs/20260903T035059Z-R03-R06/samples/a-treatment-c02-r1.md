The pool theory is plausible but the evidence you have doesn't support it any better than half a dozen alternatives. "A different test every time" is what almost every resource-level or timing-level fault looks like, because the test that hangs is just the one that happened to be running when the shared condition went bad. The same is true of "only in CI." So neither observation narrows anything, and arguing about which cause is most likely is less productive than making the next hang produce an artifact that names it.

The useful reframing is that a hang is two separate defects stacked on each other. Something goes wrong (a leak, a race, a dead dependency, a lock cycle), and then some wait in your stack has no deadline, so the wrong thing becomes an indefinite block instead of an error with a traceback. The missing deadline is usually the cheaper of the two to fix, and fixing it converts a one-in-twenty mystery into a one-in-twenty ordinary test failure that tells you where it happened.

As for what the first defect could be, connection pool exhaustion is on the list: a leaked connection per failed test, an acquire with no timeout, and eventually every checkout blocks forever. But it has company. A transaction can be waiting on a row or table lock held by a peer worker, or by a background job the suite started, in a wait that Postgres will not break because it isn't a cycle and there's no `statement_timeout` set. A client can be blocked in `read()` on a socket to a service container that was OOM-killed or restarted, with no socket timeout configured, which is the default in more HTTP and driver libraries than people expect. A test that spawns a subprocess and captures its output can deadlock when the child fills the ~64KB pipe buffer while the parent sits in `wait()`, which explains "never locally" precisely, since locally that output goes to a terminal rather than a pipe. A parallel test runner can lose a worker to the container memory limit and then wait forever for a result that will never arrive, so the coordinator looks hung while the real event was exit code 137. Code that forks while another thread holds a lock (a logging lock, an allocator lock in a native library) deadlocks the child immediately, and CI often forks more workers than your laptop does. And some fraction of apparent hangs are not hangs at all but severe slowness under a CPU quota, where a job-level timeout fires before a real operation completes.

Why CI and not your machine comes down to the differences that change timing and buffering rather than logic: stdout is a pipe instead of a tty, there are cgroup CPU and memory limits with no swap, worker parallelism is usually higher, caches are cold, and dependent services are containers on a shared network that can be restarted or throttled underneath you.

The instrument that separates all of this is a stack dump taken from the hung process before the platform kills it. Set your own timeout below the CI job timeout and have it dump rather than terminate. For Python, `faulthandler.dump_traceback_later(600, exit=True)` with `all_threads=True`, or attach out of band with `py-spy dump --pid <pid>`; for the JVM, `jstack` or `kill -3`; for Go, `SIGQUIT` dumps every goroutine; for Node, `why-is-node-running` or a SIGUSR1 inspector attach. Take two dumps thirty seconds apart, because that distinguishes blocked from merely slow better than any single snapshot. Capture alongside it `ss -tanp` for socket states and counts, `pg_stat_activity` joined against `pg_locks` for waiters and their blockers, `docker ps -a` for containers that died, and the cgroup `memory.events` or `dmesg` for OOM kills. Upload all of it as a build artifact.

Each hypothesis then reads differently. Exhaustion shows exactly pool-max threads parked in an acquire call and no more, with your open connection count pinned at the limit. A lock wait shows a thread inside the driver's socket read, and `pg_locks` names the blocking PID. A dead dependency shows a socket in `ESTABLISHED` or `CLOSE_WAIT` to a container that isn't running. A pipe deadlock shows the parent in `waitpid` and the child blocked writing. Starvation shows threads that have moved between your two dumps.

If you want a cheap discriminator before any of that lands, the pool theory has a one-line test: give the pool an acquire timeout of ten seconds and log pool statistics on failure. If the hypothesis is right, the next occurrence becomes an explicit timeout error that also points at the leak site; if the hang survives unchanged, exhaustion is ruled out. In the same spirit, set a socket timeout, a `statement_timeout`, and a per-test timeout in the runner, so every unbounded wait in the suite has a bound. And since one in twenty is too slow a feedback loop for guesswork, put a branch job in place that runs the integration suite in a loop and logs every test start and finish with worker ID and timestamp. Twenty hangs' worth of "which tests were in flight together" will tell you whether the failures cluster by co-running pair, by position late in the run, or by worker count, and those three patterns point at a race, a leak, and a contention limit respectively.
