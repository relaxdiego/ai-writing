The images are almost certainly stored with an EXIF orientation tag that your upload pipeline is discarding, and the fix is to rotate the pixels physically at ingest rather than relying on metadata to travel with the file.

Phone cameras write pixels in the sensor's fixed order regardless of how you were holding the device, then record how the viewer should turn them in an EXIF tag called Orientation. It takes eight values, covering the four rotations and their mirrored variants. The phone's gallery honours it, Preview and the Photos app on your laptop honour it, and since around 2020 so do Chrome, Firefox and Safari for plain `<img>` elements. Everything you have checked by hand agrees, because every one of those readers is looking at the tag. Somewhere between the upload and the stored file, your pipeline is resizing or re-encoding in a way that keeps the sensor-order pixels and drops the metadata, so by the time the browser sees the derivative there is no instruction left to honour. That explains both of the puzzling parts: it is deterministic because the same input file and the same transform produce the same output every time, and it affects only some photos because a picture taken in the orientation the sensor natively favours gets Orientation 1, which is a no-op, while portrait shots and upside-down landscape shots get a tag that actually matters. Screenshots, downloaded images and photos from the handful of Android cameras that rotate pixels in hardware are unaffected for the same reason.

You can confirm this in a minute with `exiftool -Orientation` run against an original upload and against the derivative your site serves. Expect a value like "Rotate 90 CW" on the original and nothing at all on the derivative.

The repair is to normalise orientation as the first step of ingest, before any thumbnail or derivative is generated, so that every stored variant is upright in its raw pixel order and the tag is either set to 1 or gone entirely. Each of the common libraries has this built in:

- Pillow: `ImageOps.exif_transpose(img)`, which applies the transform and clears the tag.
- sharp: call `.rotate()` with no arguments, before `.resize()`.
- ImageMagick: `-auto-orient`, and it must appear before the resize operator on the command line.
- libvips: `autorot`, which `vipsthumbnail` already applies by default.

Do this on the way in rather than fixing it in CSS. `image-orientation: from-image` is the browser default already, so it buys you nothing here, and any consumer that is not a browser (a canvas export, a PDF generator, a partner API, an ML pipeline) will still see sideways pixels. Normalising once at the boundary means nothing downstream has to know the tag exists.

That leaves the images you have already stored. If you kept the untouched originals, re-run them through the corrected pipeline and regenerate derivatives. If you did not, and the pipeline stripped EXIF on the way in, the rotation is not recoverable from the file: the only options are asking users to re-upload, or leaving them and offering a manual rotate control in the UI, which is worth having regardless for scanned images and other cases where no tag was ever present. One caution while you are in this code: stripping EXIF is usually deliberate, because it removes GPS coordinates from user photos. Keep stripping it, just apply the orientation first.
