I migrated four of the five files off `LegacyConnection`: `src/billing/invoices.py`, `src/billing/refunds.py`, `src/reports/monthly.py`, and `src/reports/export.py` all now use `ConnectionPool`. The test suite passes (29 passed, 3 skipped), and a repeat grep confirms those four are clean.

The fifth, `src/admin/backfill.py`, I left on `LegacyConnection`, and it needs your decision rather than mine. The backfill streams roughly 40M rows through `LegacyConnection.raw_cursor()` with a chunk size of 10,000, under a `repeatable_read` isolation level, and a comment in the file states that `ConnectionPool` has no streaming cursor equivalent as of v3.2. I did not verify whether that comment is still accurate against the version you have installed. Rewriting it against the pool's ordinary cursor would materialise the full result set, which is the exact thing the current code exists to avoid, so a naive migration there would likely take the process down on memory.

There are three plausible ways forward. If a newer `ConnectionPool` has since added streaming support, the migration is straightforward and the comment is simply stale. If not, the backfill could be reworked to page through the query with an indexed keyset cursor, which trades the streaming dependency for a different consistency story, since the `repeatable_read` snapshot would no longer cover the whole run. Failing both, `backfill.py` stays on `LegacyConnection` as a documented exception until the pool grows the capability.

The 3 skipped tests I also did not investigate; I don't know whether any of them cover the backfill path, which would matter for judging how much of a safety net you have on that file.
