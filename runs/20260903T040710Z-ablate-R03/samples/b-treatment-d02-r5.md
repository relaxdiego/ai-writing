**Fix permanent lockout when rate-limit keys lose their TTL**

The rate limiter incremented a counter and then set its expiry as two separate round trips to Redis, with a conditional in between that only issued `EXPIRE` when the counter came back as 1. If the process died or the connection timed out in that gap, the key survived with no TTL and no subsequent call would ever set one, since the counter was past 1 by then. The key stayed above the limit forever and the caller was rate-limited indefinitely. This is what happened in the recent production incident: roughly 40 users were locked out until their keys were deleted from Redis by hand.

The fix sends both commands in a single pipeline, so Redis applies them together rather than leaving a window where the counter exists without an expiry. The `EXPIRE` now carries `nx=True`, which makes it set the TTL only when the key has none. That preserves the original intent of the `count == 1` check, refreshing the window only on the first request rather than sliding it forward on every hit, while also repairing any key that somehow reaches this path without a TTL.

The new test in `tests/test_ratelimit.py` covers the crash case directly, asserting that a key created through `check` always carries an expiry, so a regression that splits the two commands apart again will fail rather than wait for another incident to surface it. Existing keys stuck without a TTL from before this change still need to be cleared manually; the `nx=True` behaviour only helps keys that go through `check` again, which a permanently locked-out caller may not do if they have given up retrying.
