Move the files to a storage service and keep a reference in your database.

At your size the decision is mostly about who has to operate the thing. A shared disk is the smaller code change, and that is its whole appeal: mount the same volume on all three machines and the existing upload paths keep working. What you get in exchange is a new stateful component that four people now own. It has to be backed up, monitored, resized before it fills, and kept alive, because once three web machines all read their files from it, its availability is your site's availability. Network filesystems also have sharp edges that only show up under load, around locking, metadata latency and stale handles, and debugging those is a bad use of a four-person team's month. Object storage moves all of that to a vendor whose durability guarantees you are not going to match with an NFS export.

The cost comparison also runs against shared disk, and not by a little. Two hundred gigabytes in S3-class storage is roughly five dollars a month; the same 200GB on a managed elastic filesystem is around sixty. Your growth of 10GB a month is noise in the first case and a slow leak in the second. Neither number will decide anything on its own, but they point the same direction as the operational argument.

Be clear-eyed about what the move costs you. Every place in the code that treats an upload as a path on a local filesystem has to change, and anything that shells out to a tool expecting a real file (thumbnailing, PDF text extraction, virus scanning) now needs an explicit download to a temp file first. You also inherit an access-control problem you did not have before: the bucket must be private, and downloads should go through short-lived presigned URLs generated by your app after it checks that the requester owns the file. A public bucket is the standard way this goes wrong. Since you accept documents as well as photos, serve them from a domain separate from your main app, or with `Content-Disposition: attachment` and a forced content type, so an uploaded HTML file cannot run script against your users' sessions.

A migration that does not require downtime looks like this:

1. Put a small storage interface in front of the current filesystem code, with `put`, `get`, `delete` and `url_for` as the only operations the rest of the app knows about.
2. Add a column to the files table for the storage key, and start writing new uploads to both the local disk and the bucket, reading from disk.
3. Backfill the existing 200GB with a script that walks the table, uploads anything missing, and records the key. This is a background job that can run for days; there is no rush.
4. Flip reads to the bucket behind a config flag, with a fallback to disk if the key is null. Watch error rates for a week.
5. Stop the dual write, then delete the local files once you have confirmed the bucket has everything and your backups of it are real.

Two details worth getting right at step two. Store an opaque key such as `uploads/2026/09/<uuid>/<sanitised-name>` rather than a full URL, so changing bucket, region or provider later is a config change and not a data migration. And use a provider with an S3-compatible API, which most now are, so that the same client library points at Cloudflare R2, Backblaze B2 or a self-hosted MinIO if the pricing or the relationship stops working for you.

The one case for shared disk is a hard deadline inside the next couple of weeks where the three-machine cutover cannot wait for an application change. If that is your situation, mount the shared volume as a bridge, ship the cutover, and treat the object-storage migration as the next piece of work rather than as something you skipped. What is not a solution is sticky sessions pinning each user to the machine that holds their files: it papers over the upload path while leaving background jobs unable to find files, and it turns any single machine's death into permanent data loss for that machine's users.
