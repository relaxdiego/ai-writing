I'd write the events into Postgres inside the same transaction as the change they describe, keep a short window there, and ship everything to an append-only object store for the seven-year tail. That is neither option as posed, but it's where I'd land, because each camp is right about a different part of the problem.

The same-database camp is right about the write path. An audit event that isn't committed atomically with the action it records can be lost in a crash or a rollback, and "the log is missing the one event the auditor asked about" is the failure mode that actually costs you. If you ship directly to an external store you need an outbox table in Postgres anyway, so you end up writing to Postgres either way; you may as well make that table the audit table.

The separate-store camp is right about the tail. Note that throughput is not your problem: 2 million events a day is about 23 per second, which Postgres will not notice. Accumulation is the problem. Seven years is roughly 5.1 billion rows, and at a guess of 500 bytes per event that's around 2.5 TB before indexes. That volume doesn't break Postgres, but it does take over the operational profile of the database you care most about: backup and restore windows, vacuum behaviour, replica rebuild time, major-version upgrades, and the cost of keeping multi-terabyte SSD storage replicated when the same data sits in Parquet on S3 for a couple of hundred gigabytes and a rounding-error monthly bill.

The join requirement is weaker than it looks, and partly an argument against co-location. Joining a seven-year-old audit event to a live user record tells you what is true now, not what was true when the action happened. If someone's role or email changed, or the row was deleted under a GDPR request, the join either lies or returns nothing. Audit events should carry a snapshot of the actor: user id, email, role, tenant, as of the moment of the event. Once you've denormalised that, the join you actually need for support work is mostly gone, and what remains is answerable within the recent window.

Concretely: partition the audit table by day or week, retain 30 to 90 days locally, and let support run ordinary SQL joins against that window, which will cover the large majority of investigations. A shipper copies sealed partitions to object storage as Parquet with Object Lock set to seven years, then drops the local partition. Older investigations go through Athena or DuckDB over the archive: slower, and rare enough that slower is fine. Revoke UPDATE and DELETE on the local table from the application role so the only privileged operation is partition drop, and if your compliance regime wants tamper evidence rather than just retention, hash-chain each partition and record the terminal hash separately.

The one thing I'd rule out is the plain version of option A, an unpartitioned audit table growing to five billion rows beside your application data. That is the choice that is easy for a year and expensive to undo in year three.
