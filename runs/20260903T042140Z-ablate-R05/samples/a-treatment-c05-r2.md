I could not pin this down, so here is what I have and where I would go next.

The failures are not random. In the last eight runs the row counts fall into two tight clusters, roughly 48k and roughly 23k, with nothing in between, and the low runs are 23, 26 and 29 August. That is every third night rather than a weekday pattern (those dates are a Saturday, a Tuesday and a Friday), which argues against anything tied to weekend traffic. I only eyed the eight most recent rows, though, so a three-day cadence is a guess drawn from three data points; pulling all thirty and plotting them would confirm or kill it quickly.

The more useful signal is the duration. Short nights run about seven minutes against about fifteen for full ones, so the job is not being truncated part-way through a normal workload: it starts, does half the work, and exits cleanly with status ok. Whatever goes wrong happens upstream of the write loop, in what `fetch_events` hands back, rather than in the transaction that writes rollups.

That points at two things I did not get far enough into. The window in `jobs/scheduler.py:61` is `last_success_at or (now - timedelta(hours=24))`, and I never checked what actually writes `last_success_at` or whether it records the start or the end of a run. If some path advances it mid-run, or a run's bookkeeping lands ahead of the data it consumed, the next window opens late and picks up a partial day. The other candidate is commit `9d02e1e`, "retry transient fetch errors". A retry wrapper that gives up after N attempts and returns the pages it managed to fetch would produce exactly this: fewer input rows, a shorter run, a successful transaction and an ok status. I did not read the body of `fetch_events`, so this is a hypothesis about the commit's title, not about its code.

To settle it I would read `fetch_events` and the retry path first, then find the write to `last_success_at`, and log the resolved `window_start`, `window_end` and `len(rows)` on every run so the next low night says which of the two it was. If the fetch layer has any retry or timeout counters, checking whether they spiked on the 23rd, 26th and 29th would probably answer it without waiting.
