# Migrating from formkit 2.x to 3.0

One change in this release will break working forms without printing an error or a warning: validators now run when a field loses focus and on submit, not on every keystroke.

Everything else in 3.0 either converts automatically or keeps working with a deprecation warning, so the bulk of the upgrade is mechanical. Budget your review time for the validation timing change, which is covered last and is the only part that requires you to look at each form and decide.

## Node 18 or later

Node 16 is no longer supported. Upgrade your local toolchain, your CI images, and your deployment runtime before you touch anything else, so that a failure later in the migration is unambiguously about formkit and not about the runtime underneath it.

## The configuration file

`formkit.json` becomes `formkit.config.js`. JSON could not express a computed value, which meant anything derived from an environment variable or a shared constant had to be duplicated by hand or generated by a build step. The new file is an ordinary module, so it can import, branch, and compute.

Run the converter on a clean working tree:

```
npx formkit migrate-config
```

It reads your existing `formkit.json`, writes `formkit.config.js`, and is expected to handle almost every case. Almost every is not every, so read the diff before you commit it, and pay particular attention to any values you had been keeping in sync by hand. Once the new file is in place and your build passes, delete `formkit.json`; 3.0 does not read it.

## `strictValidation` becomes `validation`

The boolean option `strictValidation` is replaced by `validation`, which takes a string. `true` becomes `"strict"` and `false` becomes `"loose"`. There is also a third value, `"off"`, which disables validation entirely and had no equivalent in 2.x.

The old boolean still works in 3.0 and prints a deprecation warning when it is used. It will be removed in 4.0, so treat the warning as a task rather than noise. `npx formkit migrate-config` handles this rename inside the config file, but if you set the option anywhere else, such as per-form or programmatically, you will need to change those call sites yourself.

## Validators receive a second argument

Field validators are now called with `(value, context)`, where `context` carries the values of the other fields in the form. This is additive. A one-argument validator written for 2.x continues to work unchanged, because the extra argument is simply ignored, and there is no need to touch validators that do not need it.

```js
// 2.x, and still correct in 3.0
const required = (value) => value !== '' || 'This field is required'

// 3.0: cross-field checks no longer need a closure over the form
const matchesPassword = (value, context) =>
  value === context.password || 'Passwords do not match'
```

If you previously reached other field values through a closure or a module-level reference to the form, `context` is now the supported way to do it, though the older approach is not broken.

## When validators run

In 2.x, validators ran on every keystroke. In 3.0 they run when a field loses focus, and again on submit. The old behaviour meant that a validator making a server-side check, such as testing whether a username is taken, fired one request per character typed.

Nothing in your code changes shape here, which is why this needs a manual pass. A form that depended on per-keystroke feedback will still render, still validate, and still submit; it will simply stop giving feedback until the user tabs away. To restore the old timing on a specific field, set `validateOn` where that field is defined:

```js
{
  name: 'password',
  validators: [strength],
  validateOn: 'input',
}
```

Go through your forms and look for fields whose validation was meant to be read while typing rather than after: password strength meters, character and length counters, live format hints on phone numbers or card numbers, and anything that renders a progress indicator as the user types. Those want `validateOn: "input"`. Fields backed by a network call are the ones the new default was written for, and they should be left alone.

A quick way to find candidates is to search for validators that return a value your UI renders continuously rather than only as an error, since those are the ones whose usefulness depends on running early. Once you have set `validateOn` where you want it, walk each form by hand, because the failure mode here is a form that looks correct and feels wrong.
