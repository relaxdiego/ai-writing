I'd keep it in Postgres, with one piece of precision that matters more than the same-versus-separate framing: the same *database* as application data, in its own schema, declaratively partitioned by month from day one. A separate Postgres database on the same cluster would give you most of the operational downsides and none of the join benefit, since you'd be back to FDW or dblink to reach user records.

The join requirement is what decides it. Support investigations are a daily-cadence need, and "join audit events against user records" is a one-line query when both live in the same database and a small integration project when they don't. The usual answer from the separate-store camp is to denormalise user attributes into each event, but attributes drift, and the support question is often about the user as they are now rather than as they were captured. Once you're reconstructing joins in application code across two systems, the cost lands on every investigation, not just the unusual ones.

There's a second argument for co-location that tends to go unmentioned in these debates: writing the audit event inside the same transaction as the action it records gives you atomicity for free. The event and the change it describes either both commit or neither does. Any pipeline that ships events to a separate store, whether through Kafka, a queue, or a batched writer, introduces a window where the two can disagree, and reconciling that window is exactly the work you don't want to be doing when an auditor asks why the log shows a change the data doesn't.

The separate-store camp is right about one thing, and it isn't volume. Two million events a day is about twenty-five writes per second on average, which Postgres does without noticing. What they're right about is that "append-only" needs to be enforced rather than assumed. You can get most of the way there inside Postgres: put the audit schema under a role that the application connects as with INSERT and SELECT only, revoke UPDATE and DELETE from every role the app touches, and add a hash chain over each row so that any retroactive edit breaks the chain from that point forward. Periodically anchoring the chain head somewhere outside the database gives you tamper-evidence that a database superuser can't quietly undo.

What actually threatens the co-located design is not write throughput but the size of the corpus. Seven years at this rate is roughly five billion rows, somewhere between two and five terabytes depending on payload size, and that lands on your backup window, your restore time, and your failover story for the application. Restoring the app after an incident should not mean restoring seven years of audit history first. Partitioning by month is what makes this tractable, both because it lets you back up and detach old partitions independently and because it's the only way you'll survive a schema change later. Retrofitting partitioning onto a two-billion-row table is a project; declaring it at table creation costs an afternoon. If you go this route, the partitioning decision has to happen before the table does.

That gives you a natural tiering: keep a hot window live, perhaps twelve to eighteen months, which covers essentially every support investigation, and export detached partitions as Parquet to object storage with Object Lock enabled for the seven-year tail. Queries against the old tail get slower and more deliberate, which is an accurate reflection of how often you'll run them.

The thing that would change my recommendation is a compliance regime that names the storage medium rather than the outcome. If your auditors work from something like SEC 17a-4, where non-rewritable, non-erasable media is a stated requirement rather than a property you demonstrate, then the hash-chain approach won't satisfy them and you should ship to a purpose-built store and accept the join pain. Worth finding out which kind of requirement you're under before the team spends more time split, because it's the only input here that flips the answer.
