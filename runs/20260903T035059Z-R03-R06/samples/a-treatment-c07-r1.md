Your key is the problem before the caching is. If the queries are parameterized, the SQL string is identical for every user who runs that code path: `SELECT ... FROM orders WHERE owner_id = ?` is one string, and the user identity lives in the bound parameters, not in the text. The first user to run it populates the entry and the next seven hundred read their rows out of it. That is an authorization bypass rather than a stale-data bug, and it will not show up in load testing because it only appears when two different users hit the same statement. If instead you interpolate literals into the SQL, the keys do differ per user, but then the keyspace is unbounded and you almost certainly have an injection surface as well. A workable key has to include the full parameter tuple plus any scope that comes from the session rather than from the query text.

The eight workers cut against the design in two directions. A module-level dictionary lives in one process's memory, so you get eight independent caches, each seeing roughly an eighth of the traffic, which is a much lower hit rate than a single-process estimate suggests. Worse, an invalidation on write only clears the cache in the worker that handled the write. At 400 writes a minute you are invalidating something in the working set every few seconds, and the other seven workers keep serving pre-write rows until they restart. The user-visible symptom is saving a record, refreshing, and seeing the old value about seven times in eight, depending on where the load balancer sends them. A plain dict also never evicts, so it grows until the process is OOM-killed.

What I would build instead: put the cache in Redis or memcached so all eight workers share one set of entries and a single delete on write reaches everyone. Key each entry on the normalized statement, the complete parameter tuple, and the authorizing user or tenant id read from the session. Give every entry a short TTL, thirty to sixty seconds, as a backstop for the invalidations you inevitably miss, and invalidate explicitly by table on write. Apply it only to reads you have measured as both frequent and slow; a cache in front of a two-millisecond indexed primary-key lookup adds a network round trip and buys nothing.

Before any of that, there is a cheaper version of your idea that carries none of these risks. Create the dictionary at the start of each request and throw it away at the end. It never outlives the authenticated request, so it cannot serve one user's rows to another; it never lives long enough to go stale; and it needs no invalidation or eviction at all. In most applications the repeated identical queries you are noticing are N+1 patterns inside a single request, which is exactly what this catches. Pair it with an EXPLAIN on your ten slowest queries, since a missing index on a hot filter column typically costs more than every repeated query combined.
