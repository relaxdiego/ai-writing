Write the events into Postgres inside the same transaction as the change they describe, then ship them to the append-only store and roll them off Postgres after a short hot window. The separate store is the system of record for the seven years; Postgres holds only recent history.

The case against making the append-only store the write path is that you lose atomicity. An audit event that can be written independently of the thing it records is an audit event that can go missing, and once the two writes are separate you have to pick a failure mode: fail the user's transaction when the audit store is unreachable, which hands your availability to a system that isn't on the critical path for anything the user wants, or drop the event and discover the gap during an audit. Writing to a local table sidesteps the choice entirely. The row commits with the change or neither does, and a background shipper moves it onward with retries and at-least-once delivery. Give each event a stable id so the archive can dedupe.

The case against keeping seven years in Postgres is operational rather than about capacity. Roughly 5.1 billion rows and several terabytes is not beyond a partitioned table, and 2 million events a day averages about 23 writes a second, which is nothing. The problem is that the audit data ends up inside your application database's backup, restore, replication and major-version-upgrade story. A point-in-time restore during an incident becomes a multi-terabyte operation dominated by data nobody needed to recover, and your RTO degrades for reasons unrelated to the outage. Cold audit rows also sit on the expensive storage tier, replicated to every standby, where in object storage they would cost a fraction as much.

The join requirement is the weakest argument in the room, and it argues against itself on closer reading. Joining audit events to current user records gives you the user as they are now, not as they were when the event happened, and for a support investigation or a compliance question the second is what you actually want. Denormalise the identity fields you care about into the event at write time: user id, email, role, tenant, whatever the investigation turns on. Then the archive is self-contained, the hot window in Postgres still supports live joins for the recent cases that make up nearly all support traffic, and older investigations query the archive without needing your production database at all.

One thing changes this calculus, and it's worth settling before the design: what the team means by "append-only." If it means object storage with a retention lock, you get genuine write-once semantics that no database role configuration can match, and the seven-year compliance story writes itself. If it means another database that the team has agreed not to update, you get the operational separation but not much more tamper-resistance than a hardened Postgres schema, and you should say so out loud rather than let the name carry an assurance the implementation doesn't provide. In either case, harden the Postgres side too: its own schema, a writer role with INSERT only, no UPDATE or DELETE grants, and monthly partitions so ageing data out is a detach rather than a mass delete.

Set the hot window to whatever your support team's real lookback is rather than a round number. Ninety days is a common answer and puts about 180 million rows in the live table, which partitions comfortably.
