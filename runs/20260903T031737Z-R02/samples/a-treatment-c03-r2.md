I migrated four of the five call sites off `LegacyConnection` — `src/billing/invoices.py`, `src/billing/refunds.py`, `src/reports/monthly.py`, and `src/reports/export.py` all now use `ConnectionPool`. The test suite passes (29 passed, 3 skipped), and a repeat grep confirms those four files are clean.

The fifth, `src/admin/backfill.py`, I left on `LegacyConnection`. It depends on `raw_cursor()` to stream 40M rows in chunks without materialising them, and per the note in the file, `ConnectionPool` has no streaming cursor equivalent as of v3.2 — I confirmed this against the code rather than taking the comment on faith only insofar as the comment matches what the call site actually does; I did not independently verify the ConnectionPool v3.2 API surface. Migrating it would mean either loading the full result set into memory or writing a pagination layer on top of the pool, and both are design decisions beyond what a mechanical migration should decide unilaterally.

So the deprecation isn't fully retired: one import remains, and anything gated on `LegacyConnection` disappearing entirely is still blocked. If you want that closed out, the options are to add a streaming cursor to `ConnectionPool`, rewrite the backfill around keyset pagination, or accept the single remaining usage and document it as an intentional exception. Tell me which and I'll do it.
