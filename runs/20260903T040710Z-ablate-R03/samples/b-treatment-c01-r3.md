I removed the duplicated TTL constant from the session cache. `src/cache/session.py` had `session_ttl = 3600` hardcoded on the class while `src/config/defaults.py` declared `SESSION_TTL_SECONDS = 900`, so the config value was dead and the cache was quietly running on the older number. The class attribute now reads from `SESSION_TTL_SECONDS`.

Worth being explicit that this is a behaviour change and not just a tidy-up: sessions now expire after 15 minutes rather than an hour, which is what the config always claimed but never delivered. If anything downstream was implicitly relying on the hour-long window, this is where it will show up. Going the other direction, changing `defaults.py` to 3600 to preserve current behaviour, is the alternative if the 900 was itself stale.

The first test run failed on `test_expiry_boundary`, which asserted the literal `3600` and so was pinning the bug in place rather than testing anything. I changed it to compare against `SESSION_TTL_SECONDS`, and all eight tests pass. Both files reference the constant without my having added an import, and since the assertion evaluates rather than raising `NameError`, the name is already in scope in each, presumably via an existing import or a star import I didn't inspect.

One thing I noticed while reading and did not touch: `get()` in `src/cache/session.py` uses a bare `now` at line 88 with no assignment anywhere in the method body. Either it comes from an enclosing scope or module level, or that expiry branch would fail the moment it is reached, which would also mean `test_expiry_boundary` is not actually exercising expiry despite its name.
