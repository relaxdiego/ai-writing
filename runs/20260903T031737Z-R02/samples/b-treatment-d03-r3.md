# ADR 0014: Use Postgres `SKIP LOCKED` for background job queueing

**Status:** Accepted — implemented in Q3
**Date:** 2026-09-03

## Context

Our background work currently runs through a hand-rolled runner that polls a table, marks rows in flight with an `UPDATE`, and relies on a single worker process to avoid double execution. It has no retry policy worth the name, no scheduling beyond "run soon," and it cannot be scaled horizontally without racing itself. We need to replace it with something we can reason about under failure, and we need to do that without changing how the rest of the application is deployed.

Three options were evaluated: Celery backed by Redis, RQ (also Redis-backed), and a queue built on Postgres using `SELECT ... FOR UPDATE SKIP LOCKED`. Four properties of our situation drove the comparison. First, we already run Postgres in production with backups, monitoring, failover, and an on-call rotation that understands it; Redis would be a second stateful system on that rotation, and neither the durability configuration nor the failover behaviour of Redis is currently knowledge our team holds. Second, our volume is modest — roughly 30,000 jobs a day, averaging well under one per second, with observed peaks around 40 per second — so throughput is not the binding constraint. Third, and most decisively, most of our jobs are enqueued as a consequence of a database write, and we need the two to commit or fail together; with a separate broker that guarantee requires a transactional outbox, which means a Postgres queue table plus a relay process plus the broker, so we would be building the Postgres queue anyway and then paying for Redis on top of it. Fourth, nobody on the team has run Celery in production, and Celery's failure modes — visibility timeouts, prefetch behaviour, lost acks on worker kill — are exactly the kind of thing that is learned during an incident rather than before one.

## Decision

We will implement job queueing as a `jobs` table in our primary Postgres database. Workers claim work with `SELECT ... FOR UPDATE SKIP LOCKED LIMIT n`, execute the job, and mark the outcome in the same transaction that releases the lock. Enqueueing is an ordinary `INSERT` inside the caller's existing transaction, which gives us atomicity between the business write and the job that depends on it for free, with no outbox and no relay. Retry counts, backoff schedules, and future-dated execution are columns on the same table, evaluated by the claiming query.

## Consequences

The costs we are accepting are known and bounded. `SKIP LOCKED` queueing does not scale much past a few hundred jobs per second before lock contention and table churn on the queue table start to matter, which leaves us something like an order of magnitude of headroom above our current peak — comfortable, but not indefinite, and worth watching as a capacity signal rather than discovering at the limit. We are also writing our own retry and scheduling logic, estimated at around 400 lines, which is code we own and must test rather than a library someone else maintains; we judged that acceptable partly because that logic is small and mostly declarative, and partly because the alternative was not zero code but outbox code of comparable size. Finally, a long-running job holds a Postgres connection for its duration, so the connection pool becomes a shared resource between web traffic and background work — we will isolate this by giving workers their own pool with its own ceiling, and by treating any job whose runtime approaches minutes as a design problem to be broken up rather than a pool-sizing problem to be absorbed.

The queue table will need routine maintenance that a broker would have handled implicitly: completed rows must be archived or deleted on a schedule, and the table needs autovacuum settings tuned more aggressively than our defaults, since a queue is a high-churn table whose dead tuples accumulate quickly. Operationally, the upside is that queue depth, job latency, and failure counts are all just SQL, visible to the same dashboards and the same ad-hoc queries we already use, and a queue backup is a database backup.

We should revisit this decision if sustained throughput approaches 200 jobs per second, if job durations grow such that connection-holding becomes the limiting factor on pool sizing, or if we acquire a requirement — fan-out to many consumers, cross-service pub/sub, sub-second scheduling precision — that a relational queue serves badly. Should any of those arrive, the migration path is reasonably clean: the enqueue interface stays, and jobs that genuinely need a broker can move behind it while the transactional ones stay where they are.
